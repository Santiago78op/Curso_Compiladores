Etapa 5 · Parte 1

Todo el control de flujo, y lo que casi se escapa de un análisis semántico

if/else if/else, switch sin fall-through, tres formas de for, recursión — y una auditoría de código real (2026-07-21) que encontró y corrigió cuatro problemas de validación semántica en esta misma zona del intérprete.

Ejemplo real — entradas/ejemplo4_control.vch

if / else if / else

func clasificar(n int) string {
    if n < 0 {
        return "negativo"
    } else if n == 0 {
        return "cero"
    } else {
        return "positivo"
    }
}

Gramática (Etapa 1): 'if' expr bloque ('else' 'if' expr bloque)* ('else' bloque)?. La condición de cada rama debe evaluar a bool — el intérprete reporta error semántico si no (retomado en la diapositiva de la auditoría).

Ejemplo real — entradas/ejemplo4_control.vch

switch sin fall-through

mut dia := 3
switch dia {
case 1:
    print("lunes")
case 2:
    print("martes")
case 3:
    print("miercoles")
default:
    print("otro dia")
}

Diferencia real con CompInterpreter (OLC1, Jison): la sección 4.7.2 del enunciado indica explícitamente que "el break implícito está incluido al final de cada case". Es una decisión de diseño del lenguaje V-Lang Cherry, no una limitación: no hay fall-through entre casos, a diferencia de otro lenguaje del curso que sí lo implementa. Dos lenguajes distintos, semántica de switch distinta a propósito.

Tres formas de for, una sola sentencia

for: condición, clásico y rango

sentenciaFor
    : 'for' expr bloque                                        # forCondicion
    | 'for' forInit? ';' expr? ';' forActualizacion? bloque     # forClasico
    | 'for' ID ',' ID 'in' expr bloque                          # forRango
    ;
mut i := 0
for i < 5 {                    // forCondicion: equivalente a "while"
    print("while-like:", i)
    i++
}

for j := 0; j < 100; j++ {      // forClasico
    if j == 3 { break }
    print("clasico:", j)
}

for _, v in valores {           // forRango: indice, valor
    if v % 2 == 0 { continue }
    print("impar:", v)
}

Las tres alternativas etiquetadas (#forCondicion, #forClasico, #forRango) generan, otra vez, tipos de contexto Go distintos — el traductor (Etapa 2) las distingue con su type-switch igual que hace con expr.

Ejemplo real — entradas/ejemplo5_funciones.vch

Recursión y llamada hacia adelante

func main() {
    // llamada a una funcion declarada MAS ABAJO en el archivo
    print("factorial(5) =", factorial(5))
    print("fibonacci(8) =", fibonacci(8))
}

func factorial(n int) int {
    if n <= 1 { return 1 }
    return n * factorial(n - 1)
}

func fibonacci(n int) int {
    if n < 2 { return n }
    return fibonacci(n - 1) + fibonacci(n - 2)
}

main llama a factorial, declarada más abajo en el archivo — funciona porque el intérprete de dos pasadas (Etapa 0, retomada en la próxima diapositiva) ya registró todas las funciones antes de ejecutar el cuerpo de ninguna. factorial y fibonacci se llaman a sí mismas: cada invocación crea su propio entorno local (NuevoEntorno), con n resuelto en la cadena de entornos correcta.

Cómo se rastrea "estar dentro de un ciclo o switch"

Dos contadores: profLoop y profSwitch

// profLoop/profSwitch cuentan cuantos "for"/"switch" anidados rodean la
// sentencia que se esta ejecutando ahora mismo (4.8.1/4.8.2: break solo
// es valido dentro de un ciclo o un switch, continue solo dentro de un
// ciclo). invocarFuncion los resetea a 0 al entrar a una funcion/metodo
// nuevo, para que un break/continue "perdido" en el cuerpo de una funcion
// llamada desde dentro de un ciclo no "herede" el contexto del llamador.
profLoop   int
profSwitch int

Antes de ejecutar el cuerpo de un for, se incrementa profLoop; antes de un switch, profSwitch. Al invocar una función, ambos se guardan y se resetean a 0, y se restauran al volver — así un break dentro de una función invocada desde un for no se vuelve válido "por herencia" del contexto del llamador.

Caso de estudio: auditoría de código real, 2026-07-21

Cuatro correcciones de validación semántica

Este mismo tramo del intérprete (control de flujo y declaración global) pasó por una auditoría que encontró cuatro casos donde el análisis semántico era incompleto o inconsistente frente al enunciado. Ninguno rompía los ejemplos existentes — por eso pasaron desapercibidos hasta revisarlos a propósito.

Por qué importa para la defensa oral: son ejemplos concretos de la diferencia entre "el programa corre" y "el programa valida lo que el enunciado exige validar" — un análisis semántico incompleto puede dejar pasar silenciosamente errores que sí deberían reportarse (sección 8.1).

Hallazgo 1 de 4

break/continue fuera de ciclo o switch

El enunciado (4.8.1/4.8.2) exige reportar error si break aparece fuera de un ciclo o switch, o si continue aparece fuera de un ciclo — antes de la corrección, este caso no se detectaba. Ahora profLoop/profSwitch (diapositiva anterior) lo validan directamente:

case *ast.SentenciaBreak:
    // 4.8.1: "la sentencia break solo se puede usar dentro de un bucle
    // (for) o un switch... si se encuentra fuera se considerara un error".
    if in.profLoop == 0 && in.profSwitch == 0 {
        in.errorSemantico("la sentencia \"break\" no puede usarse fuera de un ciclo o un switch", n.Linea, n.Columna)
        return Senal{Tipo: SenalNinguna}
    }

Fuente: internal/runtime/interprete.go.

Hallazgo 2 de 4

Comparación relacional (<, <=, …) entre strings

La sección 4.4 dice, en general, que "los operandos pueden ser numéricos, Strings o lógicos" para las comparaciones, y la 4.4.1 agrega que "las comparaciones entre cadenas se hacen lexicográficamente" — una nota que, pese a aparecer bajo el título de igualdad/desigualdad, describe un criterio de orden, no de igualdad. Faltaba aplicarlo también a los operadores relacionales:

func Relacional(op string, a, b Valor) (Valor, error) {
    var cmp int
    switch {
    case EsNumerico(a.Tipo) && EsNumerico(b.Tipo):
        fa, fb := aFloat(a), aFloat(b)
        cmp = compararFloats(fa, fb)
    case a.Tipo.Base == TRune && b.Tipo.Base == TRune:
        cmp = int(a.R) - int(b.R)
    case a.Tipo.Base == TString && b.Tipo.Base == TString:
        cmp = strings.Compare(a.S, b.S)
    default:
        return Valor{}, fmt.Errorf("no se puede comparar (%s) entre %s y %s", op, a.Tipo, b.Tipo)
    }
    // ...
}

Fuente: internal/runtime/operaciones.go, función Relacional. Este es el punto 8 de docs/gramatica.txt (decisiones de diseño).

Hallazgo 3 de 4

Colisión de nombres en ámbito global (7.1)

El enunciado exige que función, variable y struct no compartan nombre en el ámbito global. Faltaba validar la colisión entre las tres categorías — no solo la redeclaración dentro de la misma categoría:

// una variable global no puede llamarse igual que un struct o funcion ya
// registrados (7.1: "no podra existir una funcion, variable o struct con el
// mismo nombre") - los structs y funciones ya estan completamente
// registrados quando esto corre (dos pasadas).
if _, existe := in.global.Structs[n.Nombre]; existe {
    in.errorSemantico("el nombre \""+n.Nombre+"\" ya está en uso por un struct", n.Linea, n.Columna)
}
if _, existe := in.global.Funciones[n.Nombre]; existe {
    in.errorSemantico("el nombre \""+n.Nombre+"\" ya está en uso por una función", n.Linea, n.Columna)
}

Fuente: internal/runtime/interprete.go. Simétricamente, al registrar una función se valida que su nombre no coincida con un struct ya registrado.

Hallazgo 4 de 4

El switch que silenciaba errores de tipo

Al comparar la expresión del switch contra cada case, una combinación de tipos inválida (por ejemplo comparar un int contra un struct) se descartaba en silencio, como si el caso simplemente no coincidiera — inconsistente con cómo == reporta ese mismo error fuera de un switch:

igual, err := valoresIguales(val, cv)
if err != nil {
    // 4.4.1: "cualquier otra combinacion sera invalida y se debera
    // reportar el error" - antes este caso se descartaba en silencio
    // (como si simplemente no coincidiera), inconsistente con como
    // evaluarBinaria reporta el mismo error para == fuera de un switch.
    l, c := caso.Valor.Pos()
    in.errorSemantico(err.Error(), l, c)
    continue
}

Fuente: internal/runtime/interprete.go, función ejecutarSwitch.

Chequeo rápido

Sobre control de flujo, recursión y la auditoría

1 · ¿Por qué factorial puede invocarse desde main aunque se declara más abajo en el archivo?

Por el intérprete de dos pasadas: TODAS las funciones se registran en global.Funciones antes de ejecutar el cuerpo de ninguna. Para cuando main() corre, factorial ya está disponible.

2 · Un break dentro de una función f(), invocada desde dentro de un for en main, ¿es válido?

No, es un error semántico. invocarFuncion resetea profLoop/profSwitch a 0 al entrar a f() — el for del llamador no cuenta como contexto válido dentro del cuerpo de la función invocada.

3 · ¿Qué tienen en común los 4 hallazgos de la auditoría?

Los cuatro son casos donde el análisis semántico dejaba pasar (o descartaba en silencio) algo que el enunciado exige reportar como error: break/continue fuera de contexto (4.8), comparación relacional de strings (4.4.1), colisión de nombres global (7.1) y errores de tipo en casos de switch (4.4.1). Ninguno es un fallo de ejecución — todos son huecos de validación.
