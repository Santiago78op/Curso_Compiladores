Profundización ★

Tres generadores, cinco proyectos, un mismo problema

Los cinco proyectos del curso (DataForge, ConjAnalyzer, CompScript, CompInterpreter, VLangCherry) resuelven el mismo problema — reconocer un lenguaje y construir un analizador léxico/sintáctico — con tres herramientas distintas. Esta profundización las compara directamente, con ejemplos reales de cada una.

1 de 3 · Dos herramientas separadas

JFlex + CUP: léxico y sintaxis en archivos distintos

// Lexer.flex (JFlex) — fragmento real de DataForge
"var"       { return symbol(sym.VAR); }
{Numero}    { return symbol(sym.NUMERO, Double.valueOf(yytext())); }
{Id}        { return symbol(sym.ID); }

El .flex solo conoce tokens; la gramática vive aparte, en un .cup, que declara terminal/non terminal y produce las reglas con acciones semánticas embebidas ({: RESULT = … :}). CUP genera además la clase sym con las constantes de token — el lexer y el parser deben coincidir en esos nombres, pero se escriben y mantienen por separado.

DataForge no construye AST: como no tiene control de flujo (toda instrucción corre exactamente una vez), ejecuta directamente en las acciones del .cup — gramática S-atribuida. VLangCherry sí necesita AST, precisamente porque tiene control de flujo y recursión (Etapas 2 y 5).

2 de 3 · Una herramienta, target JavaScript

Jison: LALR sobre Node.js

CompInterpreter (OLC1) usa Jison: como ANTLR4, resuelve léxico y sintaxis en un solo archivo de especificación, pero sigue generando parsers LALR/SLR/LR con tablas precomputadas — la misma familia de algoritmo que CUP, distinto lenguaje de salida.

npx jison src/grammar.jison -o src/parser.js

El reporte de AST de CompInterpreter (reportes/ast-grafo.js) recorre el árbol dinámicamente inspeccionando las propiedades de cada objeto JavaScript — el mismo problema que resuelve internal/ast/grafo.go en VLangCherry (Etapa 2), pero con introspección dinámica de JS en vez de reflect de Go.

3 de 3 · Una herramienta, target Go

ANTLR4: LL adaptativo, con etiquetas por alternativa

expr
    : expr op=('*'|'/'|'%') expr         # exprMultiplicativa
    | expr op=('+'|'-') expr             # exprAditiva
    | literal                            # exprLiteral
    | ID                                  # exprIdentificador
    ;

La diferencia que más impacto tiene en el resto del proyecto no es el algoritmo de parsing en sí, sino las etiquetas #nombre: generan un tipo de contexto Go concreto por alternativa, algo que ni JFlex+CUP ni Jison ofrecen de forma directa. Es lo que le permite a VLangCherry evitar el patrón Visitor completo con un type-switch (Etapa 2) — una opción que, en rigor, ANTLR4 también ofrece como Visitor generado, pero que este proyecto decidió no usar.

La lección de fondo

La herramienta no decide el diseño — lo habilita

El generador es un medio

Los 5 proyectos resuelven "reconocer un lenguaje" de tres formas distintas, pero ninguna elección de herramienta obliga por sí sola a tener o no tener AST, a usar Visitor o type-switch, o a ejecutar directo en las acciones semánticas.

El requisito del enunciado sí decide

En VLangCherry, el lenguaje de implementación (Go) fue lo que descartó JFlex+CUP y Jison — no una preferencia de estilo. La elección de generador siguió al requisito, no al revés (Etapa 0).

Los patrones se repiten entre proyectos

"Entorno fresco por ejecución", "propagación de error sin cascada", "reporte de AST por recorrido genérico" aparecen en los 5 proyectos, implementados con el idioma de cada lenguaje de turno (Java, JS, Go) — son decisiones de diseño de compiladores, no atadas a una herramienta.

Chequeo rápido

Sobre los tres generadores

1 · ¿Cuál de los tres generadores resuelve léxico y sintaxis en archivos SEPARADOS?

Solo JFlex+CUP (dos herramientas, dos archivos: .flex y .cup). Jison y ANTLR4 usan un único archivo de especificación cada uno.

2 · ¿Qué tienen en común los parsers que genera JFlex+CUP y los que genera Jison?

Ambos son parsers LALR (Jison además soporta SLR/LR configurable): construyen tablas de estados en tiempo de generación. ANTLR4, en cambio, genera un parser LL adaptativo que decide en tiempo de análisis.

3 · Si CompInterpreter (Jison) hubiera necesitado generar código para Go en vez de JavaScript, ¿habría podido seguir usando Jison?

No — Jison solo genera JavaScript. Habría necesitado cambiar de herramienta, igual que VLangCherry tuvo que descartar JFlex+CUP y Jison por el requisito de Go y terminar en ANTLR4.

Profundización ★ · completa

Tres caminos al mismo destino

JFlex+CUP (Java, LALR, dos herramientas), Jison (JavaScript, LALR/SLR/LR, una herramienta) y ANTLR4 (Go entre otros, LL adaptativo, una herramienta con etiquetas por alternativa) — tres formas válidas de resolver el análisis léxico y sintáctico, elegidas cada una por el requisito real del proyecto que las usa.
