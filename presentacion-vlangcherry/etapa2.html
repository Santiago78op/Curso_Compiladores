Etapa 2 · Parte 1

Por qué no basta el parse tree de ANTLR

El parser de la Etapa 1 ya entrega un árbol completo y correcto. Aun así, VLangCherry no interpreta directamente sobre ese árbol: lo traduce a un AST propio, definido en internal/ast. Esta etapa explica por qué vale la pena ese paso extra.

Dos preguntas para toda la etapa: ¿qué se gana con un AST propio? ¿y por qué el traductor no implementa el patrón Visitor que ANTLR generó para eso mismo?

Decisión de diseño 1

AST propio en vez del parse tree de ANTLR

Desacoplamiento

Los tipos de contexto que genera ANTLR (ExprMultiplicativaContext, …) cambian si se regenera la gramática. Si el intérprete dependiera de ellos directamente, cualquier ajuste al .g4 podría romper el runtime entero.

Control del reporte visual

El enunciado (sección 8.3) pide un reporte de AST navegable en el cliente. Un AST propio, diseñado a medida, se puede recorrer y serializar exactamente como conviene — el parse tree de ANTLR trae mucho ruido (tokens, nodos intermedios) que no aporta al reporte.

Todo nodo del AST propio implementa una interfaz mínima, en internal/ast/ast.go:

type Nodo interface {
    Tipo() string
    Pos() (int, int)
}

Alrededor de 25 tipos de nodo concretos (Programa, DeclStruct, DeclFuncion, Bloque, SentenciaIf, ExprBinaria, LiteralStruct, …), todos embebiendo un base{Linea, Columna int} que resuelve Pos() para el reporte de errores con posición.

Decisión de diseño 2 — la más importante de la etapa

El traductor: type-switch en vez de Visitor generado

ANTLR genera una interfaz VLangCherryVisitor con un método por cada regla/alternativa etiquetada — el patrón Visitor clásico del Dragón (doble despacho accept/visit). Implementarla completa significa escribir ~60 firmas en BaseVLangCherryVisitor.

El comentario de cabecera de internal/traductor/traductor.go documenta la alternativa elegida:

// Package traductor convierte el parse tree que genera ANTLR en el AST
// propio de internal/ast. No usa el patron Visitor generado: como cada
// alternativa etiquetada de la gramatica produce un tipo de contexto Go
// concreto, alcanza con un type-switch directo (mas corto que implementar
// las ~60 firmas de BaseVLangCherryVisitor).

Por qué funciona: es exactamente la etiqueta #nombre de la Etapa 1 la que hace posible esto. Como cada alternativa ya tiene su propio tipo Go concreto, Go mismo puede distinguir el tipo dinámico con un switch — no hace falta que el propio nodo "sepa" a quién visitarse (el doble despacho del Visitor clásico).

Código real

traducirExpr, un caso por alternativa

func traducirExpr(ctx parser.IExprContext) ast.Nodo {
    switch ec := ctx.(type) {
    case *parser.ExprLlamadaContext:
        l, c := pos(ec)
        n := &ast.ExprLlamada{Callee: traducirExpr(ec.Expr())}
        n.Linea, n.Columna = l, c
        if la := ec.ListaArgumentos(); la != nil {
            n.Argumentos = traducirListaArgumentos(la.(*parser.ListaArgumentosContext))
        }
        return n
    case *parser.ExprMultiplicativaContext:
        return traducirBinaria(ec, ec.AllExpr(), ec.GetOp().GetText())
    // ... un case por cada alternativa etiquetada de la regla expr
    }
    return nil
}

Un case por cada una de las 15 alternativas etiquetadas de expr (Etapa 1). El helper compartido para posición:

func pos(ctx antlr.ParserRuleContext) (int, int) {
    t := ctx.GetStart()
    return t.GetLine(), t.GetColumn() + 1
}

Un detalle no evidente

Lectura y escritura comparten los mismos nodos

traducirLugar (para el lado izquierdo de una asignación) y traducirExpr (para lectura) producen exactamente los mismos tipos de nodo — ast.Identificador, ast.ExprIndice, ast.ExprCampo — para las mismas construcciones sintácticas (ID, lugar[expr], lugar.campo).

¿Quién decide entonces si se lee o se muta? No el traductor: el intérprete, más adelante, según si el nodo aparece del lado derecho de una asignación (necesita el valor, vía evaluar) o del lado izquierdo (necesita un puntero mutable a la celda, vía resolverLugar — Etapa 3). El AST queda más simple porque esa distinción no vive en su forma, sino en cómo se lo recorre.

El reporte de AST (§8.3 del enunciado)

Recorrer cualquier nodo con reflect

internal/ast/grafo.go construye el reporte visual del AST recorriendo cualquier Nodo mediante el paquete reflect, sin mantenimiento adicional cuando se agrega un tipo de nodo nuevo:

func ConstruirGrafo(raiz Nodo) Grafo
Caso, campo por campo del structQué hace
Puntero/interfaz que implementa NodoGenera un nodo hijo + una arista etiquetada con el nombre del campo.
SliceCada elemento se procesa individualmente, con nombre de campo indexado (Campos[0], Campos[1], …).
Struct "contenedor transparente" (RamaIf, CasoSwitch, Parametro, …)No implementa Nodo por sí mismo: sus campos se recorren propagando un nombre compuesto (Ramas[0].Condicion).
TipoASTSe serializa como texto (ta.String()) pegado a la etiqueta del nodo padre, sin nodo de grafo aparte.
Valor escalarSe agrega como texto ("campo: valor") a la etiqueta del nodo.

El resultado (Grafo{Nodes, Edges}) viaja como JSON al cliente, que lo dibuja con vis-network (Etapa 7) — mismo formato {nodes, edges} que ya usaba CompInterpreter. También se genera un .dot equivalente (ADot) por si se quiere graficar con Graphviz del lado del servidor.

Mismo patrón, dos lenguajes distintos

Reflection en Go, introspección dinámica en JS

Este patrón — recorrido genérico del AST para construir un reporte visual, sin mantenimiento por tipo de nodo — es análogo al empleado en reportes/ast-grafo.js de CompInterpreter (otro proyecto del curso, en JavaScript). Ahí se logra iterando dinámicamente sobre las propiedades de un objeto; acá, sobre los campos exportados de un struct Go vía reflect.Value/reflect.Type.

Consecuencia práctica para el mantenimiento: si se agrega un tipo de nodo nuevo al AST, no hace falta tocar grafo.go — el recorrido por reflection lo incorpora automáticamente al reporte, siempre que sus campos sean exportados (mayúscula inicial) y de un tipo reconocido (Nodo, slice de Nodo, struct contenedor, TipoAST, o escalar).

Chequeo rápido

Sobre el traductor y el AST

1 · ¿Qué habría que implementar si el proyecto SÍ hubiera usado el patrón Visitor generado?

Las ~60 firmas de BaseVLangCherryVisitor (un método Visit... por regla/alternativa etiquetada). El type-switch del traductor logra lo mismo con muchísimo menos código repetido.

2 · Si se agrega un tipo de nodo nuevo al AST (por ejemplo, una nueva sentencia), ¿hay que modificar grafo.go?

No, siempre que sus campos sean exportados y de un tipo reconocido — el recorrido por reflect lo incorpora solo. Sí hay que agregarle su caso en el type-switch del traductor, y su etiqueta #nombre en el .g4 si corresponde a una alternativa de gramática.

3 · ¿Por qué numeros[i] = x y leer numeros[i] usan el mismo nodo ast.ExprIndice?

Porque el traductor no distingue lectura de escritura: produce el mismo nodo para la misma construcción sintáctica. Es el intérprete quien decide, según el contexto (lado izquierdo o derecho de =), si necesita el valor o un puntero mutable a la celda.
