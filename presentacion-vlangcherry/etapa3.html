Etapa 3 · Parte 1

Un valor que sabe pasar por referencia sin que nadie se lo pida

El enunciado (sección 7.1) exige que structs y slices se pasen por referencia y los tipos primitivos por valor. Esta etapa muestra cómo el modelo de valores de VLangCherry logra eso sin implementar ningún mecanismo especial de paso de parámetros: lo resuelve la estructura misma del tipo Valor.

El modelo de valores (internal/runtime/valores.go)

Un solo tipo Valor para todo el lenguaje

type Valor struct {
    Tipo   Tipo
    I      int64
    F      float64
    S      string
    B      bool
    R      rune
    Slice  *SliceVal
    Struct *StructVal
}

Cada valor en tiempo de ejecución — sea un int, un string, un slice o una instancia de struct — es una instancia de este mismo tipo Go, con el campo Tipo indicando cuál de los demás campos es el que importa.

La decisión de diseño, documentada en el propio código

Por referencia "gratis": Slice y Struct ya son punteros

// Valor es el valor en tiempo de ejecucion de una expresion VLangCherry.
// Slice y Struct viajan por puntero: asi una copia del Valor (paso de
// parametro, asignacion) comparte la misma identidad subyacente, que es
// exactamente el "por referencia" que pide la seccion 7 para structs y
// slices (los primitivos, en cambio, se copian por valor via los campos
// escalares I/F/S/B/R).

El truco: Go copia structs por valor automáticamente (al pasar un parámetro, al hacer una asignación). Si Valor se copia, sus campos *SliceVal y *StructVal también se "copian" — pero copiar un puntero no copia lo apuntado. Dos variables VLangCherry que "comparten" un struct terminan apuntando literalmente al mismo StructVal en memoria.

No hace falta una tabla de referencias explícita ni un mecanismo de "boxing": la semántica de referencia compartida sale gratis de cómo Go maneja sus propios punteros.

Ejemplo real — entradas/ejemplo2_structs.vch

Un método que lee, otro que muta

struct Direccion {
    string Ciudad
    int CodigoPostal
}

struct Persona {
    string Nombre
    int Edad
    Direccion Domicilio
}

func (p Persona) Saludar() string {
    return "Hola, soy " + p.Nombre
}

func (p *Persona) Cumplir() {
    p.Edad = p.Edad + 1
}

func main() {
    mut persona := Persona{Nombre: "Ana", Edad: 25, Domicilio: casa}
    print(persona.Saludar())
    persona.Cumplir()
    print("Edad despues:", persona.Edad)   // 26: SI cambio
}

Saludar recibe p Persona (receptor por valor): puede leer, pero mutar p.Nombre ahí adentro no tendría efecto sobre persona. Cumplir recibe p *Persona (receptor por puntero): mutar p.Edad sí se refleja afuera, porque — dado que Valor.Struct ya es un puntero — persona y el p dentro del método apuntan al mismo StructVal.

Cómo se implementa la mutación

resolverLugar: el puntero a la celda real

func (in *Interprete) resolverLugar(nodo ast.Nodo, ent *Entorno) (*Valor, bool)

Dado un nodo ast.Identificador, ast.ExprIndice o ast.ExprCampo (los mismos nodos que produce el traductor tanto para lectura como para escritura — Etapa 2), esta función devuelve un *Valor a la celda real referenciada, no una copia.

Se usa en toda operación que muta un dato existente: asignación simple (=), compuesta (+=, -=) e incremento/decremento (++, --). Es lo que garantiza que numeros[2] = 100 o p.Edad = 30 muten el dato real dentro del slice o del struct, y no una copia efímera que se descarta al terminar la expresión.

Una excepción intencional

append no muta en el lugar

Todo lo anterior describe mutación compartida — excepto append, que siempre produce un SliceVal nuevo, igual que en el Go real:

numeros = append(numeros, 60)   // hace falta reasignar

Por qué no es una inconsistencia: es el mismo comportamiento del append real de Go, donde crecer un slice puede requerir reservar un arreglo subyacente más grande — el valor devuelto no necesariamente comparte identidad con el original. Reproducir esa semántica exacta (en vez de mutar siempre en el lugar) evita sorpresas a quien ya conoce Go.

Tipado estático, con una relajación deliberada

tipoCompatible/coercionar: int↔float64

La sección 3.6 del enunciado exige tipo exacto en toda asignación. Pero las tablas aritméticas de la sección 4.3 muestran, de forma sistemática, promoción automática int + float64 -> float64 asignada de vuelta a variables float64 — y el propio 3.7 ya admite una excepción para el literal 0 ("se considera tanto int como float").

Decisión tomada: se relaja la regla de tipo exacto para permitir la mezcla int↔float64 en cualquier asignación (no solo para el literal 0), documentado tanto en el código (tipoCompatible/coercionar, internal/runtime/interprete.go) como en docs/gramatica.txt. Todas las demás combinaciones de tipo (por ejemplo string asignado a una variable int) siguen siendo error semántico — es la excepción real que muestra el enunciado, no una relajación general del tipado estático.

Chequeo rápido

Sobre tipos, structs y referencia

1 · Si Cumplir hubiera tenido receptor (p Persona) en vez de (p *Persona), ¿qué imprimiría print("Edad despues:", persona.Edad)?

25, sin cambiar. Con receptor por valor ((p Persona)), invocarFuncion clona el struct con ClonarPorValor — una copia en profundidad, igual que Go copia un struct al pasarlo por valor. El método trabaja sobre esa copia, así que su p.Edad = p.Edad + 1 no toca el struct del llamador: persona.Edad sigue en 25. Con receptor por puntero ((p *Persona)) sí se comparte el StructVal y el cambio se vería (26). Es exactamente la distinción que documenta la sección 7.1 del enunciado. (Ojo para la defensa: este comportamiento correcto es reciente — hasta la auditoría del 2026-07-23 el receptor por valor compartía el struct por error, porque ReceptorPuntero no se leía; hallazgo A4 del Manual Técnico 8.8.)

2 · ¿Por qué numeros = append(numeros, 60) necesita el numeros = explícito, si structs y slices ya se comparten por puntero?

Porque append es la excepción intencional: siempre devuelve un SliceVal nuevo (igual que en Go real), en vez de mutar el existente. Sin la reasignación, la variable original seguiría apuntando al slice viejo.

3 · ¿Es válido asignar "hola" a una variable declarada int?

No — error semántico de tipo incompatible. La única mezcla que se relajó frente a la sección 3.6 es int↔float64; el resto del tipado estático se exige tal cual pide el enunciado.
