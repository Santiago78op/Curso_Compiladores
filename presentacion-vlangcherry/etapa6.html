Etapa 6 · Parte 1

Un servidor con la librería estándar, nada más

Todas las etapas anteriores viven detrás de un único endpoint REST. El servidor (cmd/servidor/main.go) se implementa exclusivamente con net/http — sin frameworks — y expone el mismo contrato, en forma, que CompInterpreter (otro proyecto del curso, servido con Node/Express).

La API

Tres rutas, un solo endpoint que importa

Método y rutaDescripción
GET /Información básica del servicio (nombre, estado, endpoint disponible).
GET /saludVerificación de estado ({"estado": "ok"}).
POST /interpretarEndpoint principal. Recibe { "codigo": "<fuente .vch>" } y responde el resultado completo del análisis.

Todas las rutas incluyen encabezados CORS (Access-Control-Allow-Origin: *), habilitando que el cliente web (servido desde un origen distinto en desarrollo — Etapa 7) consuma la API sin restricciones.

El contrato de respuesta

Un JSON con cuatro reportes

type Resultado struct {
    Errores       []runtime.ErrorReporte `json:"errores"`
    Consola       string                 `json:"consola"`
    ConsolaLineas []string               `json:"consolaLineas"`
    Simbolos      []runtime.FilaSimbolo  `json:"simbolos"`
    AST           ast.Grafo              `json:"ast"`
    Dot           string                 `json:"dot"`
}

func Analizar(codigo string) Resultado

internal/analizar/analizar.go implementa el pipeline completo (Etapa 0) por cada petición: lexer → parser → traductor (Etapa 2) → intérprete (Etapa 5) → este mismo Resultado, serializado a JSON.

Un criterio compartido con DataForge y ConjAnalyzer

Entorno nuevo en cada petición

entrada := antlr.NewInputStream(codigo)
lexer := parser.NewVLangCherryLexer(entrada)
lexer.RemoveErrorListeners()
lexer.AddErrorListener(&oyenteErrores{errores: errores, esLexer: true})
// ...
arbolParse := p.Programa()
programa := traductor.Traducir(arbolParse)
grafo = ast.ConstruirGrafo(programa)
interprete.Interpretar(programa)

No se conserva estado entre peticiones. Cada llamada a Analizar(codigo string) crea una instancia nueva de runtime.Interprete y de sus estructuras internas (consola, tabla de símbolos, lista de errores) — mismo criterio de "entorno fresco por ejecución" que DataForge y ConjAnalyzer aplican en Java: los reportes de una ejecución nunca se mezclan con los de otra.

Cómo se capturan errores léxicos y sintácticos de ANTLR

Reemplazar el DefaultErrorListener

type oyenteErrores struct {
    *antlr.DefaultErrorListener
    errores *runtime.ListaErrores
    esLexer bool
}

func (o *oyenteErrores) SyntaxError(recognizer antlr.Recognizer, offendingSymbol interface{},
    line, column int, msg string, e antlr.RecognitionException) {
    if o.esLexer {
        o.errores.Lexico(msg, line, column+1)
    } else {
        o.errores.Sintactico(msg, line, column+1)
    }
}

El mismo listener se registra tanto en el lexer como en el parser generados por ANTLR (esLexer distingue de cuál viene el error), acumulando en la misma ListaErrores que usa el intérprete para los errores semánticos — el enunciado (8.1) exige recolectar las tres familias de error de una sola ejecución, sin abortar.

Robustez de un servicio de larga duración

Un defer recover() alrededor de todo el pipeline

// si el parseo fallo, el arbol tiene huecos: que el traductor entre
// en panic es la consecuencia esperable, no un bug que valga mostrar
entradaRota := errores.HayDeEntrada()
func() {
    defer func() {
        if r := recover(); r != nil && !entradaRota {
            errores.Semantico(fmt.Sprintf("error interno durante la ejecucion: %v", r), 0, 0)
        }
    }()
    programa := traductor.Traducir(arbolParse)
    grafo = ast.ConstruirGrafo(programa)
    interprete.Interpretar(programa)
}()

Por qué importa en un servidor: un panic interno no contemplado (por ejemplo, un tipo de nodo del AST sin manejar en algún switch) no debe derribar el proceso completo del servidor — que sigue atendiendo otras peticiones. En vez de eso, se reporta como un error semántico adicional al usuario que envió ese código puntual.

El matiz de entradaRota — por qué el recover() a veces calla: el pipeline es best-effort: aunque el parseo falle, se sigue traduciendo y ejecutando para juntar todos los errores (§8.1). Pero si el parseo falló, el árbol viene con contextos nil y el panic del traductor es esperable — reportarlo como «error interno … línea 0» junto al error sintáctico real solo confunde, y hacía parecer roto al intérprete ante cualquier typo. Por eso se recuerda antes si la entrada ya venía rota y en ese caso el panic se traga. Al revés no: si el código parseó limpio y aun así hubo panic, eso sí es un bug propio y se reporta — esconderlo sería peor que el ruido. Hallazgo B3 de la auditoría, con pruebas de regresión en analizar_test.go.

Pero recover() no lo atrapa todo: solo captura panics, no los fatal error de Go. El caso crítico es el stack overflow por una recursión sin caso base (func f() int { return f() }): Go lo termina de forma no recuperable y mataría el proceso entero a pesar de este recover(). Por eso la robustez no descansa solo aquí: el intérprete lleva guardas de profundidad de recursión (2000) en invocarFuncion y de iteraciones por ciclo (1 000 000) en ejecutarFor, que reportan un error semántico —"recursión demasiado profunda" / "posible ciclo infinito"— antes de que el problema llegue a ser fatal.

Requisito de entrega (restricción 10.2 del enunciado)

El servidor debe correr nativo en Linux

El desarrollo se hizo en Windows, pero el enunciado exige ejecución nativa en un sistema Linux. Go cross-compila sin herramientas adicionales:

cd server
GOOS=linux GOARCH=amd64 go build -o vlangcherry-servidor ./cmd/servidor

El binario resultante vlangcherry-servidor se transfiere al equipo Linux de destino y corre directamente (./vlangcherry-servidor), sin instalar Go ni ninguna dependencia adicional ahí — Go produce binarios estáticos por defecto.

Chequeo rápido

Sobre el servidor REST

1 · ¿Qué framework HTTP usa el servidor de VLangCherry?

Ninguno — se implementa solo con net/http, la librería estándar de Go. Fue una decisión deliberada de no incorporar un framework externo.

2 · Si dos peticiones concurrentes ejecutan código VLangCherry distinto, ¿pueden mezclarse sus reportes de errores?

No — cada llamada a Analizar(codigo) crea su propia instancia de Interprete con su propia ListaErrores, consola y tabla de símbolos. No hay estado compartido entre peticiones.

3 · ¿Qué pasa si un código VLangCherry dispara un caso interno de Go no contemplado (por ejemplo, un panic por índice fuera de rango en el propio intérprete)?

El defer recover() de analizar.go lo atrapa y lo reporta como un error semántico adicional (línea/columna 0) en el JSON de respuesta — el proceso del servidor sigue en pie para atender otras peticiones.

Etapa 6 · construida

Queda construido el servidor REST

Un único endpoint (POST /interpretar), entorno fresco por petición, listener de errores de ANTLR unificado con los errores semánticos, recuperación ante pánico interno, y compilación cruzada lista para el requisito de Linux.
