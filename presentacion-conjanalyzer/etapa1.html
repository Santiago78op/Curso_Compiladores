Etapa 1 · Parte 1

La tabla de tokens de ConjAnalyzer

El vocabulario de este lenguaje es deliberadamente pequeño: 3 palabras reservadas, 4 operadores de conjunto, 9 símbolos estructurales y 3 patrones. Esa economía es lo que permite anidar operaciones sin límite sin que la gramática se complique.

Método: recorrer la sección 4 del enunciado buscando, en cada renglón, "¿qué pieza nueva del vocabulario aparece acá?"

Grupo 1 de 3

Palabras reservadas y operadores de conjunto

Las tres palabras reservadas van siempre en mayúsculas — es lo primero que exige la sensibilidad a mayúsculas de la sección 4.1: conj o Conj no disparan la regla.

TokenLexemaSección
CONJCONJ4.5 — definición de conjuntos
OPERAOPERA4.6 — definición de operaciones
EVALUAREVALUAR4.7 — evaluar pertenencia

Los operadores de conjunto también quedan como tokens reservados — no ID comunes — porque son parte fija de la notación prefija (4.6):

TokenLexemaSignificado
UNIONUunión (6.1)
INTERSECCION&intersección (6.2)
DIFERENCIA-diferencia (6.3)
COMPLEMENTO^complemento, único operador unario (6.4)

Consecuencia de reservar U: ningún conjunto ni operación puede llamarse literalmente U — el lexer lo reconoce como UNION antes de que la regla de {Id} tenga oportunidad. Restricción documentada en docs/gramatica.txt, no una validación aparte.

Grupo 2 de 3

Símbolos estructurales

TokenLexemaDónde aparece
FLECHA->CONJ : nombre -> notación;
VIRGULILLA~rango: a~z
LLAVE_IZQ / LLAVE_DER{ }encapsulamiento del programa (4.2) y referencia a un conjunto {A}
PAR_IZQ / PAR_DER( )EVALUAR( ... )
DOS_PUNTOS:CONJ :, OPERA :
PUNTO_COMA;fin de cada sentencia
COMA,listas de elementos

Regla del match más largo, otra vez: -> (FLECHA) y - (DIFERENCIA) comparten el primer carácter. JFlex prefiere el lexema más largo posible: "->" le gana a "-" sin importar el orden en que estén declaradas, porque son de distinta longitud. Basta con que la regla de "->" exista. El orden de declaración solo desempata cuando dos reglas calzan la misma longitud (por ejemplo, una reservada frente a {Id}).

Grupo 3 de 3

Tokens con patrón — y un comodín poco común

TokenPatrónLexemas de ejemplo
IDletra, seguida de letras o dígitosconjuntoA, operacion1
NUMEROuno o más dígitos0, 5, 123
SIMBOLOcomodín: cualquier ASCII imprimible (33–126) que ninguna regla anterior capturó!, @, $, %, <, >

SIMBOLO es la pieza que hace posible CONJ : signos -> !,?,@,$,%; (verificado en ejemplo4_nosimplificable.ca): cualquier signo de puntuación del universo que no sea uno de los operadores/símbolos reservados puede ser elemento de un conjunto.

Se descarta (nunca llega al parser):

Se descartaPatrón
Comentario de línea# hasta el salto de línea (4.3.1)
Comentario multilíneade <! a !> (4.3.2)
Espacios, tabs, saltos de líneaseparan tokens, no significan nada

La otra cara del universo (Etapa 0)

Todo lo que cae FUERA del universo es error léxico

El comodín SIMBOLO cubre el universo entero (ASCII 33–126). Lo que no calza en ninguna regla anterior ni en ese rango cae en la última regla del .flex, [^] (cualquier carácter): se reporta como error léxico y el análisis continúa.

# ERROR LEXICO: la ñ (fuera del universo ASCII 33..126) se descarta
CONJ : conjuñ -> a~c;

Verificado en ejemplo2_errores.ca: la ñ se reporta y se descarta, y el nombre del conjunto queda truncado a conju — que sí se termina definiendo correctamente. El error no aborta nada.

Chequeo rápido · Parte 1

Contá tokens

1 · ¿Cuántos tokens produce CONJ : a -> 1~3;?

8: CONJ · : · a (ID) · -> · 1 (NUMERO) · ~ · 3 (NUMERO) · ; (PUNTO_COMA). El punto y coma sí es un token; los espacios no cuentan.

2 · ¿Qué token produce el carácter @ suelto en el código fuente?

SIMBOLO: @ está dentro del universo ASCII (33–126) pero no calza con ninguna regla de reservada/operador/símbolo estructural, así que cae en el comodín — queda disponible como elemento de un conjunto.

3 · ¿Por qué "->" tiene que declararse antes que "-" en el .flex?

Porque si el analizador viera -> y solo tuviera la regla de - escrita, cortaría el match ahí mismo y dejaría el > suelto para la siguiente pasada. JFlex prefiere el lexema más largo posible entre las reglas disponibles: declarar "->" es lo que le da esa opción para elegir.

Etapa 1 · Parte 2

El Lexer.flex real, en 3 secciones

// SECCION 2 — sin %ignorecase: el lenguaje es CASE SENSITIVE (4.1)
%class Lexer
%public
%unicode
%cup
%line
%column

Id           = {Letra}({Letra}|{Digito})*
Numero       = {Digito}+
ComentLinea  = "#"[^\r\n]*
ComentMulti  = "<!"~"!>"
// SECCION 3 — orden: descartes, reservadas, operadores, simbolos, patrones, comodin
{ComentLinea}   { /* ignorar */ }
"CONJ"          { return symbol(sym.CONJ); }
"U"             { return symbol(sym.UNION); }
"->"            { return symbol(sym.FLECHA); }
"-"             { return symbol(sym.DIFERENCIA); }
{Id}            { return symbol(sym.ID); }
{Numero}        { return symbol(sym.NUMERO); }
[\x21-\x7E]     { return symbol(sym.SIMBOLO); }   // comodin del universo
[^]             { /* error lexico: fuera del universo */ }

El campo público Entorno entorno, que Interprete.ejecutar(...) conecta después de crear el lexer, es lo que permite registrar cada token para el reporte (5.2) y mandar los errores léxicos al Entorno en vez de a stderr — mismo patrón que DataForge.

Puesta en marcha · IntelliJ IDEA

Generar el lexer y probarlo

1 · Abrir el proyecto

Open → carpeta ConjAnalyzer (la que tiene el pom.xml) → Trust Project. IDEA importa el proyecto Maven automáticamente.

2 · Generar con Maven

Ventana Maven → conjanalyzer → Lifecycle → doble clic en compile. Corre el plugin de JFlex: aparece target/generated-sources/jflex/…/Lexer.java.

3 · Probar por consola

▶ Run sobre TestInterprete (por defecto corre un ejemplo de entradas/). El reporte de tokens también sale como reportes/tokens.html tras cada ejecución.

Ciclo de trabajo: editar Lexer.flex → compile en Maven (regenera Lexer.java) → volver a correr. Igual que en DataForge, jamás se edita el Lexer.java generado.
