Un truco que evita mantenimiento manual

El nombre de cada token, por reflexión sobre sym

// nombresTokens() recorre los campos de la clase sym generada por CUP
Map<Integer, String> nombresTokens() {
    Map<Integer, String> m = new HashMap<>();
    for (Field f : sym.class.getFields()) {
        m.put((Integer) f.get(null), f.getName());   // numero → "UNION", "CONJ", ...
    }
    return m;
}

Sin esto, el reporte necesitaría un switch manual con los ~19 tokens del lenguaje — que se desincronizaría cada vez que alguien agregue o quite un terminal en el .cup. Con reflexión, el reporte siempre está al día automáticamente: mismo truco que usa DataForge.

Todos los lexemas y descripciones se escapan (esc(String s)) antes de insertarse en la tabla HTML: lexemas legítimos del lenguaje como & o -> romperían el HTML si no se escaparan. Verificado en tokens.html real: el lexema -> aparece como -&gt;.

Sección 5.4 del enunciado — el formato exacto

El JSON de simplificación, con Gson

public static String construir(Entorno ent)
public static File generar(Entorno ent, File carpeta) throws Exception
{
  "operacion1": {
    "leyes": ["ley de doble complemento", "leyes de DeMorgan"],
    "conjunto simplificado": "U & {A} {B} {C}"
  },
  "operacion2": "No se puede simplificar la operacion"
}

Por cada operación con seSimplifico == true, un objeto con "leyes" (arreglo) y "conjunto simplificado" (la expresión prefija ya simplificada, vía toPrefijo() de la Etapa 3). Para las que no simplificaron, el valor es directamente el string literal "No se puede simplificar la operacion" — no un objeto vacío.

new GsonBuilder().setPrettyPrinting().disableHtmlEscaping().create()

disableHtmlEscaping() es necesario porque, sin esa opción, Gson escapa por defecto caracteres como & — y la notación prefija de este lenguaje los usa constantemente (U & {A} {B} {C}). Sin desactivarlo, el JSON de salida no coincidiría byte a byte con lo que pide el enunciado.

Un requisito que atraviesa todo el proyecto

Reportes solo del último análisis

La sección 5 del enunciado es explícita: "no deberá mostrarse reportes de análisis anteriores". Interprete.ejecutar(codigo) crea un Entorno completamente nuevo en cada llamada — nunca reutiliza ni acumula estado de una ejecución a la siguiente.

public static Entorno ejecutar(String codigo) {
    Lexer lexer = new Lexer(new StringReader(codigo));
    Parser parser = new Parser(lexer);
    lexer.entorno = parser.entorno;    // conectar lexer ↔ entorno del parser
    try { parser.parse(); } catch (Exception e) { /* no abortar la GUI */ }
    return parser.entorno;
}

EditorApp guarda ese Entorno devuelto en ultimoEntorno, y tanto Reportes como DiagramaVenn (Etapa 5) siempre leen de ahí — nunca de una ejecución vieja.

Chequeo rápido

¿Se entienden los reportes y el JSON?

1 · ¿Qué pasaría con el reporte de tokens si mañana se agrega un nuevo terminal al .cup, por ejemplo XOR?

Nada que arreglar en Reportes.java. Como el nombre del token se obtiene por reflexión sobre los campos de la clase sym (generada automáticamente por CUP), el nuevo token XOR aparecería con su nombre correcto sin tocar el reporte.

2 · En el JSON, ¿por qué las operaciones que no simplifican no tienen un objeto {"leyes": [], ...} vacío?

Porque el formato del enunciado (5.4) pide específicamente el string literal "No se puede simplificar la operacion" como valor directo de la clave — no un objeto con arreglo vacío. JsonSalida respeta ese formato exacto revisando seSimplifico.

3 · ¿Qué garantiza que dos ejecuciones seguidas del mismo editor nunca mezclen sus reportes?

Que Interprete.ejecutar(...) crea un Entorno nuevo en cada llamada (nunca reutiliza el anterior), y que Reportes/JsonSalida/DiagramaVenn siempre reciben ese Entorno fresco como parámetro — nunca leen un estado global acumulado.
