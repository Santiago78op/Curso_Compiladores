Etapa 3 · Parte 1

Ejecución: por qué esta vez sí hace falta un árbol

DataForge no necesitó AST: cada instrucción corre exactamente una vez, en la propia acción del .cup. ConjAnalyzer rompe esa comodidad — y la razón exacta es el tema de esta etapa.

Paquete conjanalyzer.interprete: Entorno, Conjunto, NodoOperacion, Operacion.

La pregunta que decide la arquitectura

¿Cuántas veces se necesita recorrer una operación?

Definir un conjunto (CONJ) es una acción de una sola vez: se calcula el Set<Character> y se guarda. Pero una operación (OPERA) tiene que servir para tres cosas distintas, después de que el parser terminó de leerla:

1

Evaluarse

Calcular el Set<Character> resultante contra los conjuntos base y el universo.

2

Simplificarse

El Simplificador (Etapa 4) necesita reescribir su estructura aplicando leyes algebraicas — no puede hacerlo sobre un resultado ya aplanado a un Set.

3

Servir al diagrama de Venn

La Etapa 5 necesita evaluar la operación como función booleana punto por punto — otra pasada distinta, sobre la misma estructura.

Ahí está la diferencia con DataForge: si algo se recorre una sola vez, ejecutarlo directo en la acción del .cup alcanza y sobra. Si algo se recorre más de una vez, de formas distintas, hace falta materializarlo como estructura de datos — un árbol — para no repetir el parseo.

La única estructura de tipo árbol del proyecto

NodoOperacion: hoja, unario o binario

public static NodoOperacion hoja(String nombre)             // {A}
public static NodoOperacion unario(char op, NodoOperacion hijo)   // ^X
public static NodoOperacion binario(char op, NodoOperacion a, NodoOperacion b)  // X op Y

Tres formas posibles, exactamente las tres alternativas no-hoja/hoja de la gramática de la Etapa 2. El campo op vale '\0' en una hoja, '^' en el único operador unario, o uno de 'U' '&' '-' en un binario.

Acotado, no un AST del programa completo: las sentencias CONJ y EVALUAR se siguen ejecutando directo en las acciones del .cup, sin árbol propio — igual que en DataForge. Solo OPERA necesita esta estructura, porque es la única construcción del lenguaje que se reescribe y se recorre repetidamente.

Recorrido nº 1: evaluación

Postorden: primero los hijos, luego el nodo

public Set<Character> evaluar(Map<String, Set<Character>> conjuntos, Set<Character> universo) {
    if (esHoja()) { ... }                       // busca el conjunto por nombre
    Set<Character> a = izq.evaluar(conjuntos, universo);
    if (esUnario()) {                           // complemento: universo menos A
        Set<Character> r = new LinkedHashSet<>(universo);
        r.removeAll(a);
        return r;
    }
    Set<Character> b = der.evaluar(conjuntos, universo);
    switch (op) {
        case 'U' -> r.addAll(b);        // union (6.1)
        case '&' -> r.retainAll(b);    // interseccion (6.2)
        case '-' -> r.removeAll(b);     // diferencia (6.3)
    }
    return r;
}

Se recorre en postorden (primero se resuelven los hijos, después el nodo actual) porque el resultado de un operador depende de los resultados YA calculados de sus operandos — no se puede calcular una unión sin conocer antes ambos conjuntos que se unen.

El mismo árbol, otra forma de recorrerlo

pertenenciaRegion: la operación como función booleana

public boolean pertenenciaRegion(Map<String, Boolean> region) {
    if (esHoja()) return region.getOrDefault(nombreConj, false);
    if (esUnario()) return !izq.pertenenciaRegion(region);
    boolean a = izq.pertenenciaRegion(region), b = der.pertenenciaRegion(region);
    return switch (op) {
        case 'U' -> a || b;
        case '&' -> a && b;
        case '-' -> a && !b;
        default  -> false;
    };
}

En vez de recibir conjuntos completos, recibe un mapa de booleanos: "¿un elemento hipotético pertenece a cada conjunto base?". Es exacto porque unión/intersección/diferencia/complemento operan punto a punto sobre las funciones indicadoras (∪ es ||, ∩ es &&). Esta es la función que la Etapa 5 llama por cada píxel del diagrama de Venn — sin tener que recorrer el universo entero.

Las utilidades que cierran el círculo

toPrefijo(), copia() y el Entorno

MétodoPara qué sirve
toPrefijo()Serializa el árbol de vuelta a texto ("U & {A} {B} {C}") — lo usan el reporte y el JSON de simplificación (Etapa 6).
copia()Copia profunda; el Simplificador (Etapa 4) trabaja sobre una copia para no mutar el árbol original de la operación.
referencias(Set<String>)Junta los nombres de los conjuntos base que la operación menciona — el diagrama de Venn los usa para saber cuántos círculos dibujar.

Todo ese estado — conjuntos, operaciones ya evaluadas y simplificadas, consola, errores, tokens — vive en Entorno, exactamente una instancia nueva por ejecución (mismo criterio que DataForge): así los reportes de la sección 5 nunca mezclan datos de una corrida anterior.

Caso de estudio · leer el enunciado con sentido crítico

Cuando el propio enunciado se equivoca (4.8)

El ejemplo de la sección 4.8 define conjuntoA -> 1,2,3,a,b y conjuntoB -> a~z, con operacion1 = conjuntoA & conjuntoB. Para EVALUAR({1, b}, operacion1), el PDF muestra:

1 -> exitoso
b -> exitoso

Pero la intersección real es {a, b}: conjuntoA tiene el carácter 1, pero conjuntoB (rango a~z) no lo tiene — 1 NO pertenece a la intersección. La salida correcta, y la que produce ConjAnalyzer, es:

1 -> fallo
b -> exitoso

El código respeta la semántica real (pertenencia efectiva al conjunto resultante evaluado) y documenta la inconsistencia explícitamente en Entorno.evaluar — no es un bug del proyecto, es un error del propio enunciado, defendible en la revisión oral con la evidencia matemática en mano.

Chequeo rápido

¿Quedó clara la necesidad del árbol?

1 · Si ConjAnalyzer no tuviera que simplificar ni dibujar el Venn — solo evaluar y mostrar el resultado —, ¿seguiría haciendo falta NodoOperacion?

No necesariamente. Con un solo recorrido (evaluar y listo), se podría ejecutar directo en las acciones del .cup, exactamente como hace DataForge con sus expresiones. El árbol se vuelve necesario justo cuando aparece un SEGUNDO uso de la misma estructura (simplificar) que no puede reconstruirse a partir del resultado ya evaluado.

2 · ¿Por qué evaluar() recorre en postorden y no al revés (nodo primero, hijos después)?

Porque el resultado de un nodo depende del resultado de sus hijos: no se puede calcular A ∪ B sin tener antes los conjuntos evaluados de A y de B. Postorden = "resolvé lo de abajo antes de combinar arriba".

3 · La salida del enunciado (4.8) dice "1 -> exitoso". ¿Por qué el código no la reproduce tal cual?

Porque esa salida es matemáticamente incorrecta dado cómo el propio enunciado definió los conjuntos: 1 no pertenece a la intersección real. Copiarla ciegamente habría introducido un bug real solo para "coincidir con el PDF" — se prioriza la semántica correcta y se documenta la discrepancia.

Etapa 3 · construida

Queda construido el motor de ejecución

Entorno, Conjunto y un mini-AST (NodoOperacion) acotado a lo único que de verdad lo necesita: las operaciones. El "por qué" de ese árbol es la clave arquitectónica de todo el proyecto.
