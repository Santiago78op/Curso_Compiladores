Cómo funciona Maven

No es «el botón que compila». Es un modelo de proyecto: una forma estándar de decir qué es tu software, de qué depende y cómo se construye — de modo que cualquier máquina llegue al mismo resultado.

Todos los ejemplos salen del pom.xml real de DataForge.
Se navega con ← → o con los botones.

Antes de la herramienta, el problema

«En mi máquina sí funciona»

Un proyecto Java sin gestor de build se construye a mano, y eso trae cuatro problemas que se agravan con el tiempo:

Las librerías

Los .jar se bajan a ojo y se guardan en una carpeta lib/. Nadie sabe qué versión es cada uno ni de dónde salió.

El classpath

Cada comando de compilación arrastra una lista de rutas cada vez más larga, distinta en cada computadora.

El orden

Si hay que generar código antes de compilar (nuestro caso: JFlex y CUP), el orden vive en la cabeza de quien lo escribió.

Lo transitivo

Una librería necesita otra, que necesita otra. Resolverlo a mano es un trabajo sin fin.

Maven ataca las cuatro con una idea sola: describir el proyecto en un archivo declarativo y dejar que la herramienta deduzca los pasos. Vos decís qué es el proyecto; Maven decide cómo construirlo.

La pieza fundacional

Coordenadas: la dirección universal de un artefacto

Todo en Maven —tu proyecto, cada dependencia, cada plugin— se identifica con la misma terna, que se abrevia GAV:

groupIdcom.olc1Quién lo publica. Por convención, un dominio al revés — evita choques de nombres entre organizaciones.
artifactIddataforgeCómo se llama el artefacto dentro de ese grupo.
version1.0.0Qué versión. Un -SNAPSHOT al final marca «en desarrollo, puede cambiar».

Con esa terna, cualquier máquina del mundo puede localizar exactamente el mismo binario. Es lo que hace posible escribir una dependencia en tres líneas y olvidarse:

<dependency>
    <groupId>com.github.vbmacher</groupId>
    <artifactId>java-cup-runtime</artifactId>
    <version>11b-20160615</version>
</dependency>

Fuente: DataForge/pom.xml. Ese runtime es el que aporta la clase Symbol que devuelve el lexer.

El corazón: pom.xml

Project Object Model

El POM describe el proyecto. Tiene cuatro zonas, y conviene leerlas como respuestas a cuatro preguntas distintas:

ZonaRespondeEn DataForge
groupId · artifactId · version · packaging¿Qué es este proyecto?com.olc1:dataforge:1.0.0, empaquetado como jar
<properties>¿Bajo qué parámetros se construye?Java 17 y codificación UTF-8 — clave para que las tildes de los mensajes no se rompan
<dependencies>¿De qué depende?El runtime de CUP y JavaFX
<build><plugins>¿Qué pasos extra hay que dar?Generar el lexer y el parser, correr la GUI, correr por consola

Es declarativo, no imperativo: en ningún lado dice «primero corré JFlex, después compilá». Dice «este plugin participa del build» y Maven deduce cuándo, a partir de la fase a la que el plugin se engancha. Eso es lo que veremos en la diapositiva del ciclo de vida.

La decisión de diseño que ahorra más trabajo

Convención sobre configuración

Maven no pregunta dónde están tus fuentes: asume una estructura estándar. Si la respetás, no configurás nada.

DataForge/
├── pom.xml                     ← la descripción del proyecto
├── src/
│   ├── main/
│   │   ├── java/               ← código fuente (se compila)
│   │   ├── resources/          ← recursos (se copian al JAR)
│   │   ├── jflex/              ← convención del jflex-maven-plugin
│   │   └── cup/                ← convención del cup-maven-plugin
│   └── test/
│       └── java/               ← pruebas (se compilan y corren aparte)
└── target/                     ← TODO lo generado. Desechable.
    ├── generated-sources/      ← Lexer.java, Parser.java, sym.java
    └── classes/                ← los .class

La regla de oro de target/: todo lo que hay ahí es derivado y se puede borrar sin perder nada — por eso no se versiona. Si alguna vez editás un archivo dentro de target/generated-sources/, tu cambio desaparece en el siguiente mvn compile. Las fuentes de verdad son el .flex y el .cup.

El concepto que más se malentiende

El ciclo de vida es una secuencia de fases

Maven define tres ciclos de vida independientes: default (construir), clean (borrar lo generado) y site (documentación). El importante es default, una lista ordenada de fases:

validate→ generate-sources→ process-sources→ compile→ test-compile→ test→ package→ verify→ install→ deploy

(La lista completa tiene más fases intermedias; estas son las que se usan a diario.)

La regla que lo explica todo: pedir una fase ejecuta esa fase y todas las anteriores. Por eso mvn compile no solo compila: antes pasa por generate-sources, y ahí es donde corren JFlex y CUP. Y por eso mvn package compila y prueba antes de armar el JAR.

clean es de otro ciclo, y por eso se escribe junto: mvn clean compile significa «corré el ciclo clean, después el default hasta compile».

Tres palabras que se confunden

Fase, plugin y goal

ConceptoQué esEjemplo
FaseUn momento del build. Por sí sola no hace nada: es una etiqueta en la línea de tiempo.generate-sources
PluginUn artefacto que aporta capacidades. Se identifica con coordenadas, como cualquier dependencia.de.jflex:jflex-maven-plugin:1.9.1
GoalUna acción concreta que ofrece un plugin. Es lo que realmente se ejecuta.jflex:generate

El build ocurre cuando un goal se engancha a una fase. Eso es exactamente lo que declara este bloque del POM de DataForge:

<plugin>
    <groupId>de.jflex</groupId>
    <artifactId>jflex-maven-plugin</artifactId>
    <version>1.9.1</version>
    <executions>
        <execution>
            <goals><goal>generate</goal></goals>
        </execution>
    </executions>
</plugin>

No dice a qué fase engancharse. No hace falta: cada goal declara su fase por defecto, y la de jflex:generate es generate-sources. Por eso «solo funciona». Si hiciera falta cambiarla, se agrega <phase> dentro del <execution>.

Por qué esto importa en OLC1

El build de un compilador es el caso difícil

Un proyecto Java normal no genera código: compila lo que el programador escribió. Los nuestros fabrican dos clases antes de compilar, y si el orden falla, nada funciona.

FaseQué pasaResultado
generate-sourcescup:generate lee src/main/cup/parser.cupParser.java y sym.java
generate-sourcesjflex:generate lee src/main/jflex/Lexer.flexLexer.java
compileEl compilador de Java toma tu código + lo generadoLos .class en target/classes

El error clásico y su diagnóstico: «no encuentra la clase Parser» casi nunca es un problema de import. Significa que generate-sources no produjo nada — normalmente porque el .cup tiene un error de sintaxis, o porque el archivo no está en la carpeta que el plugin espera. La pista está más arriba en la salida de Maven, no en la línea del import.

Los tres proyectos Java del curso comparten este esquema; el pom.xml de DataForge es la referencia que funciona.

Dependencias

Transitividad y scope

Maven resuelve las dependencias en cadena: si pedís A y A necesita B, B llega solo. Lo que hay que decidir es hasta dónde alcanza cada dependencia, y eso lo dice el <scope>:

ScopeDisponible en¿Va en el paquete?Caso típico
compile (por defecto)TodoSíEl runtime de CUP: se usa al compilar y al ejecutar
providedCompilar y probarNoAlgo que el entorno ya aporta (un servidor de aplicaciones)
runtimeEjecutar y probarSíUn driver JDBC: no se programa contra él, pero hace falta al correr
testSolo pruebasNoJUnit

Cuando dos caminos traen versiones distintas de la misma librería, Maven aplica «el más cercano gana»: la declaración a menor profundidad en el árbol de dependencias. Si eso no alcanza, se fija la versión a mano con <dependencyManagement> — que es justamente lo que hace el POM que genera el arquetipo quickstart con el BOM de JUnit, como veremos en la parte 2.

De dónde salen los .jar

Tres repositorios, en este orden

1

Local

~/.m2/repository. La caché de tu máquina. Maven mira acá primero, y si está, no toca la red.

2

Central

El repositorio público de Maven. Es de donde bajó, en este mismo curso, el cup-maven-plugin y todo lo demás.

3

Remotos propios

Los que declare el POM o el settings.xml: el repositorio interno de una empresa, por ejemplo.

Eso explica dos comportamientos que suelen desconcertar:

  • La primera compilación de un proyecto tarda muchísimo y las siguientes son rápidas: la primera llenó la caché local.
  • mvn install no «instala el programa» en ningún lado: copia tu artefacto al repositorio local para que otros proyectos de tu misma máquina puedan declararlo como dependencia. Publicar de verdad es deploy.

Ese detalle es la clave de la parte 2: un arquetipo se usa desde el repositorio local, así que el paso previo a estrenar el tuyo siempre es mvn install.

La chuleta

Los comandos que se usan de verdad

ComandoQué haceCuándo
mvn compileRegenera lexer y parser, y compilaDespués de tocar el .flex o el .cup
mvn clean compileLo mismo, borrando target/ antesCuando algo «no toma» el cambio y sospechás de un residuo
mvn packageCompila, prueba y arma el JARPara entregar (ConjAnalyzer se califica sobre el JAR)
mvn javafx:runLevanta la GUICorrer la aplicación
mvn exec:javaCorre una clase con mainProbar el intérprete por consola
mvn installCopia el artefacto al repositorio localPublicar un arquetipo propio (parte 2)

Un matiz que vale para la defensa: javafx:run y exec:java no son fases, son goals invocados directamente con la sintaxis prefijo:goal. Por eso no arrastran las fases anteriores — y por eso a veces hay que escribir mvn compile exec:java: para asegurarse de que hay .class frescos que ejecutar.

Chequeo rápido

¿Quedó claro? Probate

1 · Corrés mvn package. ¿Se ejecuta JFlex?

Sí. Pedir una fase ejecuta esa y todas las anteriores. package viene después de generate-sources, así que JFlex y CUP corren, después compila, después prueba, y recién ahí arma el JAR.

2 · ¿Por qué target/ no se versiona, si contiene Parser.java, que es código fuente Java?

Porque es código derivado: sale de parser.cup en cada build. Versionarlo crearía dos verdades que pueden discrepar, y la única real es el .cup. La prueba: si clonás el repo sin target/ y corrés mvn compile, reaparece idéntico.

3 · Tu compañero agrega una dependencia al POM y a vos te falla la compilación diciendo que no encuentra la clase. Tenés internet. ¿Qué pasó?

Lo más probable es que hayas actualizado el código pero no recargado el POM: el IDE mantiene su propio modelo del proyecto. En IntelliJ es Reload All Maven Projects. Desde terminal no pasa, porque Maven lee el POM en cada corrida. El segundo sospechoso es un scope equivocado — por ejemplo test en algo que se usa en src/main.

4 · ¿Qué diferencia hay entre mvn compile y mvn compiler:compile?

El primero corre la fase compile, o sea todo el ciclo default hasta ahí — incluida la generación de código. El segundo invoca un goal suelto del maven-compiler-plugin, sin fases previas: intentaría compilar sin que existan Lexer.java ni Parser.java, y fallaría.

Resumen en una pantalla

Declarás qué, Maven deduce cuándo

Coordenadas GAV para nombrar todo · el POM para describir el proyecto · una estructura de carpetas que evita configurar · un ciclo de vida de fases donde pedir una corre todas las anteriores · plugins cuyos goals se enganchan a esas fases. Con eso, generar un lexer antes de compilar deja de ser un ritual y pasa a ser una línea de XML.
