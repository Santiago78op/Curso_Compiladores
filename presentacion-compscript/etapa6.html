Etapa 6 · Parte 1

Funciones: el árbol se recorre desde cualquier punto

Si el flujo de control (Etapa 5) demostraba que el árbol se puede recorrer N veces, las funciones demuestran algo más fuerte: se puede recorrer el mismo árbol desde adentro del propio recorrido — eso es la recursión.

Fuente: ast/A.java (método privado invocar) + interprete/Interprete.java.

La recomendación del enunciado (§5.23), aplicada

Ejecutar en tres pasadas resuelve las referencias hacia adelante

// Interprete.ejecutar(String codigo)
// 1a pasada: registro de funciones/metodos/structs (permite forward-reference)
for (A.Instruccion i : raiz) {
    if (i instanceof A.DeclaracionFuncion f) ctx.registrarFuncion(f);
    else if (i instanceof A.DeclaracionStruct s) ctx.registrarStruct(s);
}
// 2a pasada: declaraciones y asignaciones globales
// 3a pasada: RUN_MAIN (punto de entrada)

Gracias a la primera pasada, ejemplo2.cs puede llamar a clasificar(...) desde main() aunque clasificar esté declarada ANTES que main en el archivo — el registro de funciones ya ocurrió, en una pasada previa a cualquier ejecución real.

Una decisión de diseño explícita del enunciado (§5.23)

Los argumentos se asocian por identificador, no por posición

<llamada>    ::= ID "(" <lista-argumentos> ")"
<argumento>  ::= ID "=" <expresion>      // SIEMPRE nombre = valor
// entradas/ejemplo5.cs
int potencia(base: int, exp: int = 2) { return base ^ exp; }
...
console.log(potencia(base = 4));               // 16 (usa exp por defecto = 2)
console.log(potencia(base = 2, exp = 5));      // 32

Esto significa que el orden de los argumentos en la llamada NO importa — potencia(exp = 5, base = 2) sería idéntico. A.invocar(...) valida además que no haya argumentos repetidos ni desconocidos antes de resolver ningún valor por defecto.

La lógica real, paso a paso

Cómo se resuelve cada parámetro

for (Parametro p : f.params) {
    Argumento a = mapaArgs.get(p.id.toLowerCase());
    Valor v;
    if (a != null) v = a.expr.evaluar(caller);          // 1: vino en la llamada
    else if (p.defecto != null) v = p.defecto.evaluar(caller); // 2: valor por defecto declarado
    else { caller.errorSemantico("falta el argumento '" + p.id + "'...", l, c); return null; } // 3: error
    // ... comprobacion de tipo contra p.tipo, luego:
    local.declarar(new Simbolo(p.id, ..., v, ...), l, c);
}

Nótese algo sutil: a.expr.evaluar(caller) evalúa la EXPRESIÓN del argumento en el entorno del llamador (caller) — porque ahí es donde viven las variables que el llamador está pasando — pero local.declarar(...) las registra en el entorno NUEVO de la función. Los dos entornos coexisten solo durante esta resolución.

Verificación real — ejemplo5.cs

Recursión: cada llamada, su propio Entorno

int factorial(n: int) {
    if (n <= 1) { return 1; }
    return n * factorial(n = n - 1);
}
console.log(factorial(n = 5));    // 120

Cada llamada recursiva a factorial ejecuta A.invocar("factorial", ...), que crea un Entorno NUEVO colgado del global (Etapa 4) con su propio valor de n. Cinco llamadas anidadas significan cinco copias distintas de n vivas simultáneamente en la pila de Java — cada una en su propio Entorno, sin pisarse.

El mismo mecanismo de la Etapa 5, reutilizado

return: el valor viaja dentro de la excepción

// A.Return.ejecutar(...)
public void ejecutar(Entorno e) {
    Valor v = (expr == null) ? null : expr.evaluar(e);
    throw new Senales.Retorno(v, linea, columna);   // el valor viaja adentro de la excepcion
}

// A.invocar(...) la atrapa:
Valor retorno = null;
try { A.ejecutar(f.cuerpo, local); }
catch (Senales.Retorno r) { retorno = r.valor; }

Un return puede estar anidado dentro de un if, dentro de un for, dentro de un match... el mecanismo de excepción atraviesa todos esos niveles de anidamiento sin que ninguno de ellos tenga que "reenviar" manualmente el valor de retorno hacia arriba.

Comprobación de tipos completa alrededor de la llamada

Argumentos Y retorno, ambos validados

A.invocar(...) comprueba la compatibilidad de tipos en dos puntos: cada argumento contra el tipo declarado del parámetro correspondiente, y el valor de return contra f.tipoRetorno. Una función declarada void que intenta retornar un valor es un error semántico:

if (f.tipoRetorno.cat == Tipo.Cat.VOID) {
    if (retorno != null && retorno.tipo.cat != Tipo.Cat.VOID)
        caller.errorSemantico("el metodo '" + id + "' es void y no puede retornar un valor", l, c);
    return Valor.VOID;
}

Sin sobrecarga: el enunciado exige que un mismo identificador no pueda nombrar más de una función/método/struct — error semántico si se repite.

Chequeo rápido

Sobre funciones y recursión reales

1 · ¿Por qué la primera pasada de Interprete.ejecutar(...) es necesaria antes de ejecutar cualquier instrucción global?

Para permitir referencias hacia adelante: una función puede llamar a otra que aparece más abajo en el archivo. Si el registro de funciones ocurriera durante la misma pasada que la ejecución, llamar a una función "todavía no vista" fallaría.

2 · En potencia(base = 4), ¿de dónde sale el valor de exp?

Del valor por defecto declarado en el parámetro (exp: int = 2), evaluado en A.invocar(...) cuando no aparece ningún argumento exp = ... en la llamada. El resultado es 4^2 = 16.

3 · ¿Qué evidencia concreta (de un reporte real) demuestra que cada llamada recursiva tiene su propio Entorno?

El reporte de símbolos (6.4) de ejemplo5.cs muestra 186 entradas del parámetro n en distintos ámbitos de fib — una por cada activación recursiva, no una sola entrada final (ver Etapa 4).

Etapa 6 · construida

Queda construida la ejecución de funciones y la recursión

Tres pasadas para permitir referencias hacia adelante, argumentos asociados por nombre con valores por defecto, retorno viajando dentro de una excepción, y un Entorno nuevo por cada activación — verificado con factorial y fibonacci reales.
