Etapa 3 · la pieza central del proyecto

ast/A.java: el árbol hecho código

Una sola clase contenedora A, dos interfaces, y unas 25 clases anidadas — cada una representando exactamente una construcción del lenguaje. Esta es la pieza que DataForge y ConjAnalyzer no necesitan.

Fuente: src/main/java/compscript/ast/A.java, verificado 2026-07-20.

El diseño en dos interfaces

Nodo, Instrucción y Expresión

public interface Nodo {
    String etiquetaAst();
    default List<Nodo> hijosAst() { return new ArrayList<>(); }
}
public interface Instruccion extends Nodo { void ejecutar(Entorno e); }
public interface Expresion  extends Nodo { Valor evaluar(Entorno e); }

Todo lo que produce un valor (una suma, un acceso a variable, una llamada) implementa Expresion; todo lo que hace algo (un if, un while, una declaración) implementa Instruccion. Cada nodo sabe ejecutarse o evaluarse a sí mismo — el patrón tree-walking interpreter, una variante del Visitor sin doble despacho.

Un tercer propósito, gratis: etiquetaAst() + hijosAst() alimentan el reporte de AST (Etapa 7) sin necesitar una clase visitante aparte — Reportes.astHtmlNodo() simplemente recorre hijosAst() de forma recursiva.

Un detalle no obvio del diseño

¿Por qué los constructores reciben Object?

public Binaria(String op, Object izq, Object der, int l, int c) {
    this.op = op;
    this.izq = (Expresion) izq;
    this.der = (Expresion) der;
    linea = l; columna = c;
}

Las acciones del .cup no pueden usar genéricos con seguridad — los no-terminales de CUP son tipos raw, igual que en DataForge y ConjAnalyzer. Recibir Object en el constructor y castear adentro mantiene cada acción del .cup en una sola línea limpia, sin repetir el cast ahí:

expr ::= expr:a MAS expr:b  {: RESULT = new A.Binaria("+", a, b, aleft, aright); :}

Un nodo evaluándose a sí mismo

Binaria.evaluar(), tal cual en el código

public Valor evaluar(Entorno e) {
    Valor a = izq.evaluar(e), b = der.evaluar(e);   // recursion: cada hijo se evalua solo
    switch (op) {
        case "+": case "-": case "*": case "/":
        case "^": case "$": case "%":
            return Operaciones.aritmetica(op, a, b, e, linea, columna);
        case "==": case "!=": case "<": case "<=": case ">": case ">=":
            return Operaciones.relacional(op, a, b, e, linea, columna);
        case "&&": case "||":
            return Operaciones.logica(op, a, b, e, linea, columna);
        default: return null;
    }
}

Nótese que izq y der son a su vez Expresion: podrían ser otro A.Binaria, un A.Literal, una A.Llamada… El árbol se recorre solo, por recursión — nadie tiene que escribir un recorrido manual nodo por nodo.

Auditoría de código, 2026-07-21 — un bug real corregido

Cuando el árbol no valida lo que asume

A.Declaracion.validarVector(...) recibe el resultado de evaluar la expresión inicializadora de un vector. Antes de la corrección, el código asumía sin comprobar que ese valor ya era un vector:

private Valor validarVector(Valor crudo, Tipo declarado, Entorno e) {
    // Guarda de tipo: init es un <expresion> general (no solo un literal de
    // vector), asi que puede evaluar a un Entero/Cadena/etc. Sin esta
    // comprobacion, crudo.lista() lanza ClassCastException sin control
    // (bug real: revienta el interprete completo en vez de reportar un
    // error semantico y terminar de forma ordenada, como exige 4.3).
    if (crudo == null || crudo.tipo.cat != Tipo.Cat.VECTOR)
        e.errorSemantico("el vector '" + id + "' espera un literal de vector y recibio "
                + Entorno.tipoDe(crudo), linea, columna);
    List<Valor> vals = crudo.lista();
    ...
}

Sin la guarda, un programa como let v: int[] = 5; (una expresión válida pero no-vectorial) provocaba un ClassCastException de Java no controlado, que tumbaba el intérprete entero — exactamente lo que el enunciado (§4.3) prohíbe. La corrección agrega la comprobación de tipo ANTES de castear, y reporta un error semántico ordenado en su lugar.

Por qué importa acá y no en DataForge: cada nodo del AST es responsable de validar sus propios supuestos sobre los valores que recibe — no hay una gramática externa que lo garantice. Con evaluación directa (DataForge) el chequeo de tipos ocurre en el mismo lugar donde se usa el valor; con AST, cada nodo repite esa responsabilidad en su propio evaluar()/ejecutar().

De la raíz al primer recorrido

Ejecutar el árbol: un for sobre la raíz

// el resultado del parse ya es una lista de instrucciones, en memoria:
ArrayList raiz = (ArrayList) parser.parse().value;

// y "ejecutar el programa" es simplemente recorrerla:
for (A.Instruccion i : raiz) i.ejecutar(entornoGlobal);

Cada instrucción de nivel superior delega en sus propios hijos. Un A.If llama a cond.evaluar(e) y después ejecuta su cuerpo o su rama else; un A.While vuelve a evaluar su condición en cada vuelta del bucle Java while(true). El árbol convirtió al programa en datos que se pueden recorrer cuantas veces haga falta — la Etapa 5 muestra exactamente cómo.

Chequeo rápido

Sobre el AST real

1 · ¿Qué interfaz implementa un nodo A.If: Instruccion o Expresion? ¿Y A.Binaria?

A.If implementa Instruccion (no produce un valor, solo decide qué ejecutar). A.Binaria implementa Expresion (produce un Valor al evaluarse, como el resultado de una suma).

2 · ¿Cuál habría sido el síntoma del bug de validarVector ANTES de la corrección, al ejecutar let v: int[] = 5;?

Un ClassCastException de Java sin capturar, que interrumpía TODO el intérprete de forma abrupta — no solo el programa .cs que se estaba ejecutando. Después de la corrección, el mismo caso produce un error semántico ordenado, reportado en la tabla de errores, sin tumbar el proceso.

3 · ¿Por qué etiquetaAst() y hijosAst() no necesitan una clase "visitante" aparte para generar el reporte de AST?

Porque cada nodo ya sabe describirse (etiquetaAst()) y enumerar a sus propios hijos (hijosAst()) — Reportes.astHtmlNodo() solo necesita recorrer esa estructura recursivamente, sin conocer las ~25 clases concretas de antemano.

Etapa 3 · construida

Queda construido el árbol de sintaxis abstracta

Dos interfaces, ~25 clases, cada una sabiendo ejecutarse o evaluarse a sí misma. El programa dejó de ser «algo que se ejecuta mientras se analiza» para convertirse en una estructura de datos que se puede recorrer las veces que haga falta.
