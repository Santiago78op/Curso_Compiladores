Etapa 2 · Parte 1

La gramática de CompScript: expresiones infijas de verdad

DataForge llamaba a sus operaciones como funciones (SUM(a,b)): sin ambigüedad. CompScript, en cambio, usa notación infija (a + b * c) como cualquier lenguaje de propósito general — y eso significa que su BNF de <expresion> es ambigua por diseño.

Fuente: docs/gramatica.txt (BNF entregable, no copia del .cup) + src/main/cup/parser.cup real.

El problema clásico de las expresiones infijas

Una sola producción, todas las operaciones

La BNF entregable declara <expresion> como una única producción recursiva con TODOS los operadores al mismo nivel:

<expresion>   ::= <expresion> "+" <expresion>
               | <expresion> "*" <expresion>
               | <expresion> "&&" <expresion>
               | "!" <expresion>
               | "-" <expresion>
               | ...
               | ENTERO | DECIMAL | CADENA | ID | ...

Una gramática "de libro" partiría esto en niveles expr → termino → factor para forzar la precedencia estructuralmente ([[Ambigüedad, precedencia y asociatividad]] del Dragón, §4.3). CompScript, en cambio, se desambigua con la tabla de precedencia y asociatividad de CUP — exactamente como lo hace el propio enunciado en su §5.9.

La tabla real del .cup

Ocho niveles, de más débil a más fuerte

precedence left  OR;                                              // nivel 7 (mas debil)
precedence left  AND;                                             // nivel 6
precedence right NOT;                                             // nivel 5
precedence left  IGUAL_IGUAL, DIFERENTE, MENOR, MENOR_IGUAL,
                 MAYOR, MAYOR_IGUAL;                               // nivel 4
precedence left  MAS, MENOS;                                      // nivel 3
precedence left  POR, DIV, MOD;                                   // nivel 2
precedence nonassoc POT, RAIZ;                                    // nivel 1
precedence right UMENOS;                                          // nivel 0 (mas fuerte)

En CUP, cada línea posterior liga más fuerte que la anterior. Así a || b && c se agrupa como a || (b && c) sin que la gramática necesite un no-terminal extra por nivel: la tabla resuelve el conflicto shift-reduce por sí sola en tiempo de generación.

Contraste con DataForge: ahí no hacía falta ninguna tabla de precedencia — las llamadas tipo SUM(a, b) ya delimitan sus operandos con paréntesis, sin ambigüedad posible.

El truco del pseudo-terminal

UMENOS: un token que nunca aparece en el código fuente

El símbolo - tiene dos significados: resta binaria (a - b) y negación unaria (-a). Ambos usan el mismo token léxico MENOS, pero necesitan precedencias distintas — la negación unaria debe ligar MÁS fuerte que cualquier operador binario.

// parser.cup
terminal UMENOS;   // pseudo-terminal: SIN lexema, solo existe para dar precedencia

expr ::= MENOS expr:e   {: RESULT = new A.Unaria("NEG", e, ...); :}  %prec UMENOS
       | expr:a MENOS expr:b {: RESULT = new A.Binaria("-", a, b, ...); :}
       ;

La cláusula %prec UMENOS le dice a CUP: «trata esta producción específica como si tuviera la precedencia de UMENOS (la más alta), aunque use el símbolo MENOS». Es el truco estándar de CUP/Yacc para el problema clásico «unario vs. binario» sobre el mismo símbolo léxico.

Error común documentado: si se olvida el %prec UMENOS, CUP no sabe que la negación debe ligar distinto de la resta — y reporta un conflicto shift-reduce al generar el parser.

El otro conflicto clásico

El else colgante

Con if (a) if (b) x; else y;, ¿el else pertenece al if (a) o al if (b)? CompScript lo resuelve estructuralmente, con el orden de las producciones de if_stmt:

<if>  ::= "if" "(" <expresion> ")" <bloque>
       | "if" "(" <expresion> ")" <bloque> "else" <bloque>
       | "if" "(" <expresion> ")" <bloque> "else" <if>

CUP no reportó ningún conflicto shift-reduce al generar este parser: por diseño de la gramática, un else siempre se asocia con el if abierto más cercano — la resolución clásica del Dragón §4.8.2, lograda sin necesitar ninguna directiva de precedencia especial para if/else.

La decisión de diseño central de todo el proyecto

Cada acción del .cup construye un nodo

Esto es lo que distingue a CompScript de DataForge y ConjAnalyzer (ambos S-atribuidos, ejecutan directo en las acciones). Acá, ninguna acción calcula un resultado final — todas arman objetos del paquete ast:

expr ::= expr:a MAS expr:b  {: RESULT = new A.Binaria("+", a, b, aleft, aright); :}
       | ID:id              {: RESULT = new A.AccesoVariable(id, idleft, idright); :}
       ;

parser.raiz termina siendo un ArrayList (tipo raw, por la misma restricción de CUP sobre no-terminales que ya existía en DataForge) con la lista de instrucciones de nivel superior — el Interprete lo recorre después, en las etapas siguientes.

Modo pánico, igual patrón que DataForge

Recuperación ante errores sintácticos

<instruccion> ::= <sentencia-simple> ";"
                | ... | "error" ";"        // produccion de panico

Ante un token inesperado, syntax_error(Symbol s) registra el error en el Contexto compartido con la posición exacta, y la producción de pánico descarta símbolos hasta el próximo ;, permitiendo seguir analizando la instrucción siguiente en la misma pasada.

// entradas/ejemplo6_errores.cs, linea 8
let w: int = ;   // [Sintactico] no se esperaba ';' (linea 8, columna 14)

Ojo con el pánico y los bloques: si el error ocurre dentro de un bloque sin ; cercano (por ejemplo un if mal cerrado), la recuperación puede descartar más código del esperado — vale la pena probarlo con casos reales, como se hizo en la verificación de este proyecto.

Chequeo rápido

Sobre la gramática real

1 · ¿Cómo se agrupa 2 + 3 * 4 según la tabla de precedencia?

2 + (3 * 4). POR está en un nivel de precedencia más alto (ligado más fuerte) que MAS en la tabla del .cup.

2 · ¿Por qué UMENOS no aparece nunca como lexema en un archivo .cs?

Porque es un pseudo-terminal: se declara en el .cup solo para asignarle una precedencia distinta a la negación unaria mediante %prec UMENOS. El lexer nunca produce ese token — el símbolo léxico real siempre es MENOS.

3 · ¿Qué construye la acción de expr ::= expr MAS expr — un valor numérico o un objeto?

Un objeto: new A.Binaria("+", a, b, ...). La suma NO se calcula durante el análisis sintáctico — el nodo se limita a recordar la operación y sus dos operandos; el cálculo ocurre después, cuando el árbol se recorre (Etapa 3).

Etapa 2 · construida

Queda construido el analizador sintáctico

Expresiones infijas desambiguadas por tabla de precedencia, el pseudo-terminal UMENOS, el dangling else resuelto por orden de producciones, y cada acción construyendo un nodo del AST en vez de calcular un valor.
