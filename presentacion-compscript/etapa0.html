Etapa 0 · Parte 1

CompScript: el proyecto que sí necesita un árbol

CompScript es el tercer proyecto del curso: un intérprete completo con análisis léxico, sintáctico y semántico, y un requisito explícito que no tenía DataForge — construir un árbol de sintaxis abstracta (AST) y ejecutar el programa recorriéndolo.

Objetivo general del enunciado: «Aplicar los conocimientos sobre la fase de análisis léxico, sintáctico y semántico de un compilador para la realización de un intérprete sencillo, con las funcionalidades principales para que sea funcional.»

El enunciado, en cuatro líneas

Objetivos específicos (sección 2)

1 · Reforzar léxico/sintáctico/semántico

Para la creación de un lenguaje de programación propio.

2 · Interpretar código de alto nivel

Aplicar los conceptos de compiladores a un proceso de interpretación real.

3 · Construir un AST

Explícito en el enunciado: «Construir un árbol de sintaxis abstracta (AST) para la ejecución de código de alto nivel.»

4 · Detectar y reportar errores

Léxicos, sintácticos y semánticos — con una exigencia nueva: poder terminar la ejecución ante un error semántico.

El objetivo 3 es la clave de todo el curso guiado: ningún otro proyecto hermano lo pide con esa literalidad. Esa sola frase obliga a un cambio de arquitectura completo frente a DataForge.

El contraste con el proyecto hermano

Recordando DataForge: evaluación directa

En DataForge, cada acción semántica del parser ({: RESULT = ... :}) calcula un valor en el momento de la reducción. Eso funciona porque DataForge no tiene ninguna instrucción que deba ejecutarse una cantidad variable de veces: todo el programa es una secuencia lineal de declaraciones, asignaciones y gráficas, cada una ejecutada exactamente una vez, en el orden en que aparece.

// DataForge — evaluación directa: la acción CALCULA
aritmetica ::= op PAR_IZQ expr COMA expr PAR_DER
    {: RESULT = Operaciones.aritmetica(op, a, b, ...); :}

Ese patrón se rompe apenas aparece un while o una función recursiva: el analizador sintáctico reduce cada producción una sola vez, sin importar cuántas veces debería ejecutarse su cuerpo en tiempo de ejecución.

La razón estructural

CompScript tiene control de flujo real

El lenguaje incluye if/else, match, while, for, do-while, break/continue/return, funciones con recursión y métodos. Todas estas construcciones exigen poder ejecutar el mismo fragmento de código cero, una o N veces — algo que una gramática S-atribuida, evaluada en el momento de cada reducción LALR, no puede resolver.

DataForge (S-atribuido)CompScript (con AST)
Cada instrucción correexactamente 1 vez, en orden textual0, 1 o N veces — lo decide el árbol al recorrerlo
¿Cuándo se ejecuta?en el instante de la reducción del parseren una fase posterior, separada del análisis sintáctico
Construcciones que soportadeclaraciones, aritmética, estadística, gráficasif, while, for, funciones, recursión, structs

Manual Técnico de CompScript, §3.1: «en cuanto la gramática de un lenguaje incluye ciclos o funciones con recursión, la construcción de un árbol intermedio se vuelve necesaria.»

Adelanto de la Etapa 6

Ejecutar un árbol no es solo «recorrerlo una vez»

El enunciado (§5.23) recomienda tres pasadas sobre el árbol ya construido:

// Interprete.ejecutar(String codigo) — compscript.interprete.Interprete
// 1a pasada: registrar funciones, metodos y structs (permite referencias hacia adelante)
// 2a pasada: declaraciones y asignaciones globales
// 3a pasada: ejecutar RUN_MAIN (el punto de entrada del programa)

Esto es algo que la evaluación directa de DataForge jamás podría hacer: no hay forma de «pasar dos veces» por una acción de CUP que ya se ejecutó y se olvidó de sí misma. Con el árbol en memoria como estructura de datos, en cambio, recorrerlo tres veces —o las que hagan falta— es trivial.

Para retener durante todo el curso: el AST convierte al programa en datos. Analizar sintácticamente ya no es «ejecutar mientras se lee»: es «construir una estructura», y ejecutar pasa a ser una operación completamente aparte, que se puede repetir, posponer o partir en fases.

Chequeo rápido

¿Quedó claro el porqué?

1 · ¿Por qué una gramática S-atribuida (evaluación directa, como DataForge) no alcanza para un while?

Porque el parser LALR reduce cada producción exactamente una vez, en el momento en que completa su patrón. Un while necesita que su cuerpo se re-evalúe N veces (o cero) según una condición que cambia en tiempo de ejecución — algo que ya pasó y no puede «volver a pasar» en una gramática S-atribuida.

2 · ¿Qué cambia concretamente en las acciones del .cup al construir un AST en lugar de evaluar directo?

En vez de RESULT = Operaciones.aritmetica(...) (que calcula un valor final), la acción hace RESULT = new A.Binaria("+", a, b, ...) (que construye un objeto que sabe calcularlo después, cuando alguien llame a evaluar(entorno)).

3 · Según el Manual Técnico, ¿en cuántas pasadas se recorre el árbol para ejecutar el programa, y por qué esa cantidad?

Tres: registrar funciones/structs, ejecutar declaraciones globales, y ejecutar RUN_MAIN. La primera pasada existe para permitir referencias hacia adelante — que una función llame a otra declarada más abajo en el archivo — algo imposible de resolver con evaluación directa en una sola pasada del parser.
