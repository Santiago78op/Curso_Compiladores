Etapa 4 · Parte 1

Contexto y Entorno: dos objetos, dos responsabilidades

DataForge tenía un único Entorno con un solo mapa de símbolos, porque no hay bloques anidados ni funciones. CompScript necesita algo más: una pila de ámbitos enlazados — porque cada if, cada ciclo y cada llamada a función abre su propio espacio de nombres.

Fuente: interprete/Contexto.java, interprete/Entorno.java.

Lo único, compartido por toda la ejecución

Contexto: el estado global de una corrida

Se instancia UNA vez por llamada a Interprete.ejecutar(...) — igual que el Entorno fresco de DataForge, garantiza que cada ejecución parta de cero:

Lo que SÍ se anida

Entorno: un ámbito, con un padre

public class Entorno {
    public final Contexto contexto;
    public final Entorno padre;             // null = entorno global
    private final LinkedHashMap<String, Simbolo> tabla = new LinkedHashMap<>();

    public Entorno crearHijo(String nombre) {
        return new Entorno(contexto, this, nombre);
    }
    public Simbolo buscar(String id) {
        for (Entorno e = this; e != null; e = e.padre) {
            // busca en e.tabla; si no esta, sube a e.padre
        }
    }
}

Un Contexto por ejecución, pero muchos Entorno: cada if, while, for, match, cuerpo de función crea un hijo con e.crearHijo("nombre"). buscar() sube por la cadena de padres hasta encontrar el identificador o llegar al ámbito global — alcance estático anidado, tal como lo describe el Dragón (§2.7, entornos y ámbitos).

La decisión de diseño más importante de este capítulo

¿De quién cuelga el entorno de una función?

// A.invocar(...) — el entorno de la funcion SIEMPRE cuelga del global:
Entorno local = ctx.global.crearHijo(f.id);   // NO: caller.crearHijo(f.id)

Cada llamada a función crea un nuevo registro de activación (Registro de activación y pila de control, Dragón cap. 7) cuyo padre es siempre el entorno global — nunca el entorno de quien la invoca. Esto es lo que hace que CompScript tenga alcance estático: una función no ve las variables locales de quien la llama, sin importar desde dónde se invoque.

Error común documentado: si por accidente se cuelga del entorno del invocador (caller.crearHijo(...)), las funciones dejarían de tener alcance estático y empezarían a ver variables locales de quien las invoca — el clásico bug de dynamic scoping no deseado.

Comprobación de tipos para tipos compuestos

Tipo: igualdad estructural, no solo por nombre

enum Cat { INT, DOUBLE, BOOL, CHAR, STRING, VOID, NULL, VECTOR, LIST, STRUCT }

Para los tipos primitivos, comparar es trivial. Pero Tipo también modela vectores (con elemento y dimensiones) y structs (con structName), e implementa equals() con igualdad estructural: dos vectores son el mismo tipo si tienen igual elemento base y dimensiones; dos structs, si comparten el mismo nombre declarado. Esto permite validar, por ejemplo, que int[][] no se pueda asignar donde se espera int[].

Una decisión que sorprende la primera vez

La tabla de símbolos del reporte NO es el estado final

Simbolo guarda nombre, categoría (Variable/Vector/Lista/Struct), tipo, mutabilidad (let vs. const), ámbito, valor y posición. ctx.simbolos es un registro histórico acumulativo: cada vez que e.declarar(...) registra una variable, se agrega una entrada nueva — nunca se sobrescribe ni se limpia.

Caso realLo que muestra el reporte 6.4

Por qué es un log y no un snapshot: es evidencia directa de que cada llamada a función — recursiva o no — crea su propio Entorno hijo, con su propia copia de cada parámetro. El reporte no muestra "el valor final de n"; muestra la historia completa de cuántas veces se declaró.

Chequeo rápido

Sobre ámbitos y símbolos

1 · ¿Por qué DataForge no necesitaba una pila de Entornos como CompScript?

Porque DataForge no tiene bloques anidados ni funciones: todas sus variables viven en un único ámbito plano. CompScript, con if/ciclos/funciones, necesita que cada uno de esos bloques pueda declarar variables propias sin chocar con las de afuera — de ahí la cadena de padres.

2 · Si fibonacci(n=10) hace 177 llamadas recursivas, ¿cuántos Entornos distintos existieron durante esa ejecución (aproximadamente)?

Uno por cada llamada — cada invocación de fib crea su propio Entorno hijo del global vía ctx.global.crearHijo("fib"). Esto coincide con las 186 entradas de n que aparecen en el reporte de símbolos de ejemplo5.cs.

3 · ¿Qué pasaría si el entorno de una función colgara del entorno del llamador en vez del global?

La función podría ver (y potencialmente modificar) variables locales de quien la invoca — dynamic scoping en vez de static scoping. Rompería el modelo mental esperado de un lenguaje con bloques: una función debería depender solo de sus parámetros y del ámbito global, nunca de dónde fue llamada.

Etapa 4 · construida

Queda construida la pila de ámbitos

Contexto (uno por ejecución, estado global) + Entorno (una cadena de ámbitos enlazados, uno por bloque/función) implementan alcance estático anidado. El entorno de una función cuelga siempre del global, nunca del invocador.
