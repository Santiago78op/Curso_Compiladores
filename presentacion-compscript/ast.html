El AST real de CompScript — un programa entero, dibujado

Las etapas anteriores mostraron las piezas por separado: las interfaces (Etapa 3), la pila de ámbitos (Etapa 4), el flujo de control (Etapa 5), las funciones (Etapa 6). Acá se arma todo junto sobre un único ejemplo real — factorial de entradas/ejemplo5.cs — y se compara, sin adornos, contra la evaluación directa de DataForge.

Al final de esta presentación queda la posibilidad de defender la arquitectura del proyecto en la calificación.

Cómo se arma el árbol, reducción a reducción

El parser construye nodos, no valores

Se toma la expresión n * factorial(n = n - 1) (dentro del return de factorial) y se sigue el pipeline completo — cada reducción del parser dispara su acción {: ... :}, en este orden:

El parser reduce……y corre esta acciónResultado
el lexer entrega: n * factorial ( n = n - 1 )
expr ::= ID (la primera n)RESULT = new A.AccesoVariable("n", ...)nodo AccesoVariable sube
expr ::= ID (la segunda n, dentro del argumento)RESULT = new A.AccesoVariable("n", ...)otro nodo AccesoVariable, independiente del primero
expr ::= ENTERO (el 1)RESULT = new A.Literal(Valor.vInt(1))nodo Literal sube
expr ::= expr MENOS expr (n - 1)RESULT = new A.Binaria("-", n, 1, ...)un nodo Binaria que envuelve a los dos anteriores — nada se calculó todavía
argumento ::= ID IGUAL expr (n = n-1)RESULT = new A.Argumento("n", binaria, ...)nodo Argumento envolviendo al Binaria
llamada ::= ID PAR_IZQ lista_arg PAR_DERRESULT = new A.Llamada("factorial", [argumento], ...)nodo Llamada — sigue sin ejecutarse nada
expr ::= expr POR expr (n * factorial(...))RESULT = new A.Binaria("*", n, llamada, ...)la RAÍZ de esta expresión: un árbol de 7 nodos, cero cálculos hechos

El contraste con la Etapa 2 de la traza de DataForge: ahí, la reducción de aritmetica ::= op PAR_IZQ expr COMA expr PAR_DER llamaba a Operaciones.aritmetica(...) y calculaba 5.0 en el acto. Acá, la reducción equivalente construye new A.Binaria(...) y NO calcula nada — el cálculo queda pendiente hasta la fase de ejecución.

// entradas/ejemplo5.cs — el codigo fuente exacto de este arbol:
int factorial(n: int) {
    if (n <= 1) { return 1; }
    return n * factorial(n = n - 1);
}

Este texto es exactamente lo que produce Reportes.astHtmlNodo(...) al recorrer hijosAst() recursivamente — la misma estructura que se ve en ast.html del reporte real, o en el TreeView de la GUI (Etapa 7). Nótese que las llaves { }, los paréntesis y el punto y coma NO aparecen en ningún lado: ya cumplieron su función guiando al parser (Etapa 2) y no forman parte del árbol abstracto.

De la estructura al cálculo

Ejecutar es recorrer — y factorial se recorre a SÍ MISMO

Cuando console.log(factorial(n = 5)) corre, A.invocar("factorial", ...) ejecuta el cuerpo del árbol de arriba con n=5. La rama return n * factorial(n = n - 1) vuelve a llamar a invocar(...) — que vuelve a recorrer el MISMO árbol (la misma instancia de A.DeclaracionFuncion en memoria), pero con un Entorno nuevo y n=4:

Llamadan en su propio EntornoQué rama del árbol ejecuta
factorial(n=5)5n <= 1 falso → return n * factorial(n=4)
factorial(n=4)4n <= 1 falso → return n * factorial(n=3)
factorial(n=1)1n <= 1 verdadero → return 1 (caso base)

El árbol de sintaxis existe UNA sola vez en memoria (se construyó una vez, durante el análisis sintáctico) — pero se recorre 5 veces, cada una con su propio Entorno (Etapa 4) colgado del global. Es exactamente lo que la evaluación directa de DataForge no puede reproducir: ahí, cada acción de CUP corrió una única vez, en el momento de su reducción, y ya no existe.

La comparación entre los dos proyectos hermanos

Evaluación directa vs. recorrido de árbol

DataForge (evaluación directa)CompScript (AST)
La acción del .cupcalcula el resultado finalconstruye un nodo (RESULT = new A....)
¿Cuándo se calcula?en el instante de la reduccióndespués, cuando alguien llama a evaluar()/ejecutar()
Cada instrucción correexactamente 1 vez, en orden textual0, 1 o N veces — lo decide el árbol al recorrerse
¿Se puede recorrer 2 veces?no — la acción ya se ejecutó y se olvidó de sí mismasí — es la base de while/for y de la recursión
Costo de implementaciónmínimo, sin clases extra~25 clases de nodo, una por construcción
Necesario cuando…el lenguaje NO tiene control de flujohay if/ciclos/funciones/recursión

La defensa del proyecto en una frase: «CompScript tiene control de flujo real —if, ciclos, funciones con recursión— por lo que cada instrucción puede necesitar ejecutarse cero, una o N veces. Eso es imposible con evaluación directa en las acciones de un parser LALR, que reduce cada producción una única vez. Por eso el análisis sintáctico construye un AST (ast.A) y la ejecución es una fase separada que recorre ese árbol tantas veces como el propio programa lo exija.»

Chequeo rápido

¿Se puede defender la arquitectura?

1 · En el árbol de factorial, ¿por qué hay DOS nodos AccesoVariable distintos con el mismo nombre n dentro de return n * factorial(n = n - 1)?

Porque cada aparición textual de n en el código fuente produce su propio nodo al reducirse — el árbol no "deduplica" identificadores. Ambos nodos, al evaluarse, consultarán el mismo Entorno (Etapa 4) y encontrarán el mismo valor, pero son dos objetos A.AccesoVariable diferentes en memoria.

2 · ¿Cuántas veces se construye el árbol de factorial durante console.log(factorial(n = 5))? ¿Y cuántas veces se recorre?

Se construye una sola vez, durante el análisis sintáctico (cuando CUP reduce la producción de <funcion>). Se recorre 5 veces — una por cada llamada recursiva (n=5,4,3,2,1) — cada vez con un Entorno distinto.

3 · Si a DataForge le agregaran un while en la calificación, ¿qué tendría que cambiar en su arquitectura?

Migrar de evaluación directa a un AST: (1) crear interfaces Instruccion/Expresion y una clase por construcción, siguiendo literalmente el patrón de ast.A de CompScript; (2) cambiar cada acción de CUP de "calcular" a "construir nodo" (RESULT = new ...); (3) tras el parse, recorrer el programa llamando a ejecutar(entorno) sobre cada instrucción de la raíz. El lexer y la gramática de operadores quedarían intactos — solo cambia QUIÉN ejecuta y CUÁNDO.

Resumen en una pantalla

Construir una vez · recorrer las veces que haga falta

DataForge: las acciones CUP calculan al reducir, una vez, en orden — perfecto sin control de flujo. CompScript: las acciones construyen objetos (ast.A) y ejecutar es recorrer ese árbol — obligatorio con if/while/funciones/recursión. Los dos proyectos eligieron bien, cada uno para su propio lenguaje.
