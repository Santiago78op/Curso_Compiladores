Etapa 5 · Parte 1

Cero, una o N veces: el momento en que el árbol se justifica

Con el AST y la pila de Entornos ya construidos (Etapas 3 y 4), if/else, match, while, for y do-while se implementan como código Java normal — cada nodo re-evalúa su condición y vuelve a recorrer su cuerpo tantas veces como haga falta.

Fuente: ast/A.java (clases If, Match, While, For, DoWhile) + interprete/Senales.java.

La construcción más simple

If: un ámbito nuevo por rama

public void ejecutar(Entorno e) {
    Valor v = cond.evaluar(e);
    if (v.tipo.cat != Tipo.Cat.BOOL)
        e.errorSemantico("la condicion del if debe ser Booleana", linea, columna);
    if ((Boolean) v.valor) A.ejecutar(cuerpo, e.crearHijo("if"));
    else if (sinoIf != null) sinoIf.ejecutar(e);
    else if (!sino.isEmpty()) A.ejecutar(sino, e.crearHijo("else"));
}

Cada rama (if, else) crea su propio Entorno hijo: una variable declarada dentro del bloque if no existe fuera de él. La comprobación de tipo de la condición (debe ser Booleana) es semántica en tiempo de ejecución — no la valida la gramática, la valida el propio nodo al evaluarse.

Los tres ciclos, lado a lado

La condición se re-evalúa en cada vuelta

CicloCuándo evalúa la condiciónÁmbito
whileANTES de cada iteración (0 o más veces)un hijo nuevo por iteración
forANTES de cada iteración, tras ejecutar init una sola vezun hijo del for por el init, y otro anidado por iteración
do-whileDESPUÉS de cada iteración (mínimo 1 vez)un hijo nuevo por iteración
 
// A.While.ejecutar(...) — el patron que se repite en For y DoWhile:
while (true) {
    Valor v = cond.evaluar(e);
    if (!(Boolean) v.valor) break;
    try { A.ejecutar(cuerpo, e.crearHijo("while")); }
    catch (Senales.Break b) { break; }
    catch (Senales.Continue ct) { /* siguiente iteracion */ }
}

Este while (true) de Java es, literalmente, el mecanismo que hace posible ejecutar el mismo subárbol N veces — algo que la evaluación directa de DataForge no puede reproducir, porque ahí cada acción del parser corre exactamente una vez, al reducir.

Verificación real — ejemplo3.cs

continue y break sobre el mismo for

for (i = 0; i < 10; i++) {
    if (i == 2) { continue; }
    if (i == 4) { break; }
    console.log(i * 10);     // 0 10 30
}

Consola real obtenida al correr ejemplo3.cs: 0 10 30. Confirma que continue en i==2 saltó el console.log de esa vuelta (no imprimió 20) y que break en i==4 cortó el ciclo antes de imprimir 40.

Una decisión de diseño elegante

break/continue/return son excepciones de control

// Senales.java
public static class Break extends RuntimeException {
    public Break(int l, int c) {
        super(null, null, false, false);  // sin stacktrace: es control de flujo, no un error
    }
}

En vez de que cada ciclo lleve una bandera booleana detener que haya que revisar manualmente después de cada instrucción del cuerpo, A.Break.ejecutar() simplemente lanza Senales.Break — y el while/for/do-while más cercano la atrapa con un catch. Java se encarga de "saltar" fuera del cuerpo aunque el break esté anidado dentro de varios if.

A.Return usa el mismo mecanismo, pero Senales.Retorno viaja con el valor adentro: A.invocar(...) (Etapa 6) la atrapa para recuperar el resultado de la función.

Qué pasa si se escapa: un break fuera de cualquier ciclo no tiene quién lo atrape — llega hasta Interprete.ejecutar(...), que lo convierte en un error semántico: 'break' fuera de un ciclo.

El switch de CompScript

match: sin fall-through, por diseño explícito

for (CasoMatch cm : casos) {
    Valor cv = cm.valor.evaluar(e);
    Valor eq = Operaciones.relacional("==", sel, cv, e, linea, columna);
    if (eq != null && (Boolean) eq.valor) {
        A.ejecutar(cm.cuerpo, e.crearHijo("match"));
        return;   // sin fall-through (5.15.2)
    }
}
if (defecto != null && !defecto.isEmpty())
    A.ejecutar(defecto, e.crearHijo("match-default"));

El return explícito dentro del bucle de casos ES la implementación literal de "no requiere break, no hay fall-through" del enunciado (§5.15.2): apenas un caso coincide, se ejecuta su cuerpo y se sale del método sin mirar los casos restantes.

Un bug real, encontrado en auditoría y corregido

&& y || evalúan con cortocircuito

// A.Binaria.evaluar() — der solo se evalua si izq no decide ya el resultado:
case "&&": {
    Valor a = izq.evaluar(e);
    if (a.tipo.cat == Tipo.Cat.BOOL && !(Boolean) a.valor) return Valor.vBool(false);
    return Operaciones.logica(op, a, der.evaluar(e), e, linea, columna);
}
case "||": {
    Valor a = izq.evaluar(e);
    if (a.tipo.cat == Tipo.Cat.BOOL && (Boolean) a.valor) return Valor.vBool(true);
    return Operaciones.logica(op, a, der.evaluar(e), e, linea, columna);
}

La versión original de A.Binaria.evaluar() evaluaba izq y der ANTES de entrar al switch que decide qué operador aplicar — es decir, evaluaba siempre ambos lados de &&/||, sin cortocircuito. Una auditoría posterior lo señaló como bug real (no una decisión de diseño documentada): el enunciado no lo exige explícitamente, pero la falta de cortocircuito SÍ es observable semánticamente, no solo una optimización perdida — una guarda típica como x != 0 && 10/x > 1 explotaba con división entre cero en vez de evitarla. La corrección: izq se evalúa primero; si ya determina el resultado (false para &&, true para ||), der ya no se evalúa.

Por qué importa: el cortocircuito no es solo un ahorro de cómputo — evita ejecutar der cuando podría fallar (división entre cero, índice fuera de rango) o tener efectos secundarios (llamada a función con push/pop sobre una lista) que no deberían ocurrir. Se verificó contra los 6 ejemplos de entradas/ sin regresiones, y con un caso ad-hoc de guarda (x = 0; x != 0 && 10/x > 1) que ya no lanza error de división entre cero.

Chequeo rápido

Sobre el flujo de control real

1 · ¿Qué diferencia de comportamiento hay entre while y do-while en cuanto al número mínimo de ejecuciones del cuerpo?

while puede ejecutar su cuerpo CERO veces si la condición es falsa desde el inicio (se evalúa ANTES). do-while ejecuta su cuerpo AL MENOS una vez, porque la condición se evalúa DESPUÉS de la primera pasada — así lo confirma ejemplo3.cs con k imprimiendo 0 1.

2 · ¿Por qué Senales.Break extiende RuntimeException en vez de usar una variable booleana de control?

Porque un break puede estar anidado dentro de varios niveles de if o incluso otro ciclo interno — usar una excepción permite que Java "desenrolle" automáticamente todas esas capas intermedias hasta el ciclo que la atrapa, sin tener que revisar manualmente una bandera después de cada instrucción del cuerpo.

3 · Si verificar() tiene efectos secundarios (por ejemplo, hace contador.push(1)) y se evalúa false && verificar(), ¿se ejecuta verificar() en CompScript?

No. A.Binaria.evaluar() evalúa izq primero; como ya es false (un Booleano), el resultado de && queda decidido sin necesidad de evaluar der, así que verificar() nunca corre — el mismo cortocircuito de la mayoría de lenguajes de propósito general. (Antes de la corrección de esta etapa, sí se ejecutaba siempre; era un bug real, no una decisión de diseño.)

Etapa 5 · construida

Queda construido el flujo de control

if/match/while/for/do-while re-evalúan sus condiciones cuantas veces haga falta; break/continue/return viajan como excepciones de control. Esta es exactamente la razón por la que el proyecto necesitaba un árbol (Etapa 0).
