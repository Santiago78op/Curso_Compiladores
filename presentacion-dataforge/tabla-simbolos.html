Profundización · Dragón §2.7 (y §6.5)

La tabla de símbolos, a fondo

La memoria del compilador: dónde viven las variables, cómo se buscan, y el concepto que el libro considera central — los ámbitos anidados. Incluye la comparación honesta: ¿la de nuestro DataForge está «bien» según la teoría?

Spoiler: sí — como caso particular. Esta presentación muestra el caso general, que será necesario en CompScript.

La definición del libro

Un diccionario con dos operaciones

El Dragón la define sin misterio (§2.7): una estructura donde el compilador guarda información sobre cada nombre declarado, con dos operaciones esenciales:

put(nombre, info) — al DECLARAR

Cuando el parser procesa var:double:: numero <- 2.5, inserta la ficha de numero. En nuestro Entorno: declararVariable(...).

get(nombre) — al USAR

Cuando aparece numero en una expresión, busca su ficha (¿existe? ¿de qué tipo es? ¿qué vale?). En nuestro Entorno: valorDe(...).

¿Y qué lleva la «ficha»? El libro dice: lo que el compilador necesite saber del nombre. Para un intérprete como el nuestro:

Campo de nuestro SimboloPara qué
nombremostrarlo como lo escribió el usuario
categoria (variable / arreglo)que @datos no se confunda con datos
tipo (double / char[])chequeo semántico de asignaciones y operaciones
valorsomos un INTÉRPRETE: la variable vive acá
linea, columnareporte §6.3 y mensajes de error

Detalle nuestro: un compilador clásico NO guarda el valor (genera código que lo calculará en runtime); un intérprete sí. Misma tabla, inquilino extra.

Implementación

¿Con qué se construye? Hash, dice el libro

El libro (§2.7 y §6.5) recomienda una tabla hash: get/put en tiempo constante O(1), porque un compilador consulta la tabla muchísimas veces. En Java eso es un HashMap — y nosotros usamos su primo:

private final LinkedHashMap<String, Simbolo> simbolos = new LinkedHashMap<>();
//        └─ hash O(1) para get/put ─┘└─ y además RECUERDA el orden de inserción
  • ¿Por qué Linked? El reporte §6.3 debe listar los símbolos en orden de declaración. Un HashMap pelado los devuelve en orden arbitrario; el Linked mantiene el orden sin costo relevante. Teoría del libro + requisito del enunciado.
  • ¿Por qué la clave en minúsculas? DataForge es case insensitive — nUmero y numero son LA MISMA variable. Clave normalizada (toLowerCase), nombre original guardado en la ficha para mostrar.

El libro también menciona alternativas históricas (listas, árboles de búsqueda) — hoy son curiosidad: hash ganó. Lo que NO es curiosidad histórica es lo que viene ahora: los ámbitos.

El concepto central del §2.7

Ámbitos: la misma palabra, distintas cosas

El problema que el libro considera EL problema de las tablas de símbolos: en casi todo lenguaje, un mismo nombre puede declararse varias veces en bloques distintos, y cada uso debe resolver a la declaración correcta:

int x = 1;              // x "de afuera"
{
    int x = 2;          // OTRA x, que ensombrece a la primera
    print(x);           // → 2  (la más cercana gana)
}
print(x);               // → 1  (la de adentro YA NO EXISTE)

La regla universal: gana la declaración del bloque más cercano (ámbito estático o léxico). Y la estructura que el libro propone para implementarla es elegante:

Una tabla por bloque, encadenadas hacia afuera. Al entrar a un bloque se crea una tabla nueva que apunta a la de su bloque padre; al salir, se descarta. Buscar = mirar en mi tabla, y si no está, subir por la cadena. (Es la clase Env del libro, fig. 2.37.)

La comparación honesta

¿Y la nuestra está bien, según el libro?

Sí — porque DataForge es el caso donde la cadena tiene UN solo eslabón. A continuación, la comparación punto por punto:

Teoría del libro (§2.7)Nuestro EntornoVeredicto
Operaciones put / getdeclararVariable / valorDe (+ variantes de arreglo)✓ igual
Tabla hash para O(1)LinkedHashMap (hash + orden para el reporte)✓ igual (mejorado para §6.3)
Ficha con tipo e info del nombreSimbolo: categoría, tipo, valor, línea, columna✓ igual (+ valor, porque somos intérprete)
Una tabla por bloque, encadenadasUNA sola tabla global✓ correcto acá
get sube por la cadena de padresget directo (no hay adónde subir)✓ correcto acá

¿Por qué «correcto acá»? Los ámbitos existen donde el lenguaje tiene bloques que declaran — llaves, funciones, procedimientos. La gramática de DataForge no tiene NINGUNO: todas las declaraciones viven directas entre PROGRAM…END PROGRAM. Un solo bloque ⇒ un solo entorno ⇒ la cadena degenera en una tabla. Usar la maquinaria completa habría sido sobre-ingeniería, no fidelidad al libro.

Chequeo contra el enunciado: la única semántica de nombres que pide es declarar-antes-de-usar y el reporte §6.3 — ambas cubiertas. Y nuestra decisión de rechazar redeclaración es coherente: sin bloques, una segunda var x no puede ser «otra x de otro ámbito» — solo puede ser un error.

El upgrade que viene

CompScript: donde la cadena se vuelve real

El tercer proyecto tendrá if, ciclos y funciones — es decir, bloques que declaran. Ahí el Entorno muta a la estructura del libro, y el cambio es sorprendentemente chico:

public class Entorno {
    private final Entorno padre;                       // ← LA línea nueva
    private final LinkedHashMap<String, Simbolo> simbolos = new LinkedHashMap<>();

    public Entorno(Entorno padre) { this.padre = padre; }   // global: padre = null

    public Simbolo buscar(String id) {
        Simbolo s = simbolos.get(id.toLowerCase());
        if (s != null) return s;                        // está en MI ámbito
        if (padre != null) return padre.buscar(id);     // subir por la cadena
        return null;                                    // no declarada en ningún lado
    }
}

Entrar a un bloque = new Entorno(entornoActual); salir = volver a usar el padre. La demo de la diapositiva 5, hecha con tres líneas de Java. Nuestro Entorno de DataForge es exactamente esto con padre = null siempre.

Momento de diseño: por eso el trabajo de hoy no se tira — se extiende. Cuando se construya CompScript, el punto de partida es agregar el campo padre y el buscar recursivo. Conviene recordar esta diapositiva.

Chequeo rápido

¿Dominás la memoria del compilador?

1 · En la demo de la diapositiva 5, ¿por qué print(y) dentro del bloque imprime 5 sin que y esté en el entorno del bloque?

Porque get no se rinde en la primera tabla: al no encontrar y en el entorno del bloque, sube por la referencia al padre y la encuentra en el global. La cadena de entornos ES la regla «la declaración más cercana gana» hecha estructura de datos.

2 · ¿Por qué en DataForge la redeclaración es error, pero en CompScript int x dentro de un bloque NO lo será aunque exista una x afuera?

Porque el conflicto solo existe dentro del mismo ámbito. En CompScript las dos x viven en tablas distintas de la cadena (sombreado legal); en DataForge hay una sola tabla, así que la segunda declaración chocaría con la primera sí o sí → error semántico.

3 · Un compilador clásico y nuestro intérprete guardan fichas casi iguales… salvo un campo. ¿Cuál y por qué?

El valor. Un compilador traduce: en su tabla guarda tipo/dirección, y el valor existirá recién cuando el programa compilado corra. Un intérprete ejecuta YA: la tabla de símbolos es, literalmente, la memoria del programa en ejecución. Por eso nuestro Simbolo.valor no está en las figuras del libro — y está bien que no esté.
