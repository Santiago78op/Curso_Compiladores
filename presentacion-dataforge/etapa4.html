Etapa 4 · Ponerle cara

El entorno de trabajo

El intérprete ya lee, valida y ejecuta — pero vive en la terminal. El enunciado (§4) pide un editor: pestañas, abrir/guardar .df, botón Ejecutar y consola de salida. Hoy se construye con JavaFX.

Novedad de la etapa: acá no hay Dragón — es ingeniería de UI. La teoría vuelve en las Etapas 5 y 6.

La herramienta

JavaFX en 3 conceptos (y un déjà vu)

Stage

La ventana del sistema operativo. JavaFX la entrega en el método start(Stage stage).

Scene

El contenido de la ventana. Una ventana muestra una escena a la vez.

Nodos

Todo lo que se ve — botones, pestañas, áreas de texto — organizados en un scene graph.

¿Y el déjà vu? El scene graph es un árbol: contenedores con hijos, hijos con hijos… Van tres etapas trabajando con árboles (derivaciones, cajas anidadas, atributos que suben) — la UI es otro más:

Stage
└── Scene
    └── BorderPane                    (raíz)
        ├── top:    HBox              (barra de botones)
        │           ├── Nuevo · Abrir · Guardar · ▶ Ejecutar
        └── center: SplitPane         (dividido en vertical)
                    ├── TabPane       (el editor: una pestaña por archivo)
                    │   └── Tab → TextArea (el código fuente)
                    └── TextArea      (la consola, NO editable)

Ciclo de vida: JavaFX llama a start(), se arma el árbol, stage.show(), y de ahí en más todo es reaccionar a eventos (setOnAction).

Decisión de diseño

¿UI por código o con FXML/Scene Builder?

JavaFX ofrece dos caminos para armar el árbol:

FXML + Scene Builder

La UI se describe en un XML que se diseña arrastrando controles en Scene Builder; un «controller» Java le pone la lógica. Bueno para interfaces grandes con diseñador visual.

Por código (la opción elegida) ✓

El árbol se construye con new y métodos — todo en un solo archivo Java, sin XML, sin recursos que cargar, sin herramienta extra. Para una UI de 6 controles, es lo más directo y lo más fácil de depurar.

El porqué pedagógico: al construir el scene graph a mano, queda a la vista — cada contenedor, cada hijo. Con FXML el árbol queda escondido en el XML. Cuando la UI crezca (o se prefiera diseñar visualmente), Scene Builder queda disponible — el enunciado no exige ninguno de los dos caminos.

El código clave · 1 de 2

Pestañas y archivos

Cada requisito del §4 se mapea a un control estándar. La pestaña es la unidad central — un Tab cuyo contenido es el editor y cuyo userData recuerda a qué archivo pertenece:

private void nuevaPestana(String titulo, String contenido, File archivo) {
    TextArea area = new TextArea(contenido);
    area.setFont(Font.font("Consolas", 14));
    Tab tab = new Tab(titulo, area);
    tab.setUserData(archivo);      // null = nuevo, sin guardar aún
    pestanas.getTabs().add(tab);
    pestanas.getSelectionModel().select(tab);
}

Abrir y guardar usan FileChooser con filtro *.df (requisito 4.2 exacto). El truco de Guardar: si userData es null, es un archivo nuevo → diálogo «Guardar como», y la pestaña adopta el nombre del archivo:

fc.getExtensionFilters().add(
    new FileChooser.ExtensionFilter("DataForge (*.df)", "*.df"));
File f = fc.showOpenDialog(stage);   // o showSaveDialog para guardar
Files.readString(f.toPath(), StandardCharsets.UTF_8);  // leer moderno, sin loops

«Eliminar pestaña: si los cambios no se han guardado, se descartan» (4.2) — las Tab de JavaFX traen la ✕ de cierre por defecto, y descartar es exactamente no hacer nada. Requisito cumplido gratis.

El código clave · 2 de 2

El botón que une las 4 etapas

La elegancia de esta etapa: conectar TODO lo construido cuesta tres líneas, gracias a una fachada nueva (Interprete.java):

// la fachada: String → pipeline completo → Entorno con resultados
public static Entorno ejecutar(String codigo) {
    Parser parser = new Parser(new Lexer(new StringReader(codigo)));
    try { parser.parse(); } catch (Exception e) { /* ya registrado */ }
    return parser.entorno;
}

// y el botón Ejecutar en la GUI:
ultimoEntorno = Interprete.ejecutar(areaActual().getText());
consola.setText(ultimoEntorno.getConsola() + /* + errores */);
  • StringReader en vez de FileReader: al lexer le da igual de dónde vienen los caracteres — ahora vienen de la pestaña, no del disco. Mismo pipeline, otra fuente.
  • Entorno fresco por ejecución: cada clic crea parser y entorno nuevos — el estado de una corrida no contamina la siguiente (§6: los reportes son solo del último análisis).
  • ultimoEntorno queda guardado: ahí esperan las gráficas registradas (Etapa 5) y los datos de los reportes (Etapa 6).

Infraestructura

El pom nuevo y el truco del Lanzador

Dos agregados al pom.xml:

<dependency>            <!-- los controles de UI (traen también los Charts) -->
    <groupId>org.openjfx</groupId>
    <artifactId>javafx-controls</artifactId>
    <version>21.0.4</version>
</dependency>

<plugin>                <!-- para correr con: mvn clean javafx:run -->
    <groupId>org.openjfx</groupId>
    <artifactId>javafx-maven-plugin</artifactId>
    <version>0.0.8</version>
    <configuration><mainClass>dataforge.gui.EditorApp</mainClass></configuration>
</plugin>

El error famoso: si se le da ▶ Run directo a EditorApp, Java puede abortar con «JavaFX runtime components are missing». El launcher de Java revisa si la clase main extiende Application y exige module-path. La esquiva clásica: una clase Lanzador que NO extiende Application y solo llama a EditorApp.main() — el chequeo no se dispara y el classpath plano de IDEA alcanza. En IDEA hay que correr siempre Lanzador.

Chequeo rápido · Etapa 4

¿Quedaron entendidas las costuras?

1 · ¿Por qué bastó cambiar FileReader por StringReader para que el intérprete corra desde la GUI?

Porque el lexer se programó contra la abstracción Reader (un chorro de caracteres), no contra archivos. Da igual si los caracteres vienen del disco, de una pestaña o de un socket: el pipeline lexer→parser→entorno no se enteró del cambio. Programar contra interfaces pagó su dividendo.

2 · ¿Qué pasaría si reutilizáramos el MISMO Entorno entre clics de ▶ Ejecutar?

El estado se acumularía: la segunda ejecución vería las variables de la primera (¡todas «ya declaradas»!), los errores viejos seguirían en la lista y los reportes mezclarían análisis — justo lo que el enunciado §6 prohíbe («no deberá mostrarse reportes de análisis anteriores»). Por eso: parser y entorno nuevos en cada clic.

3 · ¿Para qué existe Lanzador.java si tiene una sola línea?

Para esquivar el chequeo del launcher de Java: al arrancar desde una clase que NO extiende Application, no se exige tener JavaFX en el module-path, y el classpath plano que IDEA arma desde el pom funciona. Una línea que ahorra pelearse con módulos de Java.
