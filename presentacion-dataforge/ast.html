El AST — y cómo corre el código de verdad

Dos deudas en una: primero, la traza paso a paso de qué ejecuta exactamente el intérprete cuando corre una línea. Después, el árbol de sintaxis abstracta — el patrón que casi todos los proyectos de OLC1 usan, que se decidió NO usar, y por qué esa decisión es correcta acá y sería un error en CompScript.

Al final de esta presentación queda la posibilidad de defender la arquitectura del proyecto en la calificación.

Deuda nº 1 · la traza real

Qué corre EXACTAMENTE al ejecutar una línea

Se toma var:double:: m <- SUM(2,3) end; y se sigue el pipeline completo — cada reducción del parser dispara su acción {: ... :}, en este orden:

El punto clave para lo que viene: cada acción corrió exactamente una vez, en el instante de su reducción, y después se descartó todo. No queda ningún árbol en memoria — solo los efectos (la tabla de símbolos, la consola). Conviene retener esto.

Deuda nº 2 · el concepto

¿Qué es el árbol de sintaxis ABSTRACTA?

El árbol de análisis (las «cajas») refleja la gramática al pie de la letra — con paréntesis, comas y todo. El AST es su versión destilada: solo la esencia de cada construcción (§2.5.1: árbol sintáctico abstracto):

Árbol de análisis (concreto)

aritmetica
├── op_arit → SUM
├── PAR_IZQ (
├── expr → NUMERO 2
├── COMA ,
├── expr → NUMERO 3
└── PAR_DER )

Fiel a la gramática: 6 hijos, incluida la puntuación.

AST (abstracto)

Suma
├── Literal 2
└── Literal 3

Solo lo que importa para ejecutar: la operación y sus operandos. Los ( , ) ya cumplieron su misión (guiar al parser) y desaparecen.

La idea central: el AST es una estructura de OBJETOS en memoria que representa el programa. En vez de ejecutar durante el parse, el parse construye el árbol… y ejecutarlo es un paso separado, que puede repetirse cuantas veces haga falta.

El patrón clásico de OLC1 · 1 de 2

Construir el AST: una clase por concepto

Dos interfaces parten el mundo — lo que produce un valor y lo que hace algo — y cada construcción del lenguaje es una clase:

public interface Expresion  { Object evaluar(Entorno ent); }
public interface Instruccion { void ejecutar(Entorno ent); }

public class Literal implements Expresion {
    private final Object valor;
    public Object evaluar(Entorno ent) { return valor; }
}

public class Suma implements Expresion {
    private final Expresion izq, der;      // ¡los hijos son Expresion:
    public Object evaluar(Entorno ent) {    //  el árbol se anida solo!
        return (Double) izq.evaluar(ent) + (Double) der.evaluar(ent);
    }
}

¿Y quién arma el árbol? Las mismas acciones de CUP — pero en vez de calcular, construyen nodos:

// evaluación directa (lo NUESTRO):        // con AST (el patrón clásico):
RESULT = Operaciones.aritmetica(...);       RESULT = new Suma(a, b);

Es el §5.3.1 del Dragón (construcción de árboles sintácticos): SDT cuyo «valor sintetizado» es un nodo. La jerarquía de clases es la del Apéndice A del libro (Stmt, Expr, While, If…). La reducción final entrega la raíz: un ArrayList<Instruccion> con el programa entero.

El patrón clásico de OLC1 · 2 de 2

Ejecutar el AST: caminar el árbol

Con el árbol en memoria, ejecutar el programa es un paseo recursivo (el intérprete de recorrido de árbol, tree-walking interpreter):

// después del parse, el programa es datos:
ArrayList<Instruccion> programa = (ArrayList<Instruccion>) parser.parse().value;

// y ejecutarlo es recorrerlo:
for (Instruccion i : programa) i.ejecutar(entorno);

Cada nodo sabe ejecutarse a sí mismo y delega en sus hijos — Suma.evaluar() llama a izq.evaluar() y der.evaluar(), que quizás son otras sumas… La recursión de la gramática, ahora hecha objetos.

Honestidad con el libro: la estructura del árbol es la del Dragón (§5.3.1 + Apéndice A), pero nuestros nodos hacen evaluar()/ejecutar() — un intérprete de recorrido de árbol. Los nodos del Dragón hacen gen(): generan código intermedio, porque el libro construye un compilador (caps. 6-8). En OLC1 los proyectos son intérpretes y la generación de código está fuera de alcance — mismo árbol, distinta misión al visitarlo (esta variante está más cerca de Appel).

¿Y por qué tanto lío si el resultado es el mismo? Porque el árbol se puede recorrer más de una vez, o ninguna, o por partes — y ahí está toda la diferencia. Siguiente diapositiva: el argumento decisivo.

La comparación honesta

¿Cuándo se necesita el AST? Cuando algo corre ≠ 1 vez

Vale la pena recordar la traza de la diapositiva 2: cada acción de CUP corre exactamente una vez, al reducir. Ahora conviene imaginar que DataForge tuviera un while:

public class Mientras implements Instruccion {
    private final Expresion condicion;
    private final ArrayList<Instruccion> cuerpo;
    public void ejecutar(Entorno ent) {
        while ((Boolean) condicion.evaluar(ent))     // se evalúa N veces
            for (Instruccion i : cuerpo) i.ejecutar(ent);  // ¡N veces!
    }
}

Con evaluación directa esto es imposible: la acción del cuerpo del while correría una única vez (al parsear), no N. Un if falso tiene el problema espejo: su cuerpo correría UNA vez cuando debía correr CERO.

Evaluación directa (DataForge)AST (CompScript, CompInterpreter)
Cada instrucción correexactamente 1 vez, en orden0, 1 o N veces — lo decide el árbol
Sirve paralenguajes SIN control de flujoif, while, for, funciones, recursión
Costomínimo (sin clases extra)~1 clase por construcción del lenguaje
En el Dragón§2.3, §5.1 (SDT que evalúa)§2.5.1, §5.3 (SDT que construye árbol)

La defensa del proyecto en una frase: «DataForge no tiene control de flujo — toda instrucción se ejecuta exactamente una vez en orden textual — por lo que la evaluación directa en las acciones es suficiente y el AST habría sido complejidad sin retorno. En CompScript, que tiene if/ciclos, construiré el AST con el patrón Instruccion/Expresion.»

Chequeo rápido

¿Se puede defender la arquitectura?

1 · En la traza de la diapositiva 2, ¿por qué la acción de aritmetica pudo ejecutar la suma ANTES de que se redujera decl_var?

Porque LR reduce de adentro hacia afuera: el patrón completo de aritmetica se completa (y reduce) antes que el de decl_var que lo contiene. El orden de las reducciones ES el orden de evaluación — por eso la evaluación directa funciona sin planificar nada.

2 · ¿Qué diferencia hay entre el árbol de las «cajas» (Demo 3 de Gramáticas) y el AST?

Las cajas son el árbol de análisis concreto: una caja por producción aplicada, con puntuación incluida. El AST es su destilado abstracto: solo operaciones y operandos como objetos (Suma(Literal 2, Literal 3)), sin paréntesis ni comas — esos ya cumplieron guiando al parser y no hacen falta para ejecutar.

3 · Si le agregaran un IF a DataForge en la calificación, ¿qué cambiaría en el proyecto?

Migrar de evaluación directa a AST: (1) crear las interfaces Instruccion/Expresion y una clase por construcción; (2) cambiar cada acción de CUP de «calcular» a «construir nodo» (RESULT = new …); (3) tras el parse, recorrer el programa con ejecutar(entorno). El lexer, la gramática y el Entorno quedan intactos — solo cambia QUIÉN ejecuta y CUÁNDO.

Resumen en una pantalla

Acción una vez · árbol N veces

Evaluación directa: las acciones CUP calculan al reducir, una vez, en orden — perfecto sin control de flujo. AST: las acciones construyen objetos (Instruccion/Expresion) y ejecutar es recorrer el árbol — obligatorio con if/while/funciones. DataForge eligió bien; CompScript elegirá el otro camino.
