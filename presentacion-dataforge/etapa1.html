Etapa 1 · Parte 1

La tabla de tokens de DataForge

Antes de escribir el archivo .flex, se necesita el vocabulario completo del lenguaje: cada palabra, símbolo y patrón que el analizador léxico debe reconocer.

Método: recorrer el enunciado sección por sección (5.1 → 5.10) preguntando siempre lo mismo:
«¿qué piezas nuevas aparecen acá que todavía no están en la tabla?»

Regla del match más largo: ante ::, el analizador NO devuelve dos veces : — siempre prefiere el lexema más largo posible. Igual con <-. JFlex lo hace automáticamente.

Decisiones que el enunciado deja abiertas

Cuatro decisiones de diseño

1 · ¿@ es un token aparte?

Podría ser símbolo @ + token ID. Se decide un solo token ID_ARREGLO (@darray completo): el @ nunca aparece solo en el lenguaje, y así la gramática queda más simple.

2 · Los atributos de gráfica NO son reservados

titulo, ejeX, ejeY, tituloX, tituloY, values, label serán ID comunes. Prueba del enunciado: en §5.9.2 declara var:char[]:: titulo <- "Enteros" — si titulo fuera reservada, ¡su propio ejemplo no compilaría! La gramática validará esos nombres.

3 · graphBar vs grapBar

El enunciado escribe graphBar( al abrir pero EXEC grapBar (sin h) al ejecutar — en los 3 tipos. Es un typo sistemático del enunciado: el patrón aceptará ambas formas para el mismo token.

4 · Case insensitive, ¿dónde?

En el patrón: cada palabra reservada se escribe aceptando mayúsculas y minúsculas (JFlex tiene la directiva %ignorecase). El lexema original se conserva para los reportes.

Chequeo rápido · Parte 1

Contá tokens

1 · ¿Cuántos tokens produce console::print = "hola", 15 end;?

9: console · :: · print · = · "hola" · , · 15 · end · ;. Los espacios no cuentan: separan y se descartan.

2 · Con nuestras decisiones, ¿cuántos tokens es @datos?

1: el token ID_ARREGLO con lexema @datos (decisión de diseño nº 1). Con la otra decisión válida habrían sido 2 (@ + ID).

3 · ¿Por qué titulo no puede ser palabra reservada?

Porque el propio enunciado (§5.9.2) lo usa como nombre de variable: var:char[]:: titulo <- "Enteros" end;. Una palabra reservada no puede ser nombre de variable — por eso los atributos de gráfica se tokenizan como ID.

Etapa 1 · Parte 2

Del papel al código: anatomía del .flex

Un archivo JFlex tiene tres secciones separadas por %%. La tabla de tokens se reparte entre las dos últimas:

1

Código de usuario

Se copia tal cual arriba de la clase generada: el package y los import (usamos Symbol de CUP).

2

Opciones y macros

Directivas (%class, %cup, %line, %ignorecase…) y las definiciones regulares: la columna «Patrón» de la tabla, con nombre.

3

Reglas

La tabla hecha código: «cuando se vea esto → se devuelve este token». Una regla por fila.

// sección 2 — así se ve una definición regular con nombre:
Id        = {Letra}({Letra}|{Digito})*
Numero    = {Digito}+("."{Digito}+)?
Cadena    = \"[^\"]*\"

Fuente: nota [[JFlex]] del vault · manual jflex.de.

Etapa 1 · Parte 2

Las reglas: la tabla hecha código

Extracto real del Lexer.flex del proyecto — se compara cada línea con la tabla de tokens:

/* descartar: comentarios y blancos */
{ComentLinea}   { }
{ComentMulti}   { }
{Blancos}       { }

/* reservadas — SIEMPRE antes que {Id} */
"var"       { return symbol(sym.VAR); }
"media"     { return symbol(sym.MEDIA); }

/* símbolos */
"::"        { return symbol(sym.DOBLE_DOS_PUNTOS); }
"<-"        { return symbol(sym.ASIGNACION); }

/* patrones — al final */
{Numero}    { return symbol(sym.NUMERO, Double.valueOf(yytext())); }
{Id}        { return symbol(sym.ID); }

/* cualquier otra cosa = error léxico */
[^]         { /* reportar carácter desconocido */ }

¿Por qué las reservadas van antes que {Id}? media calza con ambas reglas y con el mismo largo. A igual longitud de match, JFlex elige la regla escrita primero. Si {Id} estuviera arriba, ¡ninguna palabra reservada se reconocería jamás!

Puesta en marcha · Opción A: IntelliJ IDEA

Abrir y configurar el proyecto

IntelliJ IDEA trae Maven embebido y puede descargar el JDK 17 desde el propio IDE — no hace falta instalar nada por terminal.

1 · Instalar IDEA (edición Community, gratuita)

Desde jetbrains.com/idea o con: winget install JetBrains.IntelliJIDEA.Community

2 · Abrir el proyecto

Open → hay que seleccionar la carpeta DataForge (la que contiene el pom.xml) → Trust Project. IDEA detecta el pom.xml y lo importa como proyecto Maven automáticamente (conviene esperar a que termine de indexar, barra inferior).

3 · Configurar el JDK 17

File → Project Structure → Project → SDK. Si no aparece ningún 17: Add SDK → Download JDK… → Version 17, Vendor Eclipse Temurin → Download. IDEA lo instala y lo asocia solo.

¿Por qué no molesta el Java 8 que ya está instalado? Porque IDEA usa el SDK configurado en el proyecto, no el del PATH del sistema. Cada proyecto elige su Java.

Puesta en marcha · Opción A: IntelliJ IDEA

Generar el lexer y correrlo

4 · Generar el lexer con Maven

Hay que abrir la ventana Maven (barra lateral derecha, ícono m) → dataforge → Lifecycle → doble clic en compile. Eso corre JFlex: aparece target/generated-sources/jflex/…/Lexer.java y IDEA lo marca como código generado automáticamente.

5 · Ejecutar

Hay que abrir TestLexer.java → botón ▶ verde junto a main → Run. La tabla de tokens sale en la pestaña Run de abajo.

6 · El ciclo de trabajo de aquí en adelante

Cada vez que se edite Lexer.flex: compile en la ventana Maven (regenera el Lexer.java) → ▶ Run. Ese par de clics es el ciclo editar-probar.

Instalar las herramientas (una sola vez)

Alternativa para quienes prefieran trabajar sin IDE — quienes usen IntelliJ IDEA (opción A, diapositivas anteriores) pueden saltarse estas dos.

El proyecto necesita JDK 17 (Java moderno; tener Java 8 instalado no alcanza) y Maven. En Windows se instalan con dos comandos en PowerShell:

Paso obligatorio: al terminar, hay que cerrar y volver a abrir la terminal. Los instaladores modifican el PATH, pero la terminal abierta sigue usando el viejo.

Chequeo rápido · Parte 2

Sobre el lexer real

1 · Si movieras la regla {Id} ARRIBA de las palabras reservadas, ¿qué token produciría var?

ID. Mismo largo de match (3) → gana la regla escrita primero. El lenguaje entero dejaría de tener palabras reservadas. Por eso el orden de las reglas ES parte del diseño.

2 · ¿Para qué escribimos sym.java a mano si CUP la va a generar en la Etapa 2?

Para poder compilar y probar el lexer HOY sin tener parser. El Lexer.flex ya quedó en su forma final (devuelve Symbol con constantes de sym); cuando CUP genere la clase real, borramos la temporal y nada más cambia.

3 · ¿Qué hace nuestro lexer si encuentra un $ en el código fuente?

Cae en la última regla [^] (cualquier carácter no reconocido): se reporta como error léxico con línea y columna — «El carácter "$" no pertenece al lenguaje», exactamente el ejemplo de la tabla de errores del enunciado (§6.2) — y el análisis continúa.
