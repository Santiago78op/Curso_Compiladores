Pieza 1 · el lexer chismoso

Registrar cada token al producirlo

El lugar natural para capturar tokens es donde nacen: los helpers symbol() del .flex. Un campo público conecta lexer y entorno:

// en la sección %{ ... %} del Lexer.flex:
public dataforge.interprete.Entorno entorno;   // lo setea el Interprete

private Symbol symbol(int type) {
    registrar(type);                             // ← la línea nueva
    return new Symbol(type, yyline, yycolumn, yytext());
}
private void registrar(int type) {
    if (entorno != null) entorno.registrarToken(yytext(), type, yyline, yycolumn);
}
  • yytext(), no el valor: el reporte quiere el lexema tal como se escribió — 1 se reporta 1, no 1.0. (La deuda anotada en la Etapa 1, saldada.)
  • Los errores léxicos también migran: la regla [^] ya no imprime a stderr — llama a entorno.error("Léxico", …) y el $ intruso aparece en la tabla §6.2, exactamente como el ejemplo del enunciado.
  • Si entorno == null (TestLexer viejo), todo sigue funcionando como antes.

Pieza 2 · la teoría de la etapa · Dragón §4.8.3

Recuperación en modo pánico: el terminal error

Hasta hoy, el primer error sintáctico mataba el análisis («Couldn't repair and continue parse»). Pero el reporte quiere todos los errores. La herramienta es un terminal especial que CUP (y Yacc, y Jison) traen de fábrica:

instruccion ::= decl_var | decl_arr | imprimir | columna | grafica
              | error PUNTO_COMA ;   // ← la producción de pánico

Qué hace CUP cuando el parser se atasca, paso a paso:

1

Reportar

Llama a syntax_error — el override propio lo registra en el Entorno con línea/columna.

2

Podar la pila

Descarta símbolos de la pila hasta llegar a un estado donde el terminal error se pueda desplazar (o sea: donde empezaba una instrucción).

3

Descartar y seguir

Tira tokens de la entrada hasta encontrar ;, reduce instruccion ::= error PUNTO_COMA… y el análisis continúa con la siguiente instrucción como si nada.

¿Por qué «pánico»? Porque ante el error el parser huye hacia un punto de sincronización seguro — el ;, que en DataForge cierra toda instrucción — sacrificando lo que haya en el camino. Simple, robusto, y el método que el libro recomienda como primera opción (§4.8.1). El costo honesto: lo descartado no se analiza (un error puede ocultar otro en la misma instrucción).

Pieza 3 · refactor pequeño

De Strings a RegistroError

La tabla §6.2 tiene columnas (#, tipo, descripción, línea, columna) — un String formateado no se puede descomponer en celdas. Refactor mínimo:

public class RegistroError {
    public final String tipo;         // "Léxico" | "Sintáctico" | "Semántico"
    public final String descripcion;
    public final int linea, columna;  // ya en base 1, listos para mostrar

    @Override public String toString() { /* mismo formato de siempre */ }
}

El truco del refactor indoloro: toString() devuelve el formato que ya se usaba, así la consola de la GUI y TestInterprete siguen mostrando lo mismo sin cambiar su lógica — pero el generador de reportes ahora accede a cada campo por separado.

Con esto, las TRES familias de errores conviven en una sola lista tipada, cada una etiquetada con su origen: el lexer registra los léxicos, syntax_error los sintácticos, y Entorno/Operaciones los semánticos.

Pieza 4 · el generador

Reportes.java: plantilla + filas + escape

Generar HTML es armar texto. Una plantilla común (título + tabla con CSS embebido — autocontenida, como esta presentación) y un método por reporte que fabrica las filas:

// el nombre del token, sin switch de 40 casos: reflexión sobre sym
for (Field f : sym.class.getFields())
    if (f.getType() == int.class) nombres.put(f.getInt(null), f.getName());

// y cada lexema se ESCAPA antes de entrar a la tabla:
s.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;");

¿Por qué escapar? Meta-momento: el reporte de tokens contiene el lexema <-… que para un navegador parece el inicio de una etiqueta HTML. Es el mismo problema de todo el curso — un texto interpretado por OTRO lenguaje — visto del lado contrario: ahora es quien construye el compilador el que genera código para el intérprete de otro (el navegador).

El botón Reportes de la GUI llama a Reportes.generar(ultimoEntorno, new File("reportes")) y abre los tres archivos con getHostServices().showDocument(...) — la forma JavaFX de lanzar el navegador.

Chequeo rápido · Etapa 6

El examen de las tres familias

1 · En ejemplo4_mixto.df, ¿por qué precio SÍ queda declarada (con 99) pese al $, pero roto NO queda pese a que su error también se recuperó?

Son recuperaciones de capas distintas. El $ es léxico: se descarta solo ese carácter y el resto de la instrucción queda intacta y válida → se ejecuta. El <- faltante es sintáctico: el modo pánico descarta la instrucción COMPLETA hasta el ; — sobrevive el análisis, no la instrucción.

2 · ¿Por qué elegimos ; como punto de sincronización del modo pánico?

Porque en DataForge toda instrucción termina en ; — es el delimitador natural del lenguaje: al saltar hasta ahí, lo próximo que viene es con altísima probabilidad el inicio limpio de otra instrucción. El libro (§4.8.1) llama a estos tokens «de sincronización»; en C serían ; y }.

3 · ¿Por qué el reporte de tokens necesitó tocar el LEXER, si el parser ya recibía todos los tokens?

Dos razones: el parser consume y descarta los Symbol al reducir (no queda lista de tokens en ningún lado), y además el Symbol lleva el valor procesado (2.5 como Double, la cadena sin comillas) — el reporte exige el lexema original, que solo existe como yytext() en el instante en que el lexer lo produce. Capturarlo donde nace o perderlo.
