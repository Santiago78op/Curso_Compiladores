Etapa 2 · La capa que valida el orden

La gramática y el parser

El lexer ya corta y clasifica las palabras. Ahora se construye la capa que decide si esas palabras forman frases válidas: la gramática BNF y el analizador sintáctico con CUP.

Es el corazón teórico del curso (Cap. 4 del Dragón — el más preguntado en parciales).

La pregunta que abre el capítulo 4

¿Por qué no se sigue con expresiones regulares?

Las regex fueron perfectas para los tokens. Pero hay que observar esta expresión válida de DataForge:

DIV( SUM( Max(@notas), Min(@notas) ), 2 )

Para validarla hay que comprobar que cada ( cierra con su ) — a cualquier profundidad de anidación. Y ahí las expresiones regulares tienen un límite matemático:

Una expresión regular no puede contar. Su autómata tiene memoria finita: para «llevo 3 paréntesis abiertos, me faltan 3» a profundidad arbitraria se necesita una pila. El formalismo que la tiene es la gramática libre de contexto (Dragón §4.1: los lenguajes regulares son un subconjunto de los libres de contexto).

Por eso el pipeline tiene dos capas distintas: regex para las palabras (JFlex), gramática para la estructura (CUP). Cada herramienta en su nivel de poder justo.

Concepto nº 1

¿Qué es una gramática libre de contexto?

Un conjunto de reglas de sustitución (producciones) que definen todas las frases válidas de un lenguaje.

Cada producción dice: «este concepto se forma así». Como en español:

<oración>   → <sujeto> <predicado>
<sujeto>    → "El" <sustantivo>
<sustantivo>→ "gato" | "perro"
<predicado> → "duerme" | "corre"

Con 4 reglas quedan definidas todas las oraciones válidas («El gato duerme», «El perro corre»…) y excluidas las inválidas («gato El duerme»). Los ingredientes tienen nombre:

Terminales

Las piezas que NO se sustituyen más: los tokens del lexer (VAR, ID, NUMERO…). Donde termina la sustitución.

No terminales

Los conceptos intermedios (<expresión>, <instrucción>). No existen en el código fuente: los construye el parser al agrupar.

Símbolo inicial

El concepto raíz del que se deriva todo. En DataForge: <inicio> (el programa completo).

Fuente: Dragón §4.2 · nota del vault: Gramática libre de contexto (BNF).

Concepto nº 2

Derivar: de la regla a la frase

Validar una frase = demostrar que se puede llegar a ella desde el símbolo inicial aplicando producciones. A continuación se deriva var:double:: numero <- 2.5 end;:

<instruccion>
  → <declaracion-var>                          (elijo esa alternativa)
  → "var" ":" <tipo> "::" ID "<-" <expresion> "end" ";"
  → "var" ":" "double" "::" ID "<-" <expresion> "end" ";"
  → "var" ":" "double" "::" numero "<-" <expresion> "end" ";"
  → "var" ":" "double" "::" numero "<-" 2.5 "end" ";"   ✓

Cada paso sustituye UN no terminal por una de sus alternativas. Si existe una derivación que produce exactamente los tokens del programa → es válido. Si ningún camino llega → error sintáctico.

El árbol que dibuja esta derivación es el árbol de análisis sintáctico — en la Etapa 3 se usa para ejecutar. CUP hace las derivaciones automáticamente (método LALR, ascendente), pero entender esto a mano es LO que preguntan en el parcial.

La gramática de DataForge · 1 de 2

El núcleo: programa, declaraciones, consola

<inicio>        ::= "PROGRAM" <instrucciones> "END" "PROGRAM"

<instrucciones> ::= <instrucciones> <instruccion>
                  | <instruccion>

<instruccion>   ::= <declaracion-var> | <declaracion-arr>
                  | <imprimir> | <imprimir-columna> | <grafica>

<tipo>          ::= "double" | "char" "[" "]"

<declaracion-var> ::= "var" ":" <tipo> "::" ID "<-" <expresion> "end" ";"
<declaracion-arr> ::= "arr" ":" <tipo> "::" ID_ARREGLO "<-" <lista-valores> "end" ";"

<imprimir>        ::= "console" "::" "print" "=" <lista-expresiones> "end" ";"
<imprimir-columna>::= "console" "::" "column" "=" <expresion> "->" <arreglo> "end" ";"

Dos patrones para leer: la recursión de <instrucciones> («una lista es una lista más una instrucción») expresa "una o más"; y <instruccion> con | es un menú de alternativas.

Tal como quedó prometido en la Etapa 1, acá el token END se desambigua: en <inicio> va seguido de PROGRAM; dentro de una instrucción, de ;. El contexto lo da la gramática, no el lexer.

La gramática de DataForge · 2 de 2

Expresiones (recursivas) y gráficas

<expresion>   ::= NUMERO | CADENA | ID
                | <aritmetica> | <estadistica>

<aritmetica>  ::= <operacion> "(" <expresion> "," <expresion> ")"
<operacion>   ::= "SUM" | "RES" | "MUL" | "DIV" | "MOD"

<estadistica> ::= <funcion-est> "(" <arreglo> ")"
<arreglo>     ::= ID_ARREGLO | <lista-valores>

<grafica>     ::= <tipo-grafica> "(" <atributos> ")" "end" ";"
<atributo>    ::= ID "::" <tipo> "=" <valor-atributo> "end" ";"
                | "EXEC" <tipo-grafica> "end" ";"

La joya está en <aritmetica>: dentro lleva <expresion>, y <expresion> puede ser <aritmetica> — esa recursión mutua es lo que permite anidar a cualquier profundidad. Los paréntesis balanceados salen gratis de la estructura.

Bonus del diseño del lenguaje: como las operaciones son funciones con paréntesis (SUM(a,b)) y no operadores infijos (a+b), casi no hay ambigüedad ni hace falta tabla de precedencia. La BNF completa está en docs/gramatica.txt — que además es un entregable del proyecto (§8).

De la teoría a la herramienta

El archivo .cup: la BNF ejecutable

Igual que el .flex era la tabla de tokens hecha receta, el .cup es la BNF hecha receta. CUP genera de él dos clases: Parser (el analizador LALR) y sym (¡la que veníamos escribiendo a mano!).

/* 1. declarar los TERMINALES = los tokens del lexer */
terminal PROGRAM, END, VAR, ARR, DOUBLE, CHAR;
terminal Double NUMERO;
terminal String CADENA, ID, ID_ARREGLO;

/* 2. declarar los NO TERMINALES = los conceptos */
non terminal inicio, lista_instr, instruccion, expr;

/* 3. el símbolo inicial */
start with inicio;

/* 4. las producciones: BNF con ::= y ; */
inicio      ::= PROGRAM lista_instr END PROGRAM ;

lista_instr ::= lista_instr instruccion
              | instruccion ;

El círculo se cierra: la lista de terminal genera la clase sym real. Por eso ahora se borra el sym.java temporal de la Etapa 1 — el lexer, sin cambiar una letra, pasa a usar las constantes generadas por CUP. Lexer y parser quedan hablando el mismo idioma por construcción.

Manejo de errores

Cuando el programa está mal escrito

Si al parser le llega un token que no puede seguir a lo ya leído según la gramática, CUP llama a syntax_error. Lo personalizamos en el bloque parser code:

parser code {:
    public void syntax_error(Symbol s) {
        System.err.printf(
            "Error sintáctico: no se esperaba '%s' (línea %d, columna %d)%n",
            s.value, s.left + 1, s.right + 1);
    }
:};

Prueba mental: var:double:: numero 2.5 end; (sin el <-). El lexer NO se queja — todos los tokens existen. El que se queja es el parser: después de ID esperaba ASIGNACION y llegó NUMERO. Error sintáctico, no léxico — la diferencia exacta que pide la tabla de errores del enunciado (§6.2).

Línea y columna salen de los Symbol que fabrica el lexer (yyline/yycolumn) — la Etapa 1 ya venía preparada para esto.

Chequeo rápido · Etapa 2

¿Cómo piensa un parser?

1 · console::print = "hola" 15 end; (falta la coma). ¿Quién detecta el problema: lexer o parser? ¿Por qué?

El parser. "hola" y 15 son tokens perfectamente válidos (CADENA, NUMERO) — el lexer los entrega sin quejarse. Es la gramática la que dice que entre expresiones de un print debe venir COMA. Error sintáctico.

2 · ¿Qué producción hace posible SUM(SUM(SUM(1,2),3),4) a cualquier profundidad?

La recursión mutua: <aritmetica> ::= <operacion> "(" <expresion> "," <expresion> ")" y <expresion> ::= … | <aritmetica>. Cada nivel de anidación es una vuelta más por ese ciclo — y la pila del parser lleva la cuenta de los paréntesis.

3 · ¿Por qué pudimos borrar el sym.java temporal sin tocar el Lexer.flex?

Porque el .flex solo referencia constantes por nombre (sym.VAR…), y las declaraciones terminal del .cup generan una clase sym con esos mismos nombres. Mientras coincidan, quién la genera es indiferente. Diseñamos la Etapa 1 sabiendo esto.
