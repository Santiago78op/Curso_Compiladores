Dragón §6.1

Del árbol al DAG: no calcular dos veces lo mismo

El AST ya fue presentado (caps. 2 y 5). El capítulo agrega una variante elegante: si una subexpresión aparece dos veces, ¿para qué tener dos subárboles idénticos? Compartirlos convierte el árbol en un DAG (grafo dirigido acíclico):

a + a * (b - c) + (b - c) * d

      árbol: (b-c) aparece DOS veces          DAG: una sola vez, compartida
              +                                        +
           ┌──┴──┐                                  ┌──┴──┐
           +     *                                  +     *
         ┌─┴─┐ ┌─┴─┐                              ┌─┴─┐ ┌─┴┐
         a   * (b-c) d                            a   * │  d
           ┌─┴─┐                                    ┌─┴─┤
           a (b-c)   ← duplicado                    a   (b-c)  ← compartido

El DAG es la primera optimización del libro que se ve nacer: detectar subexpresiones comunes y evaluarlas una vez. Para los intérpretes del curso es opcional (evaluar dos veces solo cuesta tiempo), pero el concepto — la representación intermedia puede ser más lista que el fuente — es la semilla de todo el cap. 8 en adelante.

Fuente: Dragón §6.1.1–6.1.2 (DAG y value-numbering).

Dragón §6.2 — cultura de compilador

Tres direcciones: el idioma neutro del back-end

Ya se vio pasar en el cap. 1: a lo sumo un operador por instrucción, con temporales t1, t2… para los resultados parciales. Es el formato en que los compiladores optimizan:

fuente:  a = b * -c + b * -c

tres direcciones:        como cuádruplos (op, arg1, arg2, result):
t1 = minus c              (minus, c,  —,  t1)
t2 = b * t1               (mult,  b,  t1, t2)
t3 = minus c              (minus, c,  —,  t3)
t4 = b * t3               (mult,  b,  t3, t4)
t5 = t2 + t4              (add,   t2, t4, t5)
a  = t5                   (assign,t5, —,  a)

¿Por qué existe? Porque optimizar y generar código máquina sobre el AST directamente es incómodo: el formato lineal con temporales expone cada cálculo y cada dependencia. Sobre esta lista, el DAG de la diapositiva anterior se nota solito: t3, t4 repiten a t1, t2.

Para los proyectos del curso: no se lo genera nunca — la «representación ejecutable» es el AST mismo. Pero en el parcial teórico puede caer «traduzca a tres direcciones / cuádruplos», y es mecánico: un temporal por operador, respetando precedencia.

Fuente: Dragón §6.2.1–6.2.3 (direcciones, cuádruplos, tripletas).

Dragón §6.3

Tipos y declaraciones: poblar la tabla de símbolos

Un tipo es una expresión formal: básicos (int, float, boolean…) y constructores sobre ellos — array(20, int), funciones, registros. Declarar es asociar en la tabla de símbolos un nombre con su tipo (y para un compilador, su dirección de memoria).

El libro (§6.3)DataForge (hecho ✅)CompScript (viene)
D → T id ; D puebla la tablavar:double::numero <- 2.5 end; → Entorno guarda (numero, DOUBLE, 2.5)Igual + tipo de retorno de funciones
array(n, T) con layout: ancho = n × ancho(T)Arreglos 1D: el Entorno guarda la lista y su tipo base — sin layout: la JVM administra la memoriaÍdem, quizá 2D (matrices)
Redeclarar un nombre en el mismo ámbito = errorError semántico que el código detecta al insertar en la tabla — con línea y columna para el reporte

La diferencia clave intérprete/compilador en este tema: el compilador calcula direcciones y anchos (offset de cada variable en memoria); el intérprete delega eso en las estructuras de Java. En este caso, declarar = insertar en el mapa con su tipo. El tipo es lo que importa: es lo que el chequeo consulta.

Fuente: Dragón §6.3.1–6.3.3 (expresiones de tipo, equivalencia, declaraciones).

Dragón §6.5 — el corazón semántico

Chequeo de tipos: reglas que suben por el árbol

El chequeo de tipos es una SDD más (¡cap. 5 en acción!): el atributo sintetizado es el tipo de cada subexpresión, y las reglas dicen cómo combinarlos:

// regla típica de suma aritmética, estilo libro:
E → E₁ + E₂     si E₁.tipo = int   y E₂.tipo = int   → E.tipo = int
                si E₁.tipo = float o E₂.tipo = float → E.tipo = float
                                                        (coerción del int)
                en otro caso                          → ERROR de tipos

Síntesis de tipos

El tipo de la expresión se calcula desde los hijos, con la declaración como base. Es lo que hace el Operaciones: recibe dos valores tipados, decide el resultado o el error.

Coerción (implícita)

Conversión que inserta el traductor: int → float cuando se mezclan (widening: sin pérdida). La jerarquía del libro: cada tipo puede «ensancharse» al de arriba.

Cast (explícito)

Conversión que pide el programador, incluso con pérdida (narrowing: float → int trunca). El lenguaje decide cuáles permite.

Fuente: Dragón §6.5.1–6.5.2 (reglas, conversiones) · notas del vault: Comprobación de tipos, Conversión de tipos (coerción y cast). El enunciado define estas reglas en su tabla de tipos — Operaciones es esa tabla hecha Java.

Dragón §6.5.3 — el término que el tribunal va a nombrar

Sobrecarga: el + que suma o concatena

Un símbolo sobrecargado tiene distintos significados según su contexto, y se resuelve eligiendo uno por la firma = el operador más los tipos de sus operandos:

// el mismo + , dos significados, resueltos por los tipos:
+ (int,    int)    → suma          3 + 4      = 7
+ (string, string) → concatenación "ho"+"la"  = "hola"
+ (string, int)    → concatenación "x="+5     = "x=5"

Conexión directa con los proyectos: las tablas de compatibilidad de tipos de CompScript/CompInterpreter y el Operaciones.suma de DataForge son sobrecarga de operadores — cada celda ⟨op, tipoIzq, tipoDer⟩ → tipoResultado es una firma. Aunque el código nunca use la palabra, es exactamente §6.5.3. Ojo con la trampa: el "sin sobrecarga" que a veces se dice de estos lenguajes se refiere a funciones de usuario con igual nombre — otro concepto.

Fuente: Dragón §6.5.3 (resolución por firma) · §2.8.3 (comprobación estática) · nota del vault: Comprobación de tipos.

§6.5 en movimiento — cerrando el círculo del cap. 1

El chequeo que insertó inttofloat(60)

En el cap. 1 vimos al análisis semántico corregir el árbol de posicion = inicial + velocidad * 60 «por arte de magia». Estas son las reglas disparando, de las hojas hacia arriba:

tabla de símbolos: posicionfloat inicialfloat velocidadfloat — y el literal 60int
→hojas: cada nombre consulta la tabla, cada literal se autodeclara — 4 tipos listos
→nodo velocidad * 60: float × int — tipos distintos → regla de coerción
→se inserta inttofloat(60) — ahora float × float → el nodo * es float
→nodo inicial + (…): float + float → float, sin coerción
→asignación: posicionfloat ← expresión float compatible ✓ árbol tipado y corregido

Dragón §6.6 — la parte que CompScript va a necesitar

Booleanas y flujo de control: dos mundos, misma semántica

Una expresión booleana tiene dos usos: calcular un valor (true/false) o dirigir el flujo (¿entro al if?). El libro la traduce a saltos; el intérprete la evalúa recorriendo el AST:

// COMPILADOR (§6.6): if (x < 100) y = 0;   // EL INTÉRPRETE (CompScript):
     if x < 100 goto L2                     ejecutar(NodoIf n):
     goto L3                                  cond = evaluar(n.condicion)
L2:  y = 0                                    si cond == true:
L3:  ...                                          ejecutar(n.bloqueThen)

Y la joya de la sección — el corto circuito: en B₁ && B₂, si B₁ es falso, B₂ no se evalúa (ídem || con verdadero). No es una optimización: es semántica observable:

si (x != 0 && 10/x > 2) { … }   // sin corto circuito: división por cero cuando x == 0

En el AST es una decisión de cómo se escribe evaluar(NodoAnd): conviene evaluar el hijo izquierdo primero, y si ya decide, retornar sin tocar el derecho. Si se evalúan los dos y después se aplica &&, el lenguaje no tiene corto circuito. Conviene revisar qué exige el enunciado de CompScript.

Fuente: Dragón §6.6.1 (dos usos), §6.6.6 (evaluación en corto circuito) · nota del vault: Flujo de control y switch.

Dragón §6.7–6.8

Backpatching (por qué no se necesita) y switch (por qué sí)

§6.7 Backpatching. El problema del compilador: al traducir if (B) S en una sola pasada, cuando genera el salto «si B falso ir a…» todavía no sabe a qué instrucción — el destino se conoce después. Solución: dejar el salto en blanco, anotar su posición en una lista, y parchear cuando el destino aparece.

El intérprete es inmune al problema entero: no hay saltos que parchear porque no hay código lineal — ejecutar(NodoIf) simplemente decide qué subárbol recorrer. El destino «del salto» es una llamada recursiva ya disponible. Este es el argumento técnico exacto de por qué los caps. de back-end no aplican a OLC1.

§6.8 Switch. La bifurcación n-vías. El compilador elige estrategia según los casos (cadena de ifs, tabla de saltos, búsqueda binaria). El intérprete: evaluar la expresión una vez y comparar contra cada case — pero ojo con la semántica:

¿Fall-through?

En C, sin break la ejecución sigue al case siguiente. ¿El enunciado lo quiere? Define cómo se recorren los cases del AST.

¿default?

Si ningún case matchea y hay default, corre. Posición libre en C — ¿y en el lenguaje del proyecto?

Evaluar UNA vez

La expresión del switch se evalúa una sola vez, no una por case — importa si tiene efectos (o errores) laterales.

Fuente: Dragón §6.7 (backpatching), §6.8 (switch). Las preguntas de las tarjetas se responden en el enunciado de cada proyecto — conviene leerlas antes de escribir el NodoSwitch.

Chequeo rápido

¿Quedó claro? Probate

Conviene pensar la respuesta antes de revelarla. Si falla alguna, conviene volver unas diapositivas.

1 · Con la jerarquía int → float y la tabla de la demo: ¿qué tipo tiene (2 + 3) * 4.5, y cuántas coerciones se insertan y dónde?

float, con UNA coerción. 2 + 3 es int + int → int, sin conversión (las reglas actúan nodo por nodo: acá nadie mezcla). En el *: int × float → se ensancha el resultado de la suma: inttofloat(t), una sola coerción sobre el nodo de la suma — no sobre el 2 y el 3 por separado. El chequeo trabaja sobre el árbol, no sobre el texto.

2 · Un evaluar(NodoAnd) hace: izq = evaluar(a); der = evaluar(b); return izq && der;. Compila, y todos los tests de tablas de verdad pasan. ¿Qué test lo destruye?

Uno donde el lado derecho no deba ejecutarse: x = 0; si (x != 0 && 10/x > 1) … — esa versión evalúa 10/x y explota (división por cero) donde la semántica de corto circuito dice «falso, tranquilo». Las tablas de verdad no lo detectan porque el valor es idéntico; lo que cambia es qué se ejecuta. Corto circuito es semántica observable, no optimización.

3 · Explicá en una frase por qué un compilador necesita backpatching para el while y un intérprete de AST no.

Porque el compilador emite código lineal con saltos a direcciones que aún no existen (y debe volver a parchearlas), mientras que el intérprete de AST conserva el árbol: «saltar» es decidir qué subárbol recorrer, y «repetir» es volver a llamar ejecutar(n.cuerpo) en un bucle de Java — los destinos son referencias que ya existen, nunca direcciones por conocer.
