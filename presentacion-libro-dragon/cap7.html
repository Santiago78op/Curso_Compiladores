Capítulo 7 · Entornos en tiempo de ejecución

El capítulo donde el Entorno crece

Dragón §7.1

Las cuatro zonas de la memoria de un programa

┌───────────────────┐
│   CÓDIGO          │  las instrucciones compiladas — tamaño fijo
├───────────────────┤
│   ESTÁTICA        │  globales y constantes — tamaño conocido al compilar
├───────────────────┤
│   MONTÍCULO (heap)│  objetos con vida "libre" (new) — crece hacia abajo ↓
├───────────────────┤
│        ↕ libre    │
├───────────────────┤
│   PILA (stack)    │  una activación por llamada viva — crece hacia arriba ↑
└───────────────────┘

La división responde a una pregunta por zona: ¿cuánto vive cada dato? El código y lo estático viven todo el programa; lo de la pila vive lo que dura su llamada; lo del heap vive hasta que nadie lo usa.

El intérprete corre dentro de la JVM, que ya tiene sus cuatro zonas. Pero el vocabulario aplica también acá: cuando CompScript ejecute una recursión sin caso base, la pila de entornos crecerá hasta reventar — y queda claro que el StackOverflowError de Java es literalmente esto: la pila chocando contra el heap.

Fuente: Dragón §7.1.1, fig. 7.1 (subdivisión típica de la memoria).

Dragón §7.2.1–7.2.2

Activación: cada llamada es un mundo nuevo

Una activación es una ejecución de un procedimiento. La palabra importa: si fact se llama a sí misma 3 veces, hay un procedimiento y tres activaciones — cada una con su propio n.

Las activaciones de una corrida forman el árbol de activación: el padre llama a los hijos, y los hijos terminan antes que el padre:

              main()
             ┌──┴─────────┐
        fact(3)        imprimir(r)
           │
        fact(2)          ← cada nodo: una activación
           │                con SUS propios parámetros y locales
        fact(1)

De ahí la observación que funda todo el capítulo: como las activaciones terminan en orden inverso al que empezaron (el hijo muere antes que el padre), una pila las administra perfecto. En cada instante, la pila contiene el camino de la raíz a la activación actual.

Fuente: Dragón §7.2.1 (árboles de activación), §7.2.2 (registros). Vida de una activación = su nodo y todo lo de abajo.

Dragón §7.2.2 — la equivalencia central

Registro de activación ≈ el Entorno

Cada activación vive en un registro de activación (frame): un bloque en la pila con todo lo que esa ejecución necesita. Se compara el del libro con su equivalente en el proyecto:

Campo del frame (libro, fig. 7.5)Para quéEn el intérprete (CompScript)
Parámetros realesLos argumentos de esta llamadaVariables pre-cargadas en el Entorno nuevo: n → 3
Datos localesVariables declaradas adentroEntradas que el cuerpo agrega a ese mismo Entorno
Valor de retornoLo que la llamada devuelveEl valor que el ejecutar() retorna al evaluar la llamada
Enlace de controlApunta al frame del llamador (para volver)Gratis: la pila de llamadas de Java — la recursión de ejecutar()
Enlace de accesoApunta al entorno donde buscar los no localesLa referencia padre del Entorno — ojo: NO es el llamador (diapositiva 7)
Estado de máquina (registros, dirección de retorno)Reanudar al llamador tal como estabaNo aplica: la JVM lo administra automáticamente

La traducción completa en una frase: «llamar a una función» = crear un Entorno nuevo con los parámetros adentro, ejecutar el cuerpo sobre él, y destruirlo al retornar. Todo lo demás del capítulo son los detalles de esa frase.

§7.2 en movimiento

La pila ejecutando fact(3)

funcion fact(n) {  si (n <= 1) { retornar 1; }  retornar n * fact(n - 1);  }
pila: global — se evalúa la llamada fact(3)…
→pila: globalfact · n=3 — 3 > 1: necesita fact(2)
→pila: globalfact · n=3fact · n=2 — 2 > 1: necesita fact(1)
→pila: globalfact · n=3fact · n=2fact · n=1 — caso base: retorna 1
→pila: globalfact · n=3fact · n=2fact · n=1 — completa 2 × 1: retorna 2
→pila: globalfact · n=3fact · n=2 — completa 3 × 2: retorna 6
→pila: global — la expresión vale 6 ✓ tres activaciones, tres n distintos, cero conflictos

Dragón §7.3 — el bug clásico de los intérpretes de OLC1

¿Y si la función usa una variable que no es suya?

Dentro de fact aparece fact (¡y podría aparecer una global!). Los nombres que no están en el entorno local se buscan siguiendo el enlace de acceso — la cadena de padres. La pregunta de diseño es: ¿quién es el padre del entorno nuevo?

Alcance estático ✓

El padre es el entorno donde la función fue definida (para CompScript sin funciones anidadas: el global). Lo que ve la función se decide leyendo el fuente. Es lo que hacen C, Java y lo que el enunciado espera.

Alcance dinámico ✗

El padre es el entorno del llamador. Lo que ve la función depende de quién la llamó — imposible de razonar leyendo el código.

El bug clásico

Escribir new Entorno(entornoActual) al ejecutar la llamada. Compila, funciona en tests simples… y las locales del llamador se filtran dentro de la función: alcance dinámico accidental.

// CORRECTO (estático):                  // BUG (dinámico accidental):
Entorno e = new Entorno(global);         Entorno e = new Entorno(entornoActual);
// el test que los distingue:  var x = 1;  funcion f(){ imprimir(x); }
// funcion g(){ var x = 99; f(); }   →  g() debe imprimir 1, no 99

Fuente: Dragón §7.3.1–7.3.2 (alcances), §7.3.5–7.3.6 (enlaces de acceso). Los bloques { } internos sí encadenan con el entorno actual — la demo está en La tabla de símbolos, a fondo.

Dragón §7.4–7.6 — cultura general

El montículo y el recolector: lo que la JVM regala

La pila muere en orden; los objetos no: un arreglo creado dentro de una función puede sobrevivirla (si se retorna). Para esas vidas «libres» existe el montículo — y con él, el problema de saber cuándo liberar:

Gestión manual

C: malloc/free. Poder total, bugs totales: dangling pointers (liberar temprano) y memory leaks (no liberar nunca).

Garbage collection

El runtime encuentra lo inalcanzable (nada apunta ahí) y lo recicla. Java, JS, Python. El cap. §7.5–7.6 estudia sus algoritmos (marcar-y-barrer, copia, generacional).

La posición del intérprete en el mapa

Los intérpretes del curso corren sobre la JVM/Node: cuando un Entorno muere y nada lo referencia, el GC lo recicla. La «gestión de memoria» es no retener referencias de más.

Ironía instructiva: se escribe un intérprete cuyo runtime (el de Java) fue construido con las técnicas de este mismo capítulo. Es el capítulo donde la herramienta y el proyecto son el mismo objeto de estudio a dos escalas.

Fuente: Dragón §7.4 (montículo), §7.5 (GC básico), §7.6 (GC avanzado) — lectura ligera recomendada, sin ejercicios.

Chequeo rápido

¿Quedó claro? Probate

Conviene pensar la respuesta antes de revelarla. Si falla alguna, conviene volver unas diapositivas.

1 · En el punto más profundo de fact(3): ¿cuántas activaciones de fact hay vivas, y por qué el n de una no pisa el de otra?

Tres (n=3, n=2, n=1), las tres en la pila a la vez. No se pisan porque n no vive «en la función»: vive en el registro de activación — cada llamada tiene el suyo. Un procedimiento, muchas activaciones; el código es compartido, los datos no.

2 · Con el bug del padre-llamador: var x = 1; funcion f(){ imprimir(x); } funcion g(){ var x = 99; f(); } g(); — ¿qué imprime la versión con bug y qué debía imprimir?

El bug imprime 99: el entorno de f tiene como padre al de g, así que la búsqueda de x encuentra la local del llamador (alcance dinámico). Debía imprimir 1: con alcance estático, f se definió en el global y su cadena de acceso es f → global, donde x vale 1. Metételo en los casos de prueba de CompScript desde el día uno.

3 · ¿Por qué retornar conviene implementarlo como una «señal que sube» y no como un simple valor de retorno de ejecutar()?

Porque el retornar puede estar enterrado: dentro de un if, dentro de un while, dentro de un bloque — y al dispararse debe abortar todo lo pendiente hasta salir de la función. Si fuera un valor normal, cada nodo intermedio (bloque, ciclo) tendría que chequearlo y propagarlo a mano — y un olvido = bug. Como señal (excepción propia que el nodo-función captura), el recorrido se corta solo, exactamente como la transferencia de control no local del libro. Ídem break/continue capturados por el nodo-ciclo.
