Capítulo 3 · Análisis léxico

El capítulo que vive dentro de JFlex

Cada vez que se corre mvn compile y JFlex convierte el .flex en un Lexer.java, se está ejecutando este capítulo completo: expresiones regulares → autómatas → una tabla que reconoce tokens a velocidad constante por carácter.

Objetivo: escribir cualquier .flex entendiendo qué hace la herramienta con él, y responder la parte de autómatas del parcial.
Se navega con las flechas ← → o con los botones de abajo.

Dragón §3.1

El lexer es el empleado del parser

En la arquitectura del libro, el léxico no corre «primero y aparte»: el parser manda. Cada vez que necesita un token, le pide el siguiente al lexer:

        pedime el siguiente token (next_token)
PARSER ────────────────────────────────────▶ LEXER ──▶ lee caracteres
       ◀────────────────────────────────────        del programa fuente
        queda: ⟨ID, "numero", línea 3, col 15⟩

¿Y por qué separar léxico de sintáctico, si ambos «leen» el fuente? El libro da tres razones:

1

Simplicidad

La gramática no se contamina con detalles de caracteres: piensa en ID y NUMERO, no en «letra seguida de letras o dígitos». Cada capa, su problema.

2

Eficiencia

El lexer es la única parte que toca cada carácter del fuente. Especializarla (búferes, autómatas tabulares) hace rápido todo el pipeline.

3

Portabilidad

Rarezas del alfabeto y la codificación quedan encapsuladas en una sola pieza.

En CUP esto es literal: Parser llama a next_token() del Lexer que generó JFlex. Fuente: Dragón §3.1, fig. 3.1.

Dragón §3.1.3

¿Qué es (y qué no es) un error léxico?

Un error es léxico solo cuando ningún patrón del lenguaje puede empezar con lo que sigue en la entrada. Es la categoría de error más local que existe: un carácter que no pertenece al vocabulario.

Entrada¿Error léxico?Por qué
var:double:: ñum <- 2.5 end;Sí (la ñ)Ese carácter no arranca ningún patrón del lenguaje
fi (x == 1) en CNofi es un identificador perfectamente válido — el error aparecerá después, como sintáctico
var double:: x (falta un :)NoTodos los tokens son válidos; el orden está mal → sintáctico

Recuperación en «modo pánico» léxico: la estrategia más simple del libro y la que usa el proyecto — descartar el carácter ofensivo, registrar el error y seguir desde el siguiente. El análisis nunca se detiene: el enunciado pide reportar todos los errores, no rendirse en el primero.

Fuente: Dragón §3.1.3 · en DataForge: la regla comodín final del .flex registra el error en el Entorno y no devuelve token.

Dragón §3.3 — el vocabulario formal

Alfabeto, cadena, lenguaje — y tres operaciones

Antes de las expresiones regulares, tres definiciones (van a caer en el parcial tal cual):

TérminoDefiniciónEjemplo
Alfabeto ΣConjunto finito de símbolosΣ = {0,1}, el ASCII, el Unicode
CadenaSecuencia finita de símbolos de Σ (ε = la vacía)2.5, var, ε
LenguajeCualquier conjunto de cadenas sobre Σ«todos los identificadores válidos»

Y sobre lenguajes se definen las tres operaciones que generan todo lo demás:

Unión L ∪ M

Cadenas de uno o del otro. En ER: la barra |.

Concatenación LM

Una cadena de L seguida de una de M. En ER: escribir una pieza tras otra.

Cerradura de Kleene L*

Cero o más repeticiones. La estrella que hace infinito a un patrón finito.

Fuente: Dragón §3.3.1–3.3.2. Con esto, «identificador» deja de ser una idea y pasa a ser un conjunto definido con precisión matemática.

Dragón §3.3.3–3.3.5

Expresiones regulares: el idioma de los patrones

Una ER es una fórmula que denota un lenguaje usando solo símbolos, |, concatenación y * (más paréntesis). Todo lo demás es azúcar sintáctica — así se traduce la teoría al .flex:

Teoría (libro)JFlexSignifica
a | ba|ba o b
ababa seguida de b
a*a*cero o más a
a⁺ = aa*a+una o más a
a | εa?a opcional
a|b|…|z[a-z]clase de caracteres

Y las definiciones regulares (§3.3.4) son nombres para ER, que se usan en otras ER — exactamente la primera sección del .flex:

// teoría              // JFlex
letra  → [A-Za-z]       Letra  = [a-zA-Z]
digito → [0-9]          Digito = [0-9]
id     → letra (letra|digito)*     Id = {Letra}({Letra}|{Digito})*
num    → digito⁺ (. digito⁺)?      Num = {Digito}+ ("." {Digito}+)?

Fuente: Dragón §3.3.3 (ER), §3.3.4 (definiciones regulares), §3.3.5 (extensiones + ? […]).

Dragón §3.5 en movimiento — las dos reglas de oro de Lex

Cómo decide el lexer: match más largo, primera regla

Con varios patrones compitiendo, Lex/JFlex decide siempre igual: ① gana el match más largo; ② a igual largo, gana la regla escrita primero. A continuación, la línea de DataForge tokenizándose (nombres de token ilustrativos):

entrada: var:double::numero <- 2.5
→var matchean la reservada "var" y {Id} — mismo largo → regla ② → VAR
→: ¿: o ::? lo que sigue es d, así que solo alcanza para : → DOS_PUNTOS
→double reservada le gana a {Id} por regla ② → DOUBLE
→:: matchean : (1 carácter) y :: (2) — regla ① → DOBLE_DOS_PUNTOS
→numero ninguna reservada matchea, solo {Id} → ID, lexema "numero"
→<- matchean < (menor) y <- — regla ① → ASIGNACION
→2.5 matchean 2 (entero, corto) y 2.5 — regla ① → NUM_DOUBLE ✓ 7 tokens

Dragón §3.5 — de Lex a JFlex

Anatomía de un archivo .flex

El libro presenta Lex (1975); JFlex es su descendiente para Java. La estructura de tres secciones separadas por %% es la misma desde entonces:

// ① código de usuario: package, imports (va tal cual al Lexer.java)
package dataforge.analisis;
%%
// ② directivas y definiciones regulares
%public  %class Lexer  %cup  %line  %column
Letra  = [a-zA-Z]
Digito = [0-9]
Id     = {Letra}({Letra}|{Digito})*
%%
// ③ reglas: patrón → acción (el orden ES semántica: regla ②)
"var"        { return simbolo(sym.VAR); }        // reservadas PRIMERO
{Id}         { return simbolo(sym.ID, yytext()); }
[^]          { registrarErrorLexico(); }          // comodín al FINAL

Dos gotchas ya vistas en DataForge y que ahora tienen nombre teórico: %public es obligatorio (sin él la clase queda package-private y CUP no la ve), y las reservadas van antes de {Id} — es la regla de prioridad de §3.5.3 aplicada.

Fuente: Dragón §3.5 (estructura de un programa Lex, resolución de conflictos) · nota del vault: JFlex.

Dragón §3.6–3.9 — el motor bajo el capó

¿Y cómo reconoce JFlex los patrones? Autómatas

JFlex no «prueba» las regex una por una: las compila a una máquina. El pipeline del libro:

las ER del .flex
   │  construcción de Thompson (§3.7.4): piezas de LEGO con transiciones ε
   ▼
  AFN   autómata no determinista: varios caminos posibles a la vez
   │  construcción de subconjuntos (§3.7.1): perseguir todos los caminos
   ▼
  AFD   autómata determinista: UN estado, UNA transición por carácter
   │  minimización (§3.9.6): fusionar estados equivalentes
   ▼
  AFD mínimo  →  una tabla int[estado][carácter] dentro de Lexer.java

AFN

Fácil de construir desde la ER, caro de ejecutar (hay que rastrear muchos estados a la vez).

AFD

Caro de construir, pero rapidísimo de ejecutar: un lookup de tabla por carácter, O(n) total.

La compra

Se paga la conversión una vez (al compilar el .flex) y se ejecuta barato siempre. La misma compra de todo generador.

Las demos animadas de este pipeline ya existen en el curso de DataForge: la profundización Autómatas, en movimiento construye Thompson pieza por pieza, corre la construcción de subconjuntos y simula el AFD resultante con ababb. Este deck no lo repite: conviene visitarla, jugarla y volver.

Fuente: Dragón §3.6 (AF), §3.7 (algoritmos), §3.9 (optimización) · nota del vault: Autómata finito (AFN y AFD).

¿Para qué sirve la teoría si JFlex la hace sola?

Dos razones concretas: el parcial y el debugging

1 · El parcial de OLC1 pregunta esto. Los ejercicios clásicos del capítulo son mecánicos si se conocen los algoritmos:

Ejercicio típicoAlgoritmo que lo resuelve
«Construya el AFN de (a|b)*abb»Thompson: una pieza por operador, cablear con ε
«Convierta ese AFN a AFD»Subconjuntos: cerradura-ε + mover, estado = conjunto
«Minimice el AFD»Particiones: separar estados distinguibles
«¿Acepta la cadena ababb?»Simular la tabla, carácter por carácter

2 · Debugging del .flex. Cuando un token «se come» de más (una cadena sin comilla de cierre que devora el archivo), cuando una reservada sale como ID, cuando 2.5.3 tokeniza raro — la causa es siempre una de las dos reglas de oro o un patrón cuya ER no dice lo que parecía. Sabiendo la teoría, el bug se lee en el patrón; sin ella, solo se sufre.

Chequeo rápido

¿Quedó claro? Un repaso rápido

Conviene pensar la respuesta antes de revelar. Si alguna falla, conviene volver unas diapositivas.

1 · En un .flex alguien mueve la regla {Id} arriba de las reservadas. El archivo compila perfecto. ¿Qué se rompe, y en qué capa aparece el error?

Toda reservada empata en largo con {Id}, y ahora {Id} está primero: var, double, end… salen todos como token ID. El lexer no falla nunca — el error explota en el parser como error sintáctico («se esperaba VAR»), lejos de su causa real. Moraleja: los bugs léxicos suelen disfrazarse de sintácticos.

2 · ¿Por qué JFlex se toma el trabajo de convertir AFN → AFD si el AFN ya reconoce el lenguaje correctamente?

Por costo de ejecución. Simular un AFN exige rastrear un conjunto de estados por cada carácter (con cerraduras ε incluidas). El AFD tiene exactamente un estado activo y una transición por carácter: un acceso a tabla, O(1) por carácter, O(n) por archivo. La conversión se paga una sola vez al compilar el .flex; la velocidad se cobra en cada ejecución.

3 · Un compañero define Cadena = \".*\" y con la entrada "hola" + "mundo" su lexer devuelve UNA sola cadena gigante. ¿Qué regla de oro lo traicionó y cómo se arregla?

El match más largo. .* puede abarcar hola" + "mundo completo y cerrar con la última comilla — y como ese match es más largo, gana. Arreglo: prohibir comillas dentro del patrón con una clase negada: \"[^\"\n]*\". Ahora el match más largo posible termina en la primera comilla de cierre. La regla no era el enemigo; el patrón decía otra cosa.
