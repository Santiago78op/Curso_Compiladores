Etapa 2 · Parte 1

De la secuencia de tokens al árbol

La segunda mitad de grammar.jison (después del %%) declara la gramática de producciones. Es LALR(1), igual clase de analizador que CUP — la diferencia frente a DataForge no está en la teoría, está en que acá cada producción construye explícitamente un nodo de árbol en vez de ejecutar la instrucción de una vez.

Resolviendo ambigüedad antes de escribir una sola producción

La tabla 5.10 del enunciado, en directivas de Jison

/* de MENOR a MAYOR precedencia — asi las declara Jison */
%right IF DOSPUNTOS          /* ternario: mas bajo que todo */
%left OR                     /* nivel 7 */
%left AND                    /* nivel 6 */
%right NOT                   /* nivel 5 */
%left IGUAL DIFERENTE MENOR MENORIGUAL MAYOR MAYORIGUAL IS   /* nivel 4 */
%left MAS MENOS              /* nivel 3 */
%left POR DIV MODULO         /* nivel 2 */
%nonassoc POTENCIA RAIZ      /* nivel 1 */
%right UMINUS                /* nivel 0: la mas alta */

Coincide, nivel por nivel, con la tabla de precedencia del enunciado (sección 5.10). %nonassoc en potencia/raíz es la forma en que Jison expresa la nota del enunciado de que no son asociativos: 2^3^2 sin paréntesis es directamente un error de gramática, no una ambigüedad que se resuelve a la izquierda o a la derecha.

Ojo con el entregable: esta tabla de precedencia es un mecanismo de la herramienta Jison, no forma parte de la gramática BNF que exige el enunciado (sección 8, «no debe ser una copia del archivo de Jison»). Por eso docs/gramatica.txt reescribe las expresiones en capas (expresion-or → expresion-and → ... → expresion-unaria) para quedar libre de ambigüedad por construcción, sin usar %left/%right. La pieza que hace posible un AST genérico

Una sola función construye cualquier nodo

/* codigo de soporte, al final de grammar.jison */
function nodo(tipo, props, loc) {
  var n = { tipo: tipo };
  if (props) { for (var k in props) { if (props.hasOwnProperty(k)) n[k] = props[k]; } }
  if (loc) { n.linea = loc.first_line; n.columna = loc.first_column + 1; }
  return n;
}

Todo nodo del árbol, sin excepción, tiene la propiedad tipo (una cadena: 'IF', 'BINARIA', 'LLAMADA'...), y casi todos tienen linea/columna (usadas por el reporte de errores). El resto de las propiedades depende de la producción.

// una asignacion binaria real, tal como la arma el parser
expresion : expresion MAS expresion
    { $$ = nodo('BINARIA', { op: '+', izq: $1, der: $3 }, @2); }
    ;

// el nodo IF, con su cadena opcional de else-if
if_stmt : IF PARIZQ expresion PARDER bloque ELSE if_stmt
    { $$ = nodo('IF', { cond: $3, entonces: $5, sino: [$7] }, @1); }
    ;

Por qué importa esta uniformidad: el módulo que dibuja el AST como grafo (Etapa 6) recorre cualquier nodo sin conocer de antemano sus tipos — le basta con la convención { tipo, ... }. Agregar una construcción nueva al lenguaje nunca obliga a tocar el código de visualización.

Una decisión de diseño anotada en el propio código

Inicializar un vector con el resultado de una nativa

El enunciado (5.15.1) solo contempla dos formas de inicializar un vector: new vector tipo[n] o una lista literal [1, 2, 3]. Pero varias funciones nativas —reverse, toCharArray— devuelven precisamente un vector, y se necesita poder guardar ese resultado:

let v: int[] = reverse(otro);   // no aparece literal en 5.15.1

La gramática agrega una tercera alternativa, documentada en el propio archivo como extensión propia:

vector_init1
    : NEW VECTOR tipo CORIZQ expresion CORDER
        { $$ = nodo('VECTOR_NEW', { tipoBase: $3, tam: $5 }, @1); }
    | CORIZQ lista_expresiones CORDER
        { $$ = nodo('VECTOR_LISTA', { valores: $2 }, @1); }
    | expresion
        { $$ = nodo('VECTOR_EXPR', { expr: $1 }, @1); }
    ;

Sin conflicto de gramática: una expresion nunca empieza con NEW ni con CORIZQ en las posiciones donde estas tres alternativas compiten, así que el parser LALR(1) puede decidir con un solo token de anticipación cuál regla aplica.

Modo pánico, versión Jison

La producción error no detiene todo el análisis

elemento_global
    : declaracion PUNTOCOMA          { $$ = $1; }
    | funcion                        { $$ = $1; }
    | ejecutar_stmt                  { $$ = $1; }
    | error PUNTOCOMA                { $$ = nodo('ERROR', {}); }
    ;

Igual que instruccion ::= error PUNTOCOMA en el .cup de DataForge: cuando el parser no puede continuar con las reglas normales, la producción especial error descarta tokens hasta encontrar el punto de sincronización (;) y sigue analizando el resto del archivo desde ahí, en vez de abortar en el primer error sintáctico.

Los errores no se pierden en el camino: parser.yy.parseError (ver Etapa 5) registra la descripción del error en el arreglo compartido antes de que la recuperación entre en juego, así que el reporte final los conserva todos aunque el parseo termine relanzando una excepción no recuperable.

Verificado con un caso real del proyecto

106 nodos, 105 aristas — un árbol de verdad

Corriendo analizar() sobre entradas/ejemplo_vectores2d.ci (vectores de una y dos dimensiones, con reverse/max/min/sum/average), el AST resultante tiene 106 nodos y 105 aristas: exactamente nodos − 1, la propiedad que cualquier árbol (sin ciclos) debe cumplir.

Nodos: 106
Aristas: 105
Errores: 0

Esta verificación aritmética simple (aristas = nodos − 1) es una forma barata de confirmar que la fábrica de nodos y el recorrido del grafo (Etapa 6) están construyendo un árbol y no, por error de alguna referencia compartida, un grafo con ciclos.

Chequeo rápido

Sobre el parser y el AST

1 · ¿Por qué POTENCIA y RAIZ se declaran con %nonassoc en vez de %left o %right?

Porque el enunciado (5.10) indica que no son asociativos: encadenar dos veces seguidas sin paréntesis (2^3^2) debe ser un error de gramática, no algo que se resuelva a la izquierda o a la derecha por defecto. %nonassoc es la directiva de Jison que expresa exactamente esa restricción.

2 · La gramática BNF entregable (docs/gramatica.txt) no usa %left/%right. ¿Cómo resuelve entonces la precedencia de operadores?

Reescribiendo las expresiones en capas anidadas (expresion-or → expresion-and → expresion-not → expresion-relacional → expresion-suma → expresion-termino → expresion-potencia → expresion-unaria → expresion-primaria), donde cada capa solo puede combinar elementos de la capa inmediatamente inferior. Es una gramática libre de ambigüedad por construcción, sin depender de ningún mecanismo de la herramienta.

3 · ¿Qué permite que el módulo de reporte del AST (Etapa 6) no necesite actualizarse cada vez que se agrega un tipo de nodo nuevo?

Que todos los nodos, sin excepción, se construyen con la misma fábrica nodo(tipo, props, loc) y respetan la convención { tipo: string, ...propiedades }. El recorrido del grafo detecta hijos con una sola condición genérica (typeof x.tipo === 'string'), sin una lista de casos por tipo de nodo.
