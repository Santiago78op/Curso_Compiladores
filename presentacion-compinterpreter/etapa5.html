Etapa 5 · Parte 1

Un servidor delgado sobre un pipeline completo

server/server.js es corto a propósito: no contiene lógica de análisis ni de ejecución, solo expone por HTTP lo que ya construyeron las etapas anteriores (Jison + Interprete). Toda la inteligencia vive en analizar.js y el paquete interprete/; el servidor solo traduce peticiones HTTP a llamadas de función y respuestas JSON.

El único endpoint que importa

POST /interpretar, de punta a punta

const express = require('express');
const cors = require('cors');
const { analizar } = require('./src/analizar');

const app = express();
const PUERTO = process.env.PORT || 4000;

app.use(cors());                              // CORS para el cliente de dev (Vite)
app.use(express.json({ limit: '5mb' }));

app.get('/', (req, res) => {
  res.json({ nombre: 'CompInterpreter', estado: 'ok', endpoint: 'POST /interpretar { codigo }' });
});
app.get('/salud', (req, res) => res.json({ estado: 'ok' }));

app.post('/interpretar', (req, res) => {
  const codigo = (req.body && typeof req.body.codigo === 'string') ? req.body.codigo : '';
  try {
    const resultado = analizar(codigo);
    res.json(resultado);
  } catch (e) {
    res.status(500).json({ errores: [{ tipo: 'Interno', descripcion: e.message || String(e), linea: 0, columna: 0 }], ... });
  }
});

GET /salud existe únicamente para que la suite de pruebas Playwright (Etapa 7) pueda esperar a que el servidor esté realmente listo antes de empezar a interactuar con el cliente.

La pieza que conecta todo

analizar.js: Jison, el intérprete y los reportes, en orden

function analizar(codigo) {
  const errores = new ListaErrores();
  const parser = obtenerParser();

  // yy compartido entre lexer y parser (ver Etapa 1)
  parser.yy = { errores: errores.errores };
  parser.yy.parseError = function (msg, hash) { /* arma descripcion + errores.sintactico(...) */ };
  parser.parseError = parser.yy.parseError;

  let ast = null;
  try { ast = parser.parse(codigo); }
  catch (e) { if (!errores.hay()) errores.sintactico(e.message || 'Error de análisis', 0, 0); }

  const interprete = new Interprete(errores);
  if (ast) {
    try { interprete.interpretar(ast); }
    catch (e) { errores.semantico('Error interno durante la ejecución: ' + (e.message || e), 0, 0); }
  }

  const grafo = ast ? construirGrafo(ast) : { nodes: [], edges: [] };
  return {
    errores: errores.errores.slice().sort((a, b) => (a.linea - b.linea) || (a.columna - b.columna)),
    consola: interprete.consola.join('\n'),
    consolaLineas: interprete.consola,
    simbolos: Array.from(interprete.simbolos.values()),
    ast: grafo,
    dot: aDot(grafo)
  };
}

Nótese el try/catch alrededor de interprete.interpretar(ast): es la última línea de defensa contra cualquier excepción de JavaScript no anticipada durante la ejecución — el mismo tipo de excepción que, antes de la corrección de la Etapa 4, convertía el bug del vector en un "Error interno" genérico en vez de un error semántico localizado.

Decisión de diseño explícita en el manual técnico

Ninguna ejecución contamina a la siguiente

Cada llamada a analizar(codigo) crea su propia ListaErrores y su propio Interprete — y con él, un Entorno global nuevo. Nada persiste entre peticiones.

El mismo principio que en DataForge. La Guía técnica lo documenta explícitamente: «Cada invocación a POST /interpretar construye una nueva instancia de la lista de errores y del intérprete... Esta decisión evita que variables, funciones o errores de una ejecución anterior persistan o interfieran en la siguiente, garantizando que los reportes correspondan exclusivamente al último análisis realizado.» Es exactamente la misma regla que en DataForge («entorno fresco por ejecución», enunciado §6) — cambia el vehículo (una petición HTTP en vez de una corrida de la GUI), no el principio.

Esto también es lo que hace seguro correr el servidor con varios clientes o pestañas conectadas al mismo tiempo: no hay estado global compartido entre peticiones concurrentes más allá del propio proceso Node.js.

Un detalle de despliegue que sí importa en desarrollo

Por qué hace falta cors()

En desarrollo, el cliente Vite corre en su propio puerto (típicamente 5173) y el servidor Express en otro (4000). Son orígenes distintos desde la perspectiva del navegador, así que sin CORS el navegador bloquearía las peticiones fetch del cliente hacia el servidor, aunque ambos corran en la misma máquina.

app.use(cors());   // habilitado globalmente para todas las rutas

client/src/api.js apunta al servidor mediante la variable de entorno VITE_API_URL (por defecto http://localhost:4000); si el puerto del servidor cambia, hay que actualizar esa variable en el cliente.

Chequeo rápido

Sobre el servidor y su contrato

1 · ¿Por qué server.js casi no tiene lógica propia, más allá de recibir la petición y llamar a analizar()?

Porque separa dos responsabilidades: el protocolo de transporte (HTTP, JSON, CORS) es responsabilidad de server.js; el análisis léxico/sintáctico/semántico y la ejecución son responsabilidad de analizar.js y el paquete interprete/. Esa separación permitiría, en teoría, invocar analizar() directamente desde un script de consola sin levantar ningún servidor — como de hecho se hizo para verificar los casos de prueba (Etapa 3 y Etapa 7).

2 · ¿Qué pasaría si analizar() reutilizara el mismo Interprete entre peticiones en vez de crear uno nuevo cada vez?

Las variables globales, funciones y errores de una ejecución anterior seguirían presentes en la siguiente: el reporte de símbolos mostraría variables que ya no existen en el código actual, y errores de una corrida previa podrían mezclarse con los de la corrida nueva. Por eso la Guía técnica documenta "entorno fresco por llamada" como una decisión de diseño explícita, no un detalle accidental.

3 · ¿Para qué sirve específicamente GET /salud, si el cliente nunca lo usa durante el uso normal de la aplicación?

Lo usa la suite de pruebas automatizadas (Playwright, Etapa 7) para esperar a que el servidor Express termine de arrancar antes de empezar a interactuar con el cliente — evita condiciones de carrera donde las pruebas intentan ejecutar código antes de que /interpretar esté disponible.

Etapa 5 · construida

El servidor está en pie y responde por contrato

POST /interpretar con un contrato JSON estable, entorno fresco por petición, CORS habilitado para el desarrollo con orígenes separados, y una arquitectura donde el transporte HTTP nunca se mezcla con la lógica de análisis. Falta la otra mitad: quién consume ese contrato desde el navegador.
