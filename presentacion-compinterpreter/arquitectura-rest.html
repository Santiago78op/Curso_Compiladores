Profundización ★

La diferencia arquitectónica que distingue a CompInterpreter

DataForge, ConjAnalyzer y CompScript son los tres aplicaciones de escritorio: JavaFX corriendo en un único proceso, donde la interfaz llama directamente a los métodos del intérprete. CompInterpreter es el único de los cuatro proyectos del curso con una arquitectura cliente-servidor real, separada por una API REST sobre HTTP. Este módulo profundiza en esa diferencia.

Dos formas de conectar interfaz y motor

Llamada directa vs. petición HTTP

Monolito (DataForge, JavaFX)Cliente-servidor (CompInterpreter)
Proceso(s)Uno solo: la GUI y el intérprete comparten memoriaDos independientes: servidor Express (Node.js) y cliente Vite (navegador)
Cómo se invoca el análisisLlamada de método Java directa: new Interprete(codigo)Petición HTTP: fetch('/interpretar', { method: 'POST', body: JSON.stringify({codigo}) })
Formato de intercambioObjetos Java en memoria compartidaJSON serializado sobre el cuerpo de la petición/respuesta
¿Puede la UI vivir en un dispositivo distinto al motor?No — mismo proceso, misma máquina, obligatoriamenteSí — el servidor podría correr en otra máquina sin cambiar el cliente
CostoSin latencia de red, sin serializaciónCada ejecución paga el costo de una petición HTTP + JSON.stringify/parse

Por qué el enunciado lo exige así: uno de los objetivos específicos del Proyecto 2 pide explícitamente «Generar aplicaciones utilizando la arquitectura cliente-servidor», y la sección 9 (Restricciones) exige «Se debe visualizar todo desde el navegador». No es una elección de diseño libre — es un requisito que fuerza a separar el motor de análisis (que no puede vivir en el navegador: Jison corre sobre Node.js) de la interfaz (que sí debe vivir ahí).

El contrato es la única frontera que importa

Todo lo que el cliente sabe del servidor es este JSON

Una vez que existe una frontera HTTP, el contrato de la API se vuelve la única fuente de verdad compartida entre dos códigos que, en tiempo de ejecución, nunca comparten memoria. El cliente no sabe (ni necesita saber) que el análisis léxico corre con Jison, que el AST se recorre en dos pasadas, o cómo se implementan las señales de control — solo conoce la forma de la respuesta.

POST /interpretar { "codigo": "..." }
  →
{
  "errores":        [...],
  "consola":        "...",
  "consolaLineas":  [...],
  "simbolos":       [...],
  "ast":             { nodes, edges },
  "dot":            "..."
}

Esto es exactamente el mismo tipo de desacoplamiento que separa un compilador real de su IDE: el compilador no sabe cómo el editor va a mostrar sus diagnósticos, y el editor no necesita entender el algoritmo de análisis — ambos coordinan a través de un formato de mensaje acordado.

Una consecuencia directa de la arquitectura

¿Por qué CADA petición necesita su propio intérprete?

En un monolito de escritorio hay un único usuario y una única ejecución a la vez — no hace falta pensar en concurrencia. Un servidor Express, en cambio, puede recibir varias peticiones POST /interpretar superpuestas (dos pestañas del navegador, dos estudiantes probando al mismo tiempo si el servidor fuese compartido). Si el Interprete guardara estado entre peticiones, una ejecución podría leer variables o errores de otra que ni siquiera terminó.

function analizar(codigo) {
  const errores = new ListaErrores();      // nuevo en CADA llamada
  ...
  const interprete = new Interprete(errores);   // nuevo Entorno global, cada vez
  ...
}

El mismo principio, forzado por dos razones distintas. DataForge exige "entorno fresco por ejecución" porque el enunciado pide reportes solo del último análisis (una razón de correctitud de reportes). CompInterpreter necesita exactamente lo mismo, pero además por una razón de concurrencia que no existe en un monolito de un solo usuario: sin estado nuevo por petición, ejecuciones simultáneas se contaminarían entre sí.

Otra consecuencia directa: el navegador desconfía por defecto

CORS no existe en un monolito porque no hay "otro origen"

En JavaFX, la ventana de la aplicación y el intérprete son el mismo programa — el concepto de "origen" (protocolo + dominio + puerto) ni siquiera aplica. En cliente-servidor, el navegador aplica la política de mismo origen a cualquier fetch: si el cliente (http://localhost:5173) y el servidor (http://localhost:4000) están en puertos distintos, son orígenes distintos, y el navegador bloquearía la respuesta sin el encabezado adecuado.

app.use(cors());   // server.js — sin esto, el fetch del cliente fallaría en desarrollo

Es un ejemplo concreto de cómo una restricción de seguridad del navegador (irrelevante para una app de escritorio) se vuelve una pieza obligatoria del servidor en cuanto la arquitectura cambia a cliente-servidor.

Chequeo rápido

Sobre la arquitectura REST

1 · Si un compañero preguntara "¿por qué no llamar directamente a las funciones del intérprete desde el cliente, como hace DataForge con JavaFX?", ¿cuál sería la respuesta correcta?

Porque el intérprete corre sobre Node.js (usa el parser generado por Jison, que es una librería de Node) y el cliente corre dentro del navegador, en un proceso completamente distinto y con un runtime distinto (el navegador no ejecuta módulos de Node directamente). Además, el enunciado exige explícitamente la arquitectura cliente-servidor como objetivo del proyecto, no como una opción entre varias igualmente válidas.

2 · ¿Qué pasaría si el servidor NO creara un Interprete nuevo en cada petición, en el contexto específico de una arquitectura cliente-servidor (a diferencia de un monolito)?

Dos peticiones concurrentes (dos pestañas, dos usuarios) podrían pisarse el estado mutuamente: variables globales, funciones registradas o errores acumulados de una ejecución aparecerían mezclados con los de otra que corrió al mismo tiempo. En un monolito de escritorio de un solo usuario este riesgo de concurrencia simplemente no existe.

3 · ¿En qué se parece el contrato REST de CompInterpreter a la relación entre un compilador real y el IDE que lo invoca?

En que ambos coordinan a través de un formato de mensaje acordado (en este caso, el JSON de POST /interpretar) sin que un lado necesite conocer los detalles internos del otro. El cliente no sabe que hay dos pasadas del AST ni cómo se implementan las señales de control; solo sabe interpretar errores, consola, simbolos y ast.

Profundización ★ · completa

Una frontera HTTP, dos consecuencias de diseño

El contrato REST no es solo "cómo se comunican las partes" — obliga a un entorno fresco por petición (razón de concurrencia, no solo de correctitud de reportes) y a habilitar CORS (una restricción de navegador que no existe en un monolito). Entender esta arquitectura es entender por qué CompInterpreter, aunque resuelve el mismo problema teórico que los otros tres proyectos del curso, se construye con decisiones de diseño que ellos no necesitan.
