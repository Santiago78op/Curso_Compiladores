Etapa 7 · Parte 1

Verificar el sistema completo, no sus piezas por separado

Las etapas anteriores se pueden (y se verificaron) probar por separado: analizar() desde una consola de Node, componentes de React de forma aislada. Una prueba de extremo a extremo (E2E) es distinta: levanta el servidor Express y el cliente Vite juntos, abre un navegador de verdad y confirma que la aplicación completa —tal como la usaría un estudiante— se comporta como se espera.

Playwright orquesta ambos procesos

Un solo comando levanta servidor + cliente + navegador

client/playwright.config.js configura Playwright para arrancar automáticamente tanto el servidor Express como el cliente Vite antes de correr las pruebas, y apagarlos al terminar. El script e2e del package.json del cliente (playwright test) es el punto de entrada.

Por qué GET /salud importa acá: Playwright necesita saber cuándo el servidor terminó de arrancar antes de dejar correr las pruebas contra él — ese endpoint mínimo (Etapa 5) es justamente el mecanismo que usa la configuración para esperar sin condiciones de carrera.

Test 1 de 3 · el camino feliz

Ejecutar el ejemplo del Anexo y verificar los 4 reportes

test('ejecuta el ejemplo del anexo y muestra consola/símbolos/AST', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: '▶ Ejecutar' }).click();

  // Sin errores: el panel debe quedar en Consola automáticamente.
  await expect(page.locator('.pestana.es-activa')).toHaveText('Consola');
  const consola = page.locator('.consola');
  await expect(consola).toContainText('X es mayor que Y y no es cero');
  await expect(consola).toContainText('El valor de i es: 4');
  await expect(consola).toContainText('La suma de 3 y 7 es: 10');

  await page.getByRole('button', { name: /Errores/ }).click();
  await expect(page.locator('.panel-vacio')).toContainText('Sin errores');

  await page.getByRole('button', { name: 'Símbolos' }).click();
  await expect(page.locator('.tabla-reporte tbody tr', { hasText: 'x' }).first()).toBeVisible();

  await page.getByRole('button', { name: 'AST' }).click();
  await expect(page.locator('.ast-grafo canvas')).toBeVisible();
});

El archivo inicial que carga el editor es exactamente el ejemplo del Anexo 11.1 del enunciado (ejemplo-anexo.js en el cliente) — la prueba confirma valores de salida esperados de ese programa específico, no solo "que algo se imprimió".

Test 2 de 3 · los tres tipos de error, a propósito

Reportar errores y navegar a la línea con un clic

test('reporta errores léxicos/sintácticos/semánticos y salta a la línea', async ({ page }) => {
  await page.goto('/');
  const textarea = page.locator('.editor-textarea');
  await textarea.click();
  await textarea.fill(EJEMPLO_ERRORES);   // entradas/ejemplo_errores.ci
  await page.getByRole('button', { name: '▶ Ejecutar' }).click();

  await expect(page.locator('.pestana.es-activa')).toHaveText(/Errores/);

  const filas = page.locator('.tabla-reporte tbody tr');
  await expect(filas).toHaveCount(8);
  await expect(page.locator('.fila-error-léxico')).toHaveCount(1);
  await expect(page.locator('.fila-error-sintáctico')).toHaveCount(2);
  await expect(page.locator('.fila-error-semántico')).toHaveCount(5);

  await filas.first().click();
  await expect(page.locator('.editor-gutter-linea.es-actual')).toHaveText('5');
});

Confirma, en un solo test, tres cosas a la vez: que el panel salta solo a "Errores" (Etapa 6), que el desglose exacto por tipo coincide con lo verificado manualmente en la Etapa 1 (1 léxico + 2 sintácticos + 5 semánticos = 8), y que hacer clic en una fila mueve el editor a la línea correcta (Etapa 6, irALinea).

Test 3 de 3 · lo más simple, pero igual de necesario

Nuevo archivo agrega una pestaña editable

test('nuevo archivo agrega una pestaña editable', async ({ page }) => {
  await page.goto('/');
  const pestanasIniciales = await page.locator('.file-tab').count();

  await page.getByRole('button', { name: 'Nuevo' }).click();
  await expect(page.locator('.file-tab')).toHaveCount(pestanasIniciales + 1);
  await expect(page.locator('.file-tab.es-activa')).toContainText('sin-titulo-');
});

Corto, pero cubre una funcionalidad explícitamente exigida por el enunciado (4.2: "Nuevo archivo: El editor deberá de ser capaz de crear archivos en blanco") que de otro modo dependería enteramente de pruebas manuales.

Chequeo rápido

Sobre las pruebas E2E

1 · ¿Qué diferencia hay entre correr analizar() directamente desde una consola Node (como en las Etapas 3-4) y correr la suite Playwright?

Correr analizar() desde consola prueba solo el motor de análisis/ejecución, sin servidor HTTP ni interfaz. Playwright levanta el sistema completo — servidor Express real, cliente Vite real, navegador real— y verifica la integración entre todas las piezas: que el fetch llegue, que el JSON se parsee bien, que el DOM refleje el resultado correctamente.

2 · El test 2 usa el mismo archivo ejemplo_errores.ci que se verificó manualmente en la Etapa 1. ¿Por qué es valioso reutilizar el mismo caso en vez de inventar uno nuevo para la prueba automatizada?

Porque ya se conoce el resultado esperado exacto (8 errores: 1 léxico, 2 sintácticos, 5 semánticos) de haberlo corrido directamente contra analizar(). Reutilizarlo permite que la prueba E2E confirme que ese mismo resultado, ya verificado a nivel de motor, también llega correctamente hasta la interfaz — en vez de introducir una nueva fuente de verdad que habría que volver a auditar.

3 · ¿Por qué el endpoint GET /salud (Etapa 5) es relevante específicamente para esta suite de pruebas?

Porque Playwright arranca el servidor y el cliente como parte de la propia ejecución de las pruebas, y necesita un mecanismo confiable para saber cuándo el servidor ya está listo para recibir peticiones antes de dejar avanzar los tests — sin ese endpoint, existiría el riesgo de una condición de carrera donde el primer test intenta ejecutar código antes de que el servidor esté escuchando.
