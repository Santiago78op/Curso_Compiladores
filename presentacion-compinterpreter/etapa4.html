Etapa 4 · Parte 1

break, continue, return: sin una sola excepción de JS

Podría implementarse con throw/try/catch de JavaScript — es la solución más obvia. CompInterpreter eligió otra: un valor de señal que cada instrucción devuelve hacia quien la contiene, y que cada estructura de control decide cómo interpretar.

Cómo funciona

Una señal es un objeto, no una excepción

case 'BREAK': return { tipo: 'BREAK', linea: nodo.linea, columna: nodo.columna };
case 'CONTINUE': return { tipo: 'CONTINUE', linea: nodo.linea, columna: nodo.columna };
case 'RETURN': {
  const v = nodo.valor ? this.evaluar(nodo.valor, entorno) : null;
  return { tipo: 'RETURN', valor: nodo.valor ? v : null, tieneValor: !!nodo.valor };
}

ejecutarBloque() recorre una lista de instrucciones y, en cuanto una de ellas devuelve una señal no nula, corta el recorrido y la retorna hacia arriba — sin ejecutar el resto del bloque:

ejecutarBloque(instrucciones, entorno) {
  for (const inst of instrucciones) {
    const senal = this.ejecutarInstruccion(inst, entorno);
    if (senal) return senal;
  }
  return null;
}

Cada ciclo decide qué hacer con la señal que recibe. while/for/do-until/loop: BREAK corta el ciclo, CONTINUE salta a la siguiente iteración (en for, cae primero en la actualización), y RETURN simplemente se re-propaga sin tocarlo, hasta llegar a la función que lo originó.

Una ventaja inesperada del mismo mecanismo

El fall-through de switch es el mismo truco

El enunciado (5.16.2) exige explícitamente que un case sin break siga evaluando los case siguientes — comportamiento clásico de C/Java, distinto del switch de muchos lenguajes modernos. Con señales, implementarlo es casi gratis:

for (const caso of nodo.casos) {
  if (!coincidio) {
    const ce = this.evaluar(caso.expr, local);
    const igual = ops.relacional('==', expr, ce, ...);
    if (igual !== null && igual.valor === true) coincidio = true;
  }
  if (coincidio) {
    const senal = this.ejecutarBloque(caso.cuerpo, local);
    if (senal) {
      if (senal.tipo === 'BREAK') return null;
      return senal;   // RETURN / CONTINUE se propagan
    }
  }
}

Una vez que coincidio pasa a true, el bucle deja de volver a evaluar la expresión de cada case y simplemente sigue ejecutando cuerpos hasta toparse con una señal BREAK — o hasta acabarse los casos, cayendo en default si existe.

Lo que el enunciado no pide, pero el servidor necesita

Límites contra ciclos infinitos y recursión desbordada

GuardaLímiteDónde se aplica
MAX_ITER1,000,000 iteracionesCada while/for/do-until/loop
MAX_DEPTH2,000 nivelesProfundidad de invocar() (llamadas anidadas/recursión)

Un loop {} sin ninguna forma de salir, o una función que se llama a sí misma sin caso base, colgaría el proceso Node.js del servidor completo — afectando a todas las peticiones concurrentes, no solo a la que causó el problema. Estas dos guardas no están en el enunciado; son una decisión propia para la estabilidad del servidor, y se reportan como error semántico ("Posible ciclo infinito", "Recursión demasiado profunda") en vez de colgar el proceso.

Lo que exige literalmente el enunciado (5.18.2)

continue fuera de un ciclo debe ser un error

El enunciado es explícito: «La sentencia continue siempre debe de estar dentro de un ciclo, de lo contrario será un error». Con el mecanismo de señales, esa validación se resuelve en un único lugar: el punto donde invocar() recibe la señal final que sube desde el cuerpo completo de la función.

const senal = this.ejecutarBloque(fn.cuerpo, local);
this.profundidad--;

// 5.18.2: "continue" (y, por la misma razón, "break") deben estar
// dentro de un ciclo; si la señal escapa hasta el cuerpo de la función o
// método sin que ningún ciclo la consuma, se reporta como error semántico
// en lugar de truncar en silencio el resto de la ejecución.
if (senal && (senal.tipo === 'BREAK' || senal.tipo === 'CONTINUE')) {
  const cual = senal.tipo === 'CONTINUE' ? 'continue' : 'break';
  this.errores.semantico('La sentencia "' + cual + '" debe estar dentro de un ciclo',
    senal.linea, senal.columna);
  return null;
}

Si un BREAK o CONTINUE llega hasta acá, significa que ningún while/for/do-until/loop en el camino lo interceptó — es decir, la instrucción estaba fuera de cualquier ciclo.

Caso de estudio real · Auditoría de código, 21 de julio de 2026

Dos errores reales, encontrados y corregidos

El 21 de julio de 2026 el proyecto pasó por una auditoría de código independiente. No es un ejercicio hipotético: se encontraron y corrigieron dos errores reales en el manejo de las señales de control, ambos relacionados directamente con lo que se acaba de explicar en esta etapa.

Por qué importa mostrar esto en clase: ambos errores son del tipo que un compilador de juguete "casi funcional" suele esconder durante meses — solo se manifiestan con una entrada específica que nadie probó a propósito. Son un buen recordatorio de que "los ejemplos de prueba pasan" no es lo mismo que "el manejo de errores es correcto en todos los casos".

Bug de la auditoría · 1 de 2

Un vector literal con un elemento incompatible tumbaba TODO

Entrada que disparaba el problema:

let v: int[] = [1, "hola", 3];   // "hola" no es coercionable a int

Antes de la corrección: al evaluar el elemento incompatible, la coerción fallaba y devolvía el null de JavaScript (propagación normal por error). Ese null crudo quedaba guardado en esa posición del vector. El problema es que las funciones nativas sobre vectores (sum, max, min, average) y aTexto() leen .tipo de cada elemento sin volver a comprobar si es null — asumen que todo elemento de un vector es siempre una instancia de Valor. Un null crudo ahí producía una excepción de JavaScript no controlada que abortaba toda la interpretación, reportada genéricamente como "Error interno durante la ejecución" — un único elemento mal escrito tumbaba el análisis completo del archivo, en vez de generar un único error semántico localizado en esa línea.

Bug de la auditoría · 1 de 2 (la corrección)

Rellenar con el valor por defecto, no con null

// Igual que coercionarElemento, pero para usarse al RELLENAR un vector
// (listas literales 1D/2D): si la coercion falla, el error semantico ya
// quedo reportado por coercionar(), pero esa posicion del vector NO puede
// quedar en JS null (a diferencia de una expresion suelta que se propaga
// por null): los elementos de un vector deben ser siempre instancias de
// Valor, porque las nativas (sum/max/min/average) y aTexto() leen
// directamente `.tipo` de cada elemento sin volver a chequear null. Se
// rellena con el valor por defecto del tipo base para poder seguir.
coercionarElementoOValorDefecto(tipoBase, v, l, c) {
  const coer = this.coercionar(tipoBase, v, l, c);
  return coer !== null ? coer : new Valor(tipoBase, valorPorDefecto(tipoBase));
}

La distinción clave: una expresión suelta que falla se propaga por null normalmente (nadie más la va a leer). Pero un elemento dentro de un vector va a ser leído después por código que confía en que siempre es un Valor — así que se necesita una variante que, si la coerción falla, rellene con el valor por defecto del tipo base (0 para int, "" para string, etc.) en vez de dejar el hueco.

Resultado después de la corrección: el ejemplo de arriba genera un único error semántico localizado ("no se puede asignar STRING a un elemento de tipo INT", con línea y columna), y el resto de la interpretación continúa con normalidad — exactamente el comportamiento esperado de propagación por causa única.

Bug de la auditoría · 2 de 2

break/continue fuera de un ciclo no generaba error

El enunciado exige explícitamente (5.18.2, citado en la diapositiva anterior de esta misma etapa) que continue fuera de un ciclo sea un error. Antes de la corrección, la validación en invocar() solo se aplicaba a CONTINUE — literal, sin extenderla a BREAK por el mismo criterio.

Consecuencia real: un break; escrito por error fuera de cualquier ciclo (por ejemplo, directamente en el cuerpo de una función, sin ningún while/for alrededor) no generaba ningún mensaje en el reporte de errores. La señal BREAK subía sin ser consumida hasta el final del cuerpo de la función y, ahí, simplemente se descartaba en silencio — truncando la ejecución de las instrucciones restantes de esa función sin dejar ningún rastro en la consola ni en la tabla de errores.

Por qué es peor que un error visible: un error que no se reporta es el peor tipo de error para quien depura un programa — el código simplemente deja de ejecutar instrucciones sin ninguna pista de por qué. La corrección extiende la misma validación de CONTINUE a BREAK "por consistencia": ambos son señales que solo tienen sentido dentro de un ciclo, y ambos ahora se validan en el mismo punto de invocar() (código mostrado en la diapositiva anterior).

Caso de estudio real · Segunda auditoría, 23 de julio de 2026

Un bug que tres proyectos del curso compartían

Una segunda auditoría —esta vez cruzada, sobre varios proyectos del curso a la vez— encontró en CompInterpreter que los operadores lógicos && y || no cortocircuitaban: el caso LOGICA evaluaba siempre ambos lados antes de operar.

let x: int = 0;
if (x != 0 && 10 / x > 1) { ... }   // reportaba "División entre cero"

La guarda x != 0 existe precisamente para que 10 / x no se evalúe cuando x es 0 — pero sin cortocircuito, la derecha se evaluaba igual y disparaba el error que la guarda debía evitar. La corrección: si el operando izquierdo (booleano) ya decide el resultado (false para &&, true para ||), se retorna sin evaluar la derecha.

La lección transversal: este mismo defecto estaba en tres proyectos del curso. CompScript lo había encontrado y corregido en su propia auditoría; VLangCherry y CompInterpreter lo arrastraban. De ahí la regla que guió esta ronda: todo bug confirmado en un proyecto se verifica en los demás. La misma auditoría cerró aquí otros huecos latentes: un método void usado como expresión (let x = m();) o con un return valuado, índices de vector no enteros, y las nativas sum/average/max/min sobre vectores con elementos sin asignar.

Chequeo rápido

Sobre señales y la auditoría

1 · ¿Por qué CompInterpreter no usa throw/try-catch de JavaScript para implementar break/continue/return?

El código no lo documenta como una prohibición técnica de JS (las excepciones funcionarían), sino como una decisión de diseño propia: un objeto de señal que cada instrucción retorna es un flujo de control explícito y visible en cada función (ejecutarBloque, execWhile, etc.), mientras que una excepción viajaría de forma implícita y sería más difícil de rastrear en cada punto donde se decide qué hacer con ella — además de que el mismo mecanismo resuelve gratis el fall-through de switch.

2 · En el bug 1 (vector con elemento incompatible), ¿por qué NO alcanza con propagar null de JavaScript como en cualquier otra expresión?

Porque una posición de un vector no es una expresión suelta: va a ser leída después por funciones (sum, max, min, average, aTexto()) que asumen que todo elemento es una instancia de Valor y leen .tipo directamente sin comprobar null. Un null crudo ahí provoca una excepción no controlada, no un error semántico limpio.

3 · ¿Qué tienen en común los dos bugs de la auditoría, en términos de qué tipo de error de compilador representan?

Los dos son fallas del manejo de errores, no del "camino feliz": ambos ocurren únicamente cuando el programa de entrada tiene un problema (un tipo incompatible, una instrucción de control fuera de contexto), y en ambos casos el síntoma era peor que un mensaje de error — silenciar el problema (bug 2) o abortar todo sin localizar la causa (bug 1). Confirman por qué la propagación por causa única y la validación explícita son partes centrales del diseño, no un detalle secundario.

4 · Con la corrección del cortocircuito, ¿por qué x != 0 && 10 / x > 1 ya no reporta "División entre cero" cuando x es 0?

Porque el operando izquierdo x != 0 es false, y en && un izquierdo falso ya decide el resultado (false) sin importar la derecha — así que 10 / x no llega a evaluarse. Ese es justamente el propósito del cortocircuito: permite usar el lado izquierdo como guarda del derecho. Antes de la corrección ambos lados se evaluaban siempre, y la división entre cero ocurría pese a la guarda.

Etapa 4 · construida y auditada

El control de flujo queda robusto

Señales en vez de excepciones resuelven break/continue/return y, de paso, el fall-through del switch. Guardas de estabilidad protegen al servidor de ciclos infinitos y recursión desbordada. Y dos auditorías —el 21 y el 23 de julio de 2026— corrigieron errores reales que ningún ejemplo de prueba anterior había ejercitado, incluido el cortocircuito de &&/|| que tres proyectos del curso compartían.
