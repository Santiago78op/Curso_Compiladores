Un patrón de React para exponer control interno hacia el padre

forwardRef + useImperativeHandle: saltar a una línea desde afuera

Cuando el usuario hace clic en una fila de la tabla de errores o de símbolos, hay que mover el cursor del editor a esa línea — pero el estado del cursor vive dentro de Editor.jsx, no en App.jsx. En vez de subir todo ese estado al padre, el editor expone un único método:

const Editor = forwardRef(function Editor({ value, onChange, erroresPorLinea }, ref) {
  const textareaRef = useRef(null);
  ...
  useImperativeHandle(ref, () => ({
    irALinea(num) {
      const ta = textareaRef.current;
      const offsets = value.split('\n').reduce(
        (acc, l) => { acc.push(acc[acc.length - 1] + l.length + 1); return acc; }, [0]
      );
      const pos = offsets[Math.max(0, num - 1)] || 0;
      ta.focus();
      ta.setSelectionRange(pos, pos);
      setLinea(num);
      const destino = (num - 1) * LINE_HEIGHT - ta.clientHeight / 2;
      ta.scrollTop = Math.max(0, destino);
      ...
    },
  }));

App.jsx guarda una ref al editor y, en el manejador de clic de cada fila, simplemente llama editorRef.current.irALinea(numero) — sin necesidad de conocer cómo el editor calcula la posición del cursor internamente.

Por qué no alcanza con un <textarea> plano

El gutter de números de línea es un <div> aparte

HTML no tiene numeración de línea nativa en un <textarea>. La solución: un <div> separado (.editor-gutter) con un número por línea, cuyo scrollTop se sincroniza a mano con el del <textarea> en cada evento de scroll:

const sincronizarScroll = (e) => {
  const top = e.target.scrollTop;
  setScrollTop(top);
  if (gutterRef.current) gutterRef.current.scrollTop = top;
};

La línea actual se recalcula contando saltos de línea hasta la posición del cursor (onKeyUp/onClick/onFocus) y se resalta con una franja posicionada por cálculo, no por selección CSS de fila:

<div className="editor-linea-resaltada" style={{ top: (linea - 1) * LINE_HEIGHT - scrollTop }} />

Las líneas con error reciben la clase tiene-error a partir de un Set<number> (erroresPorLinea) que App.jsx recalcula con useMemo cada vez que cambia el resultado de la última ejecución.

Una decisión de UX pequeña, verificada por la suite de pruebas

El panel de reportes salta solo a donde importa

const manejarEjecutar = async () => {
  ...
  const res = await interpretar(archivoActivo.contenido);
  setResultado(res);
  setPanel(res.errores && res.errores.length ? 'errores' : 'consola');
  ...
};

Si la ejecución produjo errores, el panel salta automáticamente a la pestaña "Errores" — el usuario no tiene que ir a buscarlos. Si no hay errores, se queda mostrando la "Consola" con la salida de los echo. Este comportamiento no es un detalle cosmético: es exactamente lo que verifica el primer y el segundo test de la suite Playwright (Etapa 7).

6.3 del enunciado: "se deben mostrar los nodos... como un grafo"

AstGrafo.jsx: el árbol ya viene armado, solo se dibuja

El servidor ya entrega { nodes, edges } completos (Etapa 2 y 5) — el cliente no reconstruye el árbol, solo lo renderiza con vis-network:

const options = {
  layout: {
    hierarchical: {
      enabled: true,
      direction: 'UD',          // de arriba hacia abajo
      sortMethod: 'directed',
      levelSeparation: 90,
      nodeSpacing: 150,
    },
  },
  nodes: { shape: 'box', color: { background: colorFondoNodo, border: colorBorde }, ... },
  edges: { arrows: { to: { enabled: true, scaleFactor: 0.6 } }, ... },
  physics: false,   // ya es jerarquico: no hace falta simulacion de fuerzas
};

Colores desde las variables CSS del tema: getComputedStyle(document.documentElement).getPropertyValue('--accent') (y equivalentes para texto/fondo/bordes) lee los mismos custom properties que usa el resto de la interfaz — el grafo respeta el tema claro/oscuro automáticamente, sin duplicar la paleta de colores en el componente.

4.1/4.2 del enunciado

Nuevo, Abrir, Guardar — sin backend de archivos

Como el cliente vive completamente en el navegador, "abrir" y "guardar" no tocan un sistema de archivos del servidor — usan APIs del propio navegador:

Nuevo

Agrega un archivo vacío sin-titulo-N.ci al arreglo de App.jsx y lo activa.

Abrir

<input type="file" accept=".ci"> oculto + FileReader.readAsText para leer el contenido en memoria.

Guardar

Arma un Blob, genera una URL con URL.createObjectURL y dispara una descarga mediante un <a download> invisible.

App.jsx mantiene archivos como un arreglo de { id, nombre, contenido, sinGuardar }; FileTabs.jsx los renderiza y permite cerrar pestañas (deshabilitado si solo queda una abierta).

Chequeo rápido

Sobre el cliente React

1 · ¿Por qué Editor.jsx usa forwardRef + useImperativeHandle en vez de simplemente recibir la línea de destino como una prop más?

Porque "ir a una línea" es una acción imperativa puntual (mover el cursor, hacer scroll), no un cambio de estado que deba re-renderizarse en cada actualización. Exponer un método vía ref permite que el padre lo dispare cuando ocurre el evento (un clic) sin tener que modelar esa acción como parte del flujo normal de props/estado de React.

2 · El cliente no reconstruye el árbol del AST a partir de los nodos crudos del intérprete — ¿qué recibe exactamente y de dónde?

Recibe la estructura { nodes: [{id, label}], edges: [{from, to, label}] } ya calculada por el servidor (ast-grafo.js, Etapa 2), como parte de la respuesta JSON de POST /interpretar. El cliente solo se encarga de la visualización con vis-network, no de recorrer el AST original.

3 · ¿Por qué AstGrafo.jsx desactiva la física (physics: false) en vez de dejar que vis-network simule fuerzas entre nodos como en un grafo genérico?

Porque un AST ya es, por definición, una jerarquía (un árbol con raíz): el layout hierarchical con dirección 'UD' ya calcula una disposición ordenada de arriba hacia abajo. Simular física adicional (repulsión/atracción entre nodos) sería redundante y solo produciría una animación de acomodo innecesaria antes de estabilizarse.
